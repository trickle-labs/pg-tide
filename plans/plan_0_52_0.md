# pg_tide v0.52.0 implementation plan

> **Status:** Proposed
> **Release theme:** Security and Supply-Chain Assurance
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.51.0 and current `main`
> **Implementation branch:** `implementation-v0.52.0`
> **Scope rule:** Validate and close the security boundaries of the reduced v1
> product. Reuse the v0.44 security controls and the existing release-evidence
> system. Do not add connectors, build a general secret manager, audit removed
> Labs code, or redesign delivery semantics.

## 1. Release outcome

v0.52.0 is complete when an independent reviewer can start from the exact
release commit and prove these claims:

1. PostgreSQL callers have only the documented publisher, relay, operator,
   reader, or administrator permissions.
2. An authorization lookup error denies the operation and leaves persistent
   state unchanged.
3. Every supported production network path either verifies the remote peer or
   requires a named development override that appears in validation and logs.
4. The webhook sink refuses every documented server-side request forgery
   bypass class before it sends a request.
5. A generated canary secret does not appear in any supported output channel.
6. The `core` and `core-kafka` dependency graphs contain no unapproved critical
   or high vulnerability and satisfy the repository license policy.
7. Every production artifact contains only allowlisted files and executables.
8. A separate verification job binds each tag, archive, extension package,
   image, Helm chart, software bill of materials, and provenance statement to
   the same commit and digest.
9. The project has rehearsed its private vulnerability response procedure.
10. An independent security reviewer has approved the exact candidate commit.

The release covers the PostgreSQL 18 extension, the outbox source, PostgreSQL
inbox, NATS JetStream, Apache Kafka, and HTTPS webhook destinations, and these
production profiles:

```text
core
  PostgreSQL source and inbox
  NATS JetStream
  HTTPS webhook

core-kafka
  everything in core
  Apache Kafka
```

`stdout` and `file` remain diagnostic sinks. Their redaction behavior is in
scope, but they are not production destinations. Removed or archived
connectors remain outside the v1 security claim.

Use the controls that already exist:

- `connectors.toml` defines the supported connector and profile boundary.
- `schemas/v1-contract-manifest.toml` defines the frozen public contracts.
- `schemas/lifecycle-compatibility-v1.json` defines adjacent version behavior.
- `tests/required-tests.toml` defines blocking test execution and evidence.
- `docs/src/reference/threat-model.md` documents threats and controls.
- `supply-chain/advisory-exceptions.toml` records time-bounded exceptions.
- `release-evidence/` binds results to a candidate.

Do not add another connector registry, security policy service, release
orchestrator, or test result format.

## 2. Preconditions and scope guard

### 2.1 Release preconditions

Before the first implementation pull request:

1. Confirm that the v0.51.0 tag resolves to the merge commit on `main`.
2. Confirm that every v0.51.0 exit criterion passes on `main`.
3. Run `just check-required-tests`, `just check-v1-contracts`,
   `just check-v1-surface`, and `just check-lifecycle-contract`.
4. Run `just test-security` and retain its output as before-change evidence.
5. Generate the `core` and `core-kafka` normal dependency trees with
   `cargo tree --locked` and retain their digests.
6. Build the current relay archive, PostgreSQL 18 extension package, container,
   Helm chart, and documentation output. Record their file inventories.
7. Record the exact starting commit, Rust version, PostgreSQL version, client
   library versions, container base digest, and pinned GitHub Action commits.
8. Confirm that no v0.52 release blocker has a retry or quarantine allowance.

If the v0.51.0 gate fails, stop. Security review must start from the lifecycle
baseline that v0.51.0 promises.

### 2.2 Frozen contract boundary

The v0.47.0 freeze still covers:

- public `tide.*` SQL signatures and behavior;
- pipeline JSON fields and validation;
- core metric names and labels;
- health behavior;
- CLI JSON fields and exit codes;
- native and CloudEvents envelopes;
- the four supported destination contracts.

v0.52.0 may add optional connector security fields, new refusal codes, bounded
security metrics, and release evidence. It must not rename or remove an existing
v1 field. A stricter default is permitted only when the old behavior could send
credentials or messages without verified transport. Local examples must state
the explicit development override where they use plaintext services.

### 2.3 Explicit non-goals

Do not include the following work:

- a new connector, source type, sink type, or wire format;
- security review of code removed in v0.49.0 or retained only in archives;
- cloud key-management providers;
- Vault, Kubernetes, or cloud secret-manager integrations;
- automatic credential rotation;
- a configurable outbound proxy feature;
- a general network allowlist or firewall product;
- certificate issuance or certificate lifecycle automation;
- formal verification;
- penetration testing claims beyond the executable cases in this plan;
- delivery, retry, checkpoint, replay, or DLQ semantic changes unless a
  security test exposes a violation of the v0.50.0 model;
- PostgreSQL major-version expansion;
- performance budgets or long-run soaks assigned to v0.53.0;
- broad documentation cleanup assigned to v0.54.0;
- tagging or publishing v0.52.0 as part of implementation.

Fix security defects that a required test exposes. Record unrelated findings
for their planned release.

## 3. Security contract

### 3.1 Trust boundaries

Use these boundaries in the threat model, tests, and review:

1. **Application to extension.** Treat SQL arguments, role memberships,
   payloads, headers, and identifiers as untrusted.
2. **Caller to extension owner.** A security-definer function may use owner
   privileges only for its documented operation.
3. **Relay to PostgreSQL.** Treat catalog rows, pipeline JSON, history, offsets,
   receipts, and DLQ rows as persistent security-sensitive state.
4. **Relay to destination.** Treat DNS, certificates, redirects, proxies,
   authentication responses, and destination errors as untrusted.
5. **Secret reference to runtime value.** A reference may persist. A resolved
   secret may exist only in the connector construction and request path.
6. **Build input to production artifact.** Treat dependencies, actions,
   toolchains, base images, downloaded tools, and generated files as inputs that
   require a digest and policy check.
7. **Producer job to verifier.** A job that creates or signs an artifact cannot
   also provide the final independent verification result.
8. **Operator output.** Assume that logs, metrics, status, history, validation,
   diagnostics, test output, and release evidence are visible to someone who
   must not receive secrets.

### 3.2 Security invariants

Every workstream must preserve these invariants:

1. PUBLIC has no implicit mutation or raw configuration access in schema
   `tide`.
2. A publisher can publish only through `tide.outbox_publish()` and only to an
   outbox allowed by `tide.outbox_publishers`.
3. A publisher cannot bypass the ACL with direct table or sequence access.
4. Only an explicit superuser, extension-owner, or positive ACL verdict allows
   publication.
5. A missing role, missing ACL object, denied lookup, null result, or SPI error
   denies the operation.
6. Security-definer functions have a fixed `pg_catalog, tide` search path and
   do not resolve caller-controlled objects.
7. Relay, operator, and reader roles cannot read or mutate data outside their
   documented matrix.
8. A supported production client never falls back from verified TLS to
   plaintext.
9. An insecure development override is explicit in config, rejected from
   production examples, and reported without credentials.
10. DNS validation covers every returned address and the client connects only
    to the validated answers.
11. The webhook client does not follow redirects and does not inherit ambient
    proxy variables.
12. Resolved secrets are absent from persisted config, history, logs, metrics,
    CLI output, diagnostics, panics, test records, and release evidence.
13. A secret file is absolute, regular, owned by the relay user, no broader
    than mode `0600`, not a symlink, valid UTF-8, and at most the existing
    `MAX_SECRET_FILE_BYTES` limit.
14. `cargo build --locked` resolves the reviewed dependency graph.
15. A production dependency exception cannot exist. A non-production exception
    must name an owner, rationale, mitigation, expiry, and removal condition.
16. A production archive or image cannot contain a test fixture, source secret,
    build cache, compiler, shell, package manager, or unapproved executable.
17. Verification checks immutable digests, not mutable tags.
18. A material security change after approval invalidates that approval.
19. Security test failures never advance checkpoints or delete source events.
20. All evidence names the candidate commit and artifact digests that produced
    it.

### 3.3 Development overrides

Retain only connector-level overrides required by local tests and development:

| Path | Secure behavior | Development override | Required signal |
|---|---|---|---|
| PostgreSQL | `verify-full` when the mode is omitted | explicit `sslmode=disable` | validation warning and structured startup warning |
| NATS | `tls://` with peer verification | explicit `allow_insecure = true` with `nats://` | validation warning and structured startup warning |
| Kafka | `ssl` or `sasl_ssl` with certificate verification | explicit `security_protocol = "plaintext"` plus `allow_insecure = true` | validation warning and structured startup warning |
| Webhook | HTTPS, SSRF checks, no redirect, no ambient proxy | existing `allow_http = true` or `ssrf_protection = false` | validation warning and structured startup warning |

Do not add one global switch that disables every security control. Each
override must identify the affected connector and control.

## 7. SEC-2: Review and test PostgreSQL privileges

### Objective

Prove effective permissions from real PostgreSQL catalogs and public calls on
both a fresh v0.52.0 installation and the supported v0.47.0 to v0.52.0 upgrade
path.

### Canonical role matrix

Retain the five `NOLOGIN` group roles created by
`deploy/postgres/pg_tide_roles.sql`:

| Role | Allowed | Must be denied |
|---|---|---|
| `tide_admin` | Configure pg_tide, manage ACLs, and run documented administration | Superuser-only cluster actions and unrelated schemas |
| `tide_publisher` | Execute `tide.outbox_publish()` for an explicitly granted outbox | Direct message insert, other outboxes, config, offsets, receipts, DLQ, replay, and rewind |
| `tide_relay` | Read enabled pipeline and source state; write exact runtime, receipt, DLQ, and monotonic offset state | ACL management, arbitrary config changes, rewind, payload administration, and unrelated schemas |
| `tide_operator` | Read sanitized operations views and run documented bounded operations | Raw config or history, payloads, ACLs, direct offsets, and secret-bearing rows |
| `tide_reader` | Read sanitized status, lag, health, and non-secret metadata | Every mutation, raw config or history, and payload access |

PUBLIC and an unprivileged login must be denied every operation above except
public metadata that PostgreSQL exposes independently.

### Close the direct-publish bypass

Change the v0.52.0 fresh schema, adjacent migration, and role provisioning so:

1. `tide_publisher` and application login roles do not receive INSERT on
   `tide.tide_outbox_messages` or usage on its sequence.
2. `tide.outbox_publish()` is the only publisher write path.
3. The public function uses extension-owner privilege only for the guarded
   insert.
4. The function continues to authorize with `session_user`, explicit group
   membership, and `tide.outbox_publishers`.
5. The function has a fixed `pg_catalog, tide` search path.
6. PUBLIC cannot execute the function.
7. A denied or failed ACL lookup inserts no row and acquires no durable state.

Use the existing Rust implementation and PostgreSQL function attributes. Do
not add a second SQL publish implementation.

### Effective catalog inventory

Add one catalog query to the clean-room test support that records:

- schema owners and ACLs;
- table, view, sequence, and function owners;
- table and column ACLs;
- function EXECUTE ACLs;
- every `prosecdef` value;
- every security-definer `proconfig` search path;
- RLS enablement, force status, and policies;
- default privileges for the extension owner;
- canonical role attributes and memberships.

Normalize object order and owner fixture names. Compare fresh v0.52.0 with the
supported upgraded installation. Keep the inventory as test evidence, not as a
second hand-maintained privilege manifest.

### Black-box tests

Add `pg-tide-relay/tests/privilege_model_test.rs` to the installed-extension
suite. Create one login fixture for each group role, one unprivileged login,
the extension owner, and a superuser. Test public functions and direct SQL.

The matrix must include:

- publish to an allowed outbox;
- publish to another outbox;
- direct message insert and explicit ID insert;
- publisher grant and revoke;
- pipeline create, update, enable, disable, and delete;
- raw config and history read;
- relay source read;
- monotonic offset write and rewind;
- receipt and DLQ insert, read, delete, replay, and sweep;
- sanitized status and lag reads;
- dynamic inbox access;
- migration execution by an unauthorized role;
- extension-owner and superuser bypass behavior;
- role membership inherited through an intermediate group;
- PUBLIC function execution;
- caller-controlled object names on the session search path.

Inject these lookup failures in isolated transactions:

- revoke SELECT needed by an ACL lookup;
- rename or make `tide.outbox_publishers` unavailable;
- make the caller role lookup return no usable row;
- deny a security-sensitive catalog query;
- force an unexpected null verdict.

Each failure must return an authorization or SPI error with outbox or pipeline
context. No test may accept any error as sufficient without checking that
messages, config, offsets, receipts, and DLQ state remain unchanged.

### Migration files

Add `sql/pg_tide--0.51.0--0.52.0.sql`. It must:

- revoke the raw publisher table and sequence grants;
- apply exact function EXECUTE grants;
- lock every security-definer search path;
- preserve relay, operator, and reader access that remains in the matrix;
- update the extension comment;
- be transactional and safe to retry after rollback.

Update `sql/pg_tide--0.1.0.sql` and `deploy/postgres/pg_tide_roles.sql` to yield
the same final privileges. Do not create database roles inside the extension
migration.

### Acceptance criteria

- Fresh and upgraded effective privilege inventories match.
- Every allowed matrix cell succeeds through a public interface.
- Every denied matrix cell fails and leaves state unchanged.
- Publishers cannot insert directly or bypass per-outbox ACLs.
- Every security-definer function has the reviewed owner and locked search
  path.
- ACL, role, and catalog lookup failures fail closed.
- `v044_validation_test` remains historical evidence but no longer stands in
  for the v0.52 black-box matrix.

## 8. SEC-3: Harden supported network clients

### Objective

Make connector behavior match the TLS and authentication claims in
`connectors.toml`, then prove failures with real clients and generated test
certificates.

### Shared test support

Extend `pg-tide-relay/tests/common/` with only the shared process and
certificate setup needed by two or more connectors. Use the installed OpenSSL
CLI and existing service containers. Do not add a certificate-generation Rust
dependency.

Generate per-run values for:

- a trusted certificate authority;
- an untrusted certificate authority;
- a valid server certificate for the expected host;
- a wrong-host certificate;
- an expired certificate;
- client certificate and key where mTLS is supported;
- valid and invalid connector credentials.

Never commit a private test key or include one in test evidence.

### PostgreSQL

Repair `pg-tide-relay/src/pg_tls.rs` without adding another PostgreSQL client:

1. Represent `disable`, `require`, `verify-ca`, and `verify-full` distinctly.
2. Reject `allow`, `prefer`, and unknown values. Never map an unknown value to
   `disable`.
3. Treat an omitted mode as `verify-full`.
4. Include the existing `native-tls` backend in both production profiles.
5. Load the system trust roots or the configured `sslrootcert`.
6. For `verify-full`, verify both the certificate chain and hostname.
7. Treat `require` as an explicit encryption-only development override and log
   that identity verification is disabled.
8. Sanitize userinfo, passwords, query secrets, paths, and certificate errors.
9. Keep every PostgreSQL connection routed through `pg_tls::connect()`.

Test the coordinator connection, notification connection, worker pool,
PostgreSQL inbox destination, and `pg_outbox` destination. A source-only test is
not enough.

### NATS JetStream

Replace the bare `async_nats::connect(url)` call with the existing client's
typed connection options. Add only the config fields required by the support
claim:

- `url`;
- `subject` or `subject_template`;
- `allow_insecure`, default false;
- `token`, as a secret reference;
- `username` and `password`, with password as a secret reference;
- `credentials_file`, using the strict secret-file policy;
- `tls_ca_file`;
- `tls_client_cert` and `tls_client_key` for mTLS.

Reject conflicting authentication methods. Require `tls://` unless
`allow_insecure = true`. Verify the server name and authority. Do not add NATS
account-management features.

### Apache Kafka

Keep librdkafka and expose a bounded config set instead of arbitrary key-value
pass-through:

- `brokers`;
- `topic` or `topic_template`;
- `security_protocol`, default `ssl`;
- `allow_insecure`, default false;
- `ssl_ca_location`;
- `ssl_certificate_location` and `ssl_key_location` for mTLS;
- `sasl_mechanism` with the exact supported values;
- `sasl_username` and secret-reference-only `sasl_password`.

Allow `plaintext` and `sasl_plaintext` only with `allow_insecure = true`.
Preserve idempotent producer and acknowledgment settings. Reject unknown
security keys so a typo cannot silently disable a control.

### HTTPS webhook

Keep `secure_client_for_url()` as the single outbound HTTP path. Close test and
implementation gaps rather than adding a new URL policy:

- validate every A and AAAA answer;
- reject an empty result, mixed public and forbidden results, and more than the
  existing bound;
- pin validated answers for the request lifetime;
- preserve the original hostname for TLS and the Host header;
- reject userinfo, fragments, malformed URLs, and non-HTTP schemes;
- keep redirects disabled;
- keep ambient proxy variables disabled;
- recheck every supported alternate IPv4 and IPv6 representation after URL
  parsing;
- classify policy refusal separately from connection failure without logging
  the raw URL.

Do not implement redirect or proxy support. The roadmap requires testing
behavior where supported. For v0.52.0 the supported behavior is refusal.

### Required real-client cases

Run applicable cases against PostgreSQL, NATS, Kafka, and webhook:

- valid trusted certificate;
- expired certificate;
- hostname mismatch;
- untrusted authority;
- missing client certificate where mTLS is required;
- bad token, password, or SASL credential;
- plaintext endpoint with secure config;
- protocol downgrade attempt;
- connection error redaction;
- explicit development override and its warning.

The webhook matrix must also include:

- IPv4 and IPv6 loopback;
- IPv4-mapped IPv6 loopback;
- link-local ranges;
- RFC 1918 and unique-local ranges;
- carrier-grade NAT and special-use ranges;
- AWS, Azure, and Google metadata addresses and hostnames;
- integer, hexadecimal, octal, shortened, and mixed address encodings accepted
  by the URL parser;
- a DNS answer set containing both public and private addresses;
- a rebinding-sensitive answer change after validation;
- a redirect chain;
- a public-to-private redirect;
- malformed and credential-bearing URLs;
- uppercase and trailing-dot hostnames;
- `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` environment variables.

For every refusal, assert that the controlled destination received zero
requests and the relay did not advance the checkpoint.

### Schema and documentation

Update the generated pipeline schema through
`pg-tide-relay/src/config/schema_support.rs`. Update `connectors.toml` and the
four destination pages only after executable behavior exists. Keep every new
credential field secret-reference-only.

### Acceptance criteria

- The `core` and `core-kafka` release builds contain the TLS backend they need.
- Connector config and `connectors.toml` make the same authentication and TLS
  claims.
- Real-client success and failure tests pass for all four destinations.
- No supported client falls back to plaintext.
- Every insecure override is explicit and noisy.
- Webhook SSRF cases produce no outbound request or checkpoint advance.
- Redirects and ambient proxies remain unsupported and disabled.

## 9. SEC-4: Complete secret-handling assurance

### Objective

Prove the existing `SecretString`, reference parser, file loader, and config
redactor as one end-to-end containment boundary.

### Secret field inventory

List every supported secret-bearing input in the pipeline schema and test it:

- PostgreSQL URL password and certificate key;
- NATS token, password, credentials file, and client key;
- Kafka SASL password and client key;
- webhook signing secret;
- local encryption key where the supported local provider remains enabled;
- process environment values used by these references.

The schema, parser, and connector constructor must agree on this list. Reject
inline values in secret fields. Keep `${env:NAME}` and
`${file:/absolute/path}` as the only canonical reference forms. Preserve the
documented temporary `${ENV:NAME}` compatibility behavior only if its removal
release has not arrived.

### Canary harness

Add one integration test that generates a random value with a recognizable
prefix for each secret source. Run both successful and failing connector paths,
capture every supported output, and search for exact canary values and encoded
forms.

Capture:

- text and JSON logs on stdout and stderr;
- connector error chains;
- `validate-config` text and JSON output;
- `doctor`, `status`, `history`, `config`, and `self-test` output;
- metrics scrape;
- catalog config and config-history rows;
- runtime status and last-error fields;
- diagnostic `stdout` and `file` sinks;
- panic-hook output from a test-only failure path;
- required-test JSON and log artifacts;
- generated security and release evidence.

The project has no supported support-bundle command in v0.51.0. Record that
channel as not present. Do not add a bundle command for this release. If one is

Search for:

- the literal secret;
- URL-encoded and JSON-escaped forms;
- base64 where the connector encodes credentials;
- userinfo-bearing URLs;
- certificate private-key markers;
- resolved values embedded in third-party error text.

Assert the positive control first by placing each canary in a private capture
that the scanner must find. A scanner that never sees its input cannot satisfy
the gate.

### Runtime handling

Keep `SecretString` as the only secret wrapper. Extend it only where a
connector API requires owned bytes or strings. Do not implement a secret cache
or provider trait.

Resolve references after catalog parsing and immediately before connector
construction. Keep references in the catalog, history, status, and config
export. Pass exposed values to third-party clients at the last call boundary.
Drop temporary owned values after construction where the client copies them.

Sanitize third-party errors at their connector boundary. Preserve connector,
pipeline, failure phase, and a stable refusal code. Do not preserve raw URLs,
headers, payloads, credentials, or library debug dumps.

### Secret-file cases

Extend unit tests for:

- absolute regular file owned by the effective user with mode `0600`;
- relative path;
- symlink;
- directory, device, and named pipe;
- wrong owner;
- group or world permission bits;
- empty file;
- file at the size limit and one byte over;
- invalid UTF-8;
- file replaced between open and metadata read;
- missing and unreadable file;
- trailing newline trimming;
- unsupported platform behavior.

Use the opened file descriptor for metadata and reads so path replacement
cannot redirect the read after validation.

### Acceptance criteria

- Every supported secret field requires a canonical reference.
- The canary scanner proves its positive control, then finds no canary in any
  supported output.
- Success, validation failure, authentication failure, TLS failure, and panic
  diagnostics all pass the scan.
- Unsafe secret files fail before connector construction.

- No new secret abstraction or remote provider is added.

## 12. SEC-7: Verify signing, SBOM, and provenance

### Objective

Move final trust from producer assertions to a separate, read-only verification
job.

### Producer requirements

For each artifact:

1. Build from the checked-out annotated tag commit with locked dependencies.
2. Record the artifact SHA-256 digest.
3. Generate a CycloneDX SBOM from the final artifact, not the source tree.
4. Generate build provenance with the artifact as subject.
5. Sign the artifact or immutable image digest with keyless Cosign.
6. Upload the artifact, checksum, SBOM, provenance, signature bundle, and
   content inventory as one named CI artifact.

Use a pinned official GitHub artifact-attestation action for build provenance
where it covers the artifact type. Retain Cosign for portable archive and image
verification. Do not hand-write a statement and call it independent provenance
without checking its builder identity.

### Independent verification job

Add a job that:

- has `contents: read` and `packages: read` only;
- has no signing identity and no artifact-production step;
- downloads producer outputs by workflow-run ID;
- runs `git verify-tag` on an annotated signed source tag;
- confirms that the tag commit equals `GITHUB_SHA`;
- verifies every checksum;
- verifies Cosign bundles with the repository workflow identity and expected
  OIDC issuer;
- resolves image tags to immutable digests before verification;
- checks each SBOM subject and component set against the final artifact;
- checks each provenance subject digest, commit, ref, builder, workflow, and
  profile;
- checks the Helm chart version, app version, image repository, tag, and
  profile;
- runs the artifact content allowlist checker;
- checks that v0.52 release evidence names the same digests;
- emits one machine-readable pass or fail result.

The GitHub release job must depend on this verifier. It may publish only the
objects that the verifier accepted. Do not rebuild or modify an artifact after

`supply-chain/advisory-exceptions.toml` and cannot apply to a production image.

### Acceptance criteria

- The independent job verifies all objects by digest and expected identity.

## 17. Migration and failure handling

### 17.1 Adjacent lifecycle policy

Extend `schemas/lifecycle-compatibility-v1.json` through v0.52.0 and keep the
v0.47.0 upgrade floor.

Use this adjacent runtime policy:

| Extension | Relay | Status | Reason |
|---|---|---|---|
| v0.51.0 | v0.51.0 | Supported starting state | v0.51.0 baseline |
| v0.51.0 | v0.52.0 | Supported during relay-first upgrade | New relay understands old schema |
| v0.52.0 | v0.52.0 | Supported target | Final state |
| v0.52.0 | v0.51.0 | Rejected | Historical relay rejects a future extension |
| earlier than v0.51.0 | v0.52.0 | Rejected at runtime | Outside adjacent relay window |

Operators starting at the v0.47.0 extension floor stop older relays and use the
packaged migration chain. For the adjacent v0.51.0 upgrade, replace all relays
with v0.52.0 before updating the extension. A v0.51.0 relay rollback after the
extension reaches v0.52.0 is unsupported. Restore the v0.51.0 database backup
before rolling the relay back.

### 17.2 Migration failure rules

The v0.51.0 to v0.52.0 migration runs in one PostgreSQL transaction. A failure
must leave extension version, grants, owners, search paths, role memberships,
config, messages, offsets, receipts, and DLQ state at v0.51.0.

Test interruption after each privilege-change class with the existing
migration failpoint method. Retry from the committed v0.51.0 state. Do not add a
partial-migration repair function.

Security config validation belongs in the v0.52.0 relay startup and doctor
paths, not in a destructive SQL migration. The extension upgrade must preserve
pipeline rows that need an explicit development override or secure endpoint
change. The new relay refuses the affected pipeline before polling and explains
the required non-secret action.

### 17.3 Failure classifications

Use stable, sanitized classifications for:

- authorization denied;
- authorization lookup failed;
- insecure transport refused;
- TLS verification failed;
- authentication failed;
- SSRF policy refused;
- secret reference invalid, missing, or unsafe;
- dependency or artifact policy failed;
- signature, SBOM, or provenance verification failed.

Do not put raw third-party error strings into persistent status or bounded
metric labels. Store a stable code and sanitized summary. Detailed local logs
may include non-secret library context after the canary test proves it safe.

### 17.4 Delivery state on security failure

When connector construction or publish fails for a security reason:

1. Do not acknowledge the batch.
2. Do not advance the checkpoint.
3. Do not delete or mark the source event consumed.
4. Record the bounded failure code and metric.
5. Stop or retry only according to the existing permanent and transient error
   classification.
6. Never retry a permanent config, authorization, authentication, TLS-policy,
   or SSRF refusal in a tight loop.

The v0.50.0 delivery model remains authoritative.
