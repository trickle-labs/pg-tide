# pg_tide v0.50.0 implementation plan

> **Status:** Proposed
> **Release theme:** Delivery Correctness and Failure Semantics
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.49.0 and current `main`
> **Implementation branch:** `implementation-v0.50.0`
> **Scope rule:** Prove the reduced v1 delivery contract. Do not add connectors,
> a second delivery engine, unrelated public surface, or unrelated performance
> work. One additive command under the existing `pg-tide replay` group is
> permitted only to make the retained replay engine reachable.

## 1. Release outcome

v0.50.0 is complete when executable evidence proves this invariant for every
supported destination:

> A committed outbox event may be retried or duplicated at a documented
> boundary, but the relay never silently loses it.

The proof covers this product path:

```text
application transaction
  -> tide.outbox_publish()
  -> canonical PostgreSQL outbox
  -> pg-tide process
  -> PostgreSQL inbox, NATS JetStream, Kafka, or webhook
  -> durable source checkpoint
  -> retention eligibility
```

The release turns the accepted delivery state machine into a small executable
model, runs the four public workflows through the real `pg-tide` process, and
tests each important crash window. It proves that checkpoints are monotonic,
never pass the acknowledged frontier, and remain behind any event required by
an active consumer. It also proves connector duplicate behavior, DLQ failure
safety, replay interruption, graceful shutdown, forced termination, and HA
ownership transfer.

v0.50.0 does not promise exactly-once transport. PostgreSQL inbox delivery can
produce one destination effect through its `event_id` constraint. NATS,
Kafka, and webhook delivery remain at least once with the connector-specific
deduplication limits recorded in `connectors.toml`.

No new production subsystem is required. Reuse the coordinator, source and
sink contracts, `proptest`, the current failpoint feature, testcontainers, the
required-test manifest, and the existing fuzz crate.

- public E2E and crash-matrix support for preview consumer-group relay modes;
  the retained consumer-offset writer still receives monotonicity regression
  coverage because the roadmap requires every offset-writing path;

Fix defects exposed by the required public workflows or crash matrix. Record
other findings for their planned release.

## 3. Canonical correctness contract

### 3.1 Use one state vocabulary

Amend ADR-012 so the detailed v0.50.0 program becomes the canonical delivery
vocabulary:

```text
Polled
  -> Encoded
  -> PublishStarted
  -> SinkAccepted
  -> SinkAcknowledged
  -> CheckpointCommitted
  -> CleanupEligible
```

Alternative terminal paths are:

```text
Encoded -> DryRunObserved -> CheckpointCommitted
Encoded -> IntentionallyFiltered -> CheckpointCommitted
PublishFailed -> DlqPersisted -> CheckpointCommitted
```

Record the one-time mapping from the previous ADR terms so old evidence remains
readable:

| v0.50.0 term | Previous ADR term | Runtime boundary |
|---|---|---|
| `Polled` | `Polled` | The source returned a batch and its original checkpoint |
| `Encoded` | `Prepared` | `poll_and_decode()` produced a sink-ready batch with stable event identities |
| `PublishStarted` | start of `PublishInFlight` | `Sink::publish()` started downstream I/O |
| `SinkAccepted` | ambiguous part of `PublishInFlight` | The destination may have accepted some or all of the batch; `accepted_maybe` is true but no durable acknowledgment is known |
| `SinkAcknowledged` | `SinkAcknowledged` | `Sink::publish()` returned only after its descriptor's acknowledgment boundary |
| `CheckpointCommitted` | `CheckpointCommitted` | `Source::acknowledge()` persisted the source checkpoint |
| `CleanupEligible` | `EligibleForCleanup` | Every active participant frontier and the retention cutoff permit deletion |

The executable model, metrics, logs, tests, ADR, and connector documentation
must use the v0.50.0 names after the ADR is amended. `SinkAccepted` remains a
distinct state because it carries the ambiguous acceptance and duplicate-risk
fact even when a connector cannot observe the exact acceptance instant.

### 3.2 Invariants

All implementation and test work must preserve these invariants:

1. A source poll retains the original batch checkpoint even if filtering or
   routing changes the delivered messages.
2. The checkpoint does not advance before the full batch reaches a durable
   terminal disposition.
3. Sink success means that the connector reached the acknowledgment boundary
   declared in `connectors.toml`.
4. A crash after downstream acceptance but before checkpoint commit may cause
   a duplicate. It cannot cause a skipped source event.
5. A checkpoint write is monotonic for its complete identity:
   `(relay_group_id, pipeline_id, outbox_name)`.
6. A checkpoint never exceeds the highest acknowledged source ID in the
   sequence being modeled.
7. An all-filtered or dry-run batch commits the original checkpoint only after
   its intentional disposition is visible.
8. DLQ persistence is atomic for the full batch. A failed or ambiguous DLQ
   write leaves the source batch eligible for retry.
9. Replay is bounded and checkpoint-neutral. Administrative rewind remains a
   separate explicit operation.
10. Cleanup uses the minimum safe frontier across every configured active
    participant and the retention cutoff. One pipeline cannot make a shared
    row eligible by itself.
11. Restart and HA takeover load durable PostgreSQL state. Worker memory and
    delivery receipts are not authoritative.
12. Event identity remains stable across retry, restart, DLQ persistence, and
    replay.

### 3.3 Supported connector boundaries

`connectors.toml` remains the source for acknowledgment, deduplication, retry,
and permanent-error capabilities. `pg-tide-relay/src/descriptors.rs` remains
generated output.

| Destination | Acknowledgment boundary | Duplicate boundary to prove |
|---|---|---|
| PostgreSQL inbox | The destination `INSERT ... ON CONFLICT` transaction completed | Repeated `event_id` produces one durable row and one application-visible pending event |
| NATS JetStream | Every JetStream publish acknowledgment future completed | `Nats-Msg-Id` deduplicates inside the stream window; a retry outside the window may be visible twice |
| Apache Kafka | Every producer delivery future completed | Producer idempotence is session-bounded; restart after sink acknowledgment may produce a consumer-visible duplicate. Flush remains a separate shutdown behavior |
| Webhook | The receiver returned a configured success status | The relay sends a stable `Idempotency-Key`; one effect requires receiver-side deduplication |

Do not copy this capability data into a new registry. The executable model may
refer to generated descriptors when it needs a connector boundary.

## 6. COR-1: Create the executable delivery model

### Objective

Add one small, pure model that makes ADR-012 transitions executable without
replacing `worker_inner()`.

### Files and symbols

- `pg-tide-relay/src/delivery_model.rs`, new test-only internal module
- `pg-tide-relay/src/coordinator.rs`
- `pg-tide-relay/src/metrics.rs`
- `docs/adr/adr-012-relay-delivery-acknowledgment-and-offset-state-machine.md`
- `docs/src/reference/architecture-decisions.md`

### Design

Keep the model free of network, database, clock, and async code. Define only
the smallest types needed to execute transitions:

```text
DeliveryState
DeliveryEvent
DeliveryFacts
TransitionError
transition(current_facts, event) -> Result<DeliveryFacts, TransitionError>
```

The model represents:

- the current ADR state;
- the durable sink acknowledgment frontier;
- the durable source checkpoint;
- whether the original event remains source-visible;
- whether a duplicate is possible;
- whether cleanup is allowed;
- whether the failure is transient or permanent.

Compile the model only for unit tests and the `test-failpoints` test profile.
Do not make it part of the normal library API or production binary. Unit and
property tests live beside it. Reuse the current `PollOutcome`,
`PublishOutcome`, `WorkerDirective`, and `DlqOutcome` semantics rather than
introducing model versions of runtime outcomes.

The coordinator remains the runtime engine. Production changes are limited to
the emissions and structured fields needed to compare observed behavior with
the test model. Keep the existing metric family and add only labels that map to
an observable coordinator boundary: `polled`, `encoded`, `publish_started`,
`intentionally_filtered`, and `dry_run_observed`. Reuse the existing
`sink_acknowledged`, `dlq_persisted`, and `checkpoint_committed` labels, the
existing `checkpoint_error` outcome, and the separate DLQ-write error counter.
Represent `SinkAccepted` as the model's `accepted_maybe` fact and a structured
outcome after an ambiguous publish result; do not emit a metric that pretends
the exact acceptance instant was observed.

`CleanupEligible` is outside the relay worker. Prove it through the existing
bounded `tide.outbox_retention_status` and `pg-tide sweep` JSON rather than
adding a relay delivery-stage metric for an extension-owned decision.

### Implementation steps

1. Amend ADR-012 with the v0.50.0 vocabulary and historical mapping in section
   3.1 of this plan.
2. Define the legal forward and alternative transitions.
3. Reject impossible transitions in the pure model with a normal model error.
   Do not panic.
4. Define the durable facts, retry result, duplicate risk, checkpoint rule,
   cleanup rule, metric label, structured event fields, and required evidence
   for each transition.
5. Use the structured event code `PGTIDE_DELIVERY_TRANSITION`. Emit it from the
   coordinator, where pipeline,
   relay group, direction, tenant, source, sink, batch, stage, outcome, retry
   class, checkpoint class, and duplicate risk are already available. Do not
   pass a new observability context through every helper. Emit once per batch
   transition, not once per message; use debug for nonterminal progress, info
   for durable success, and warn or error for failure.
6. Keep payloads, headers, URLs, credentials, and secrets out of transition
   events.
7. Add missing stage metrics and coordinator-level structured events at the
   real runtime boundaries. Keep existing durable-stage labels compatible.
8. Map observed `PollOutcome`, `PublishOutcome`, `WorkerDirective`,
   `DlqOutcome`, and `commit_checkpoint()` results to expected model events in
   tests. Do not route production control flow through the model.
9. Reuse `RelayError::retry_class()`, `RelayError::public_code()`, and generated
   connector descriptors.
10. Add exhaustive unit tests for legal transitions, illegal transitions,
    alternative terminal paths, and reset to the next batch.
11. Link the executable model and its tests from ADR-012.

### Acceptance criteria

- [ ] ADR-012 and the executable model use one state vocabulary.
- [ ] Every ADR transition has a model event and expected durable facts.
- [ ] Every observable relay stage has a bounded metric label, structured
  event, and test; ambiguous acceptance and cleanup use the truthful evidence
  defined above.
- [ ] The model contains no I/O, is absent from production profiles, and does
  not become a second worker engine.
- [ ] Runtime error and connector capability classification is reused.
- [ ] Illegal model transitions return an error without `panic!()`.
- [ ] The model is linked from ADR-012 and covered by unit tests.

## 7. COR-2: Complete public-API end-to-end coverage

### Objective

Prove each supported destination through the installed extension, documented
SQL APIs, compiled relay process, and a real service or faithful receiver.

### Required test files

```text
pg-tide-relay/tests/public_api_outbox_to_nats_e2e.rs
pg-tide-relay/tests/public_api_outbox_to_kafka_e2e.rs
pg-tide-relay/tests/public_api_outbox_to_pg_inbox_e2e.rs
pg-tide-relay/tests/public_api_outbox_to_webhook_e2e.rs
```

### Shared process harness

Add only the shared code used by at least two tests under
`pg-tide-relay/tests/common/`:

- start the path in `PG_TIDE_E2E_RELAY_BIN`, falling back to
  `CARGO_BIN_EXE_pg-tide` for local Cargo runs, with `run` and a unique relay
  group;
- pass the harness database through `PG_TIDE_E2E_DATABASE_URL`, then pass the
  URL to the relay through `PG_TIDE_POSTGRES_URL`;
- capture JSON logs from stdout and stderr;
- wait for readiness through the health endpoint or a bounded public status
  condition;
- request graceful shutdown;
- force process termination;
- restart with the same relay group;
- wait for a checkpoint through `pg-tide --output json status`; use a direct
  read of `tide.relay_consumer_offsets` only as a cross-check of the durable
  checkpoint contract;
- fail with captured process logs and PostgreSQL logs on timeout.
- read `PG_TIDE_E2E_EXPECTED_VERSION` and assert that `pg-tide --version` and
  `pg_extension.extversion` both equal it before publishing.

Use `tokio::process::Command` and the standard library. Do not add a process
test dependency.

### Common workflow requirements

Each test must:

1. Use a fresh PostgreSQL 18 database with the staged package produced by
   `cargo pgrx package --package pg-tide-ext --pg-config
   /usr/lib/postgresql/18/bin/pg_config --out-dir
   target/v0.50-e2e/extension-root` installed from that directory. Do not
   replace this step with `cargo pgrx install`.
2. Run `CREATE EXTENSION pg_tide`.
3. Create the outbox through `tide.outbox_create_if_not_exists()`.
4. Configure the pipeline through `tide.relay_set_outbox_v2()`.
5. Start the compiled `pg-tide run` process.
6. Publish an application row and `tide.outbox_publish()` in one transaction.
7. Observe the real downstream result.
8. Verify checkpoint advancement through `pg-tide --output json status`.
9. Stop and restart the relay.
10. Publish again and verify that no event is lost.
11. Induce one acknowledged-before-checkpoint retry and verify the documented
    duplicate boundary.
12. Use bounded deadlines and print useful diagnostics on failure.

The test may not insert directly into outbox messages or relay configuration,
call a sink directly, or instantiate `Coordinator`.

### Destination scenarios

#### PostgreSQL inbox

Use a separate destination database in the PostgreSQL 18 test environment.
Install the extension there and call `tide.inbox_create()` through the public
API. Configure `sink_type = "inbox"` with the logical inbox name and a
destination `postgres_url`.

Correct the current logical-name mismatch. A user configures the name passed to
`tide.inbox_create()`, but `InboxSink` and `PgInboxSink` currently treat that
value as a physical table name and hard-code schema `tide`. Resolve the logical
name to `inbox_schema` and the generated `<name>_inbox` relation through
`tide.tide_inbox_config` in one shared inbox-sink path. Validate both
identifiers before quoting them. Do not teach the public API to accept an
internal table name or assume that the inbox schema is `tide`.

Use a fresh destination inbox. Observe delivery through `tide.inbox_status()`
and the public inbox processing functions. Query the stable `event_id` only as
a cross-check. To prove one application effect, open an explicit transaction,
write the test application row, call `tide.inbox_mark_processed()`, and commit.
After an acknowledged-before-checkpoint crash and retry, assert one durable
inbox row and one application row.

#### NATS JetStream

Retain the real NATS 2.11 JetStream container. Refactor the test to spawn the
relay process. Verify publish acknowledgment, stable `Nats-Msg-Id`, checkpoint
advance, process restart, deduplication inside the stream window, and possible
duplication after the configured window expires.

#### Apache Kafka

Retain the real Kafka 3.8 KRaft broker and consumer. Refactor the test to spawn
the `core-kafka` relay process. Verify broker acknowledgment, consumer-visible
payload and stable identity, checkpoint advance, process restart, and the
session-bounded duplicate behavior after an acknowledged-before-checkpoint
crash.

#### Webhook

Run a faithful receiver that records request bodies, status responses,
`Idempotency-Key`, and receiver-side effects. Use the existing loopback HTTP
exception only for the delivery-correctness job and set `allow_http` and the
loopback SSRF exception explicitly. Keep verified HTTPS behavior in the
existing TLS tests and the v0.52.0 security matrix.

The receiver must support scripted `2xx`, `429`, `5xx`, connection close, and
delayed response behavior. It must also provide a deduplicating mode keyed by
`Idempotency-Key`. Verify that the relay retries the same key and that the
receiver records one effect when deduplication is enabled.

### CI and registry updates

- Add dedicated CI jobs for PostgreSQL inbox and webhook.
- Keep Kafka on `core-kafka`.
- Update the NATS and Kafka jobs to build and launch the binary.
- Add all four tests to `tests/required-tests.toml` with `max_retries = 0`.
- Add E2E evidence rows for PostgreSQL inbox and webhook to `connectors.toml`.
- Regenerate connector descriptors and support documentation.

## 8. COR-3: Implement the crash-window matrix

### Objective

Pause or terminate the real relay at each delivery boundary, restart it, and
prove the durable facts predicted by the executable model.

### Failpoint rules

Keep one opt-in `test-failpoints` feature and the existing file-handshake
control. Extend it only where an invariant cannot be reached through an
existing point.

Use truthful coordinator and source points for:

```text
after_poll_before_encode
after_encode_before_publish
after_sink_ack
before_checkpoint_commit
after_offset_db_commit_before_cleanup
after_checkpoint_commit
during_dlq_write
after_dlq_commit
during_replay
during_shutdown
ownership_connection_lost
```

Move the current `after_poll` hit inside `poll_and_decode()`, immediately after
a nonempty `Source::poll()` and before replay filtering or preparation. Rename
`after_prepare` to the second boundary. Rename
`after_offset_db_commit` to state that it runs after the autocommit offset
UPSERT returns and before out-of-line source cleanup. These are internal test
names, so keep no compatibility alias.

`after_network_publish` currently runs after `Sink::publish()` returns and is
therefore after acknowledgment for supported sinks. Remove it in favor of
`after_sink_ack`. The send-before-ack ambiguity is connector-specific, not one
of the generic points above. Use a connector-internal point only when the
client exposes a truthful boundary. Otherwise use controlled broker or
receiver behavior that accepts the request and drops or delays the
acknowledgment. Mark a connector/boundary pair not applicable when neither the
protocol client nor a faithful receiver can prove that instant. Do not add a
misleading generic coordinator point.

The normal `core` and `core-kafka` builds must compile out failpoint names,
environment parsing, waits, and error injection. A no-op runtime function is
not enough for the release gate. Guard the module and call sites with
`cfg(feature = "test-failpoints")`, then add an artifact check that production
binaries were built only with declared production features. Inspect enabled
features and reachable symbols, then run a negative behavior check with
`PG_TIDE_FAILPOINT` set. A string scan for the environment key and fixed point
names is a secondary guard, not the proof by itself.

### Crash invariant matrix

| Boundary | Destination state before restart | Checkpoint before restart | Allowed duplicate result | Required recovery |
|---|---|---|---|---|
| After poll | No downstream effect | Old checkpoint | None | Original event delivers once |
| After prepare | No downstream effect | Old checkpoint | None | Original event delivers once with the same ID |
| Send before acknowledgment result | Zero, some, or all downstream effects | Old checkpoint | Connector-dependent | Every source event reaches a terminal result after retry |
| After sink acknowledgment | Downstream effect exists | Old checkpoint | Yes, subject to destination deduplication | Retry or dedup produces no loss |
| Before checkpoint commit | Downstream effect exists | Old checkpoint | Yes | Retry or dedup produces no loss |
| After offset database commit, before success returns | Downstream effect exists | New durable checkpoint | No automatic replay after restart | Worker reloads the durable checkpoint |
| After checkpoint commit | Downstream effect exists | New durable checkpoint | None from automatic recovery | Next poll starts after the batch |
| During DLQ write | No complete terminal DLQ disposition | Old checkpoint | DLQ insert retry may be deduplicated | Source event remains eligible |
| After DLQ commit | Complete durable DLQ disposition | Old checkpoint until source commit | Duplicate DLQ row suppressed | Restart commits or safely retries the disposition |
| During replay | Replay effect may be partial | Live checkpoint unchanged | Connector-dependent | Bounded replay can resume or be rerun without moving live state |
| During graceful shutdown | Depends on drain boundary | Never beyond acknowledgment | Connector-dependent | Drain completes or source event remains eligible |
| Forced process termination | Depends on current model state | Durable value only | Connector-dependent | Restart follows the matching row above |
| Ownership loss and takeover | Depends on active owner's state | Durable value only | Connector-dependent | One standby resumes with no loss |

### Test organization

Add a focused crash-matrix test suite that reuses the COR-2 process harness.
Keep connector setup and downstream assertions in the four connector fixtures.
Share only:

- failpoint ready and continue files;
- process termination and restart;
- checkpoint reads;
- metric and structured-log assertions;
- model-derived expected durable facts.

Do not implement a generic connector framework solely for tests.

Run the full matrix in scheduled and release CI. Run a bounded core subset on
pull requests:

- every model boundary against NATS;
- acknowledged-before-checkpoint against all four destinations;
- DLQ write failure;
- forced termination;
- ownership takeover.

The full scheduled matrix covers every applicable boundary for all four
destinations. Mark a connector/boundary pair not applicable only when its
descriptor or protocol makes the state impossible. Record the reason in the
matrix, not as an ignored test.

### HA and shutdown corrections

Replace the current coordinator-task HA proof with two real relay processes:

1. Start both against one pipeline and relay group.
2. Prove that one process owns the advisory lock.
3. Publish a batch.
4. Kill the active owner at a controlled state.
5. Prove that the standby acquires ownership.
6. Verify final downstream identities, checkpoint, ownership metrics, and
   transition logs.

Likewise, replace simulated duration and direct-offset shutdown tests with a
real SIGTERM drain and a forced termination scenario. Keep small unit tests
only for actual pure timeout helpers.

### Acceptance criteria

- [ ] Every defined crash boundary has a modeled invariant and automated test.
- [ ] Every supported destination runs every applicable boundary in scheduled
  and release CI.

## 11. COR-6: Harden DLQ and replay semantics

### Objective

Prove that a delivery failure remains recoverable when DLQ persistence or
replay also fails.

### DLQ scenarios

Test through the real coordinator:

- atomic persistence of a failed batch;
- INSERT permission denial;
- relay/catalog PostgreSQL unavailable during DLQ persistence;
- connection loss before the DLQ commit result;
- connection loss after commit but before checkpoint commit;
- repeated DLQ insertion with the same deduplication identity;
- bounded full or unavailable behavior represented by a deterministic
  database error rather than an unbounded disk-fill test;
- status, metric, health, and structured-log visibility;
- connector recovery after a DLQ-worthy period.

For every failure, assert the source checkpoint and source row eligibility.
`DlqOutcome::TransientError` may retry. `DlqOutcome::PermanentError` may stop
the pipeline. Neither may discard the source event.

Correct the stale header in
`pg-tide-relay/tests/dlq_fault_injection_test.rs`: `insert_batch()` is now
all-or-nothing. Delete any assertion that still claims partial success.

### Make the retained replay path reachable

Do not mistake the existing replay-shaped code for a supported workflow. The
coordinator reads `replay.from_offset` and `replay.to_offset`, but the strict
`PipelineDocument` rejects those fields, `tide.relay_set_outbox_v2()` does not
persist them, and the current CLI only previews a range or changes DLQ rows.

Make the smallest existing path coherent:

1. Add `pg-tide replay execute --pipeline <name> --from-id <n> --to-id <n>
   [--batch-size <n>]` under the existing replay command group. This is an
   additive frozen-surface change and must pass the `contract-change` review.
2. Load and validate the named public pipeline, then call one extracted
   one-shot entry around the current coordinator worker. Pass a typed bounded
   range as an invocation argument; do not persist temporary `replay` keys in
   the pipeline JSON.
3. Reuse `Source::configure_replay()`, `poll_and_decode()`, the normal sink,
   retry, DLQ, acknowledgment, and close paths. Do not create another replay
   or delivery engine.
4. Exit after the inclusive upper bound or end of the range. Because this is
   a one-shot CLI process, normal coordinator reconciliation cannot restart
   it.
5. Never call the source checkpoint writer or source cleanup in replay mode.
   In particular, do not `lo_unlink()` out-of-line payload objects while
   replaying. Report the starting and ending live checkpoints and fail the
   command if they differ.
6. Reject `from-id < 0`, `to-id < from-id`, `batch-size` outside `1..=10_000`,
   a missing/disabled pipeline, and an invalid destination before the first
   publish. Require an explicit inclusive upper bound; replay can only read
   rows still retained in the outbox.
7. Remove or route the currently unreachable pipeline-JSON replay parsing
   through the typed invocation so there is one implementation boundary.

If review rejects this additive command, v0.50.0 is blocked until the roadmap
and ADR-012 name a retained public mechanism. Do not satisfy COR-6 with an
internal-only test path.

### Replay scenarios

Exercise the one-shot command through the real relay binary:

- bounded outbox range replay through the normal worker;
- interruption before and after a downstream acknowledgment;
- process restart by explicitly rerunning the same command;
- checkpoint neutrality before, during, and after replay;
- replay of an already delivered event;
- invalid destination configuration rejected before replay starts;
- destination failure followed by recovery;
- bounded batches and inclusive upper range;
- status, metric, CLI exit, and structured-log visibility.

Separately test `dlq-requeue` interrupted between resolve and requeue. Fix the
current two-statement race at its root by running the update and reinsert in one
database transaction. Requeue remains a DLQ state operation; it does not count
as delivered-message replay evidence.

- `docs/src/features/dead-letter-queue.md`;
- `docs/src/tutorials/dead-letter-queue.md`;
- `docs/src/operations/runbook-dlq-replay.md`;
- `docs/src/operations/runbook-crash-recovery.md`;

### 17.2 Adjacent compatibility boundary

The packaged-extension E2Es prove a fresh v0.50.0 install. The no-op adjacent
migration and existing chain checks prove that PostgreSQL can discover a valid
0.49.0 to 0.50.0 path. Do not add the fresh-versus-upgrade schema parity,

install the extension files, run `ALTER EXTENSION pg_tide UPDATE TO '0.50.0'`,
replace the relay binary, and start it. State that acknowledged-before-
checkpoint crashes may duplicate but cannot silently lose a source event.
Present relay rollback as an operator procedure only if the release introduces
no new config or schema dependency; do not claim executable rollback proof.

### 17.3 Failure rules during implementation

- If a public E2E exposes a contract mismatch, fix the shared runtime boundary,
  not the test fixture.
- If an ambiguous publish window cannot be injected at a truthful client
  boundary, use a controlled broker or receiver ambiguity. Mark it not
  applicable when the protocol exposes neither; do not invent a generic point.
- If a crash test passes only after a retry, keep the original run as failed.
- If the model and observed durable state disagree, treat runtime state as a
  defect or amend ADR-012 through review. Do not weaken the assertion locally.
- If a DLQ write cannot be proved complete, retain the source checkpoint.
- If a connector cannot meet its declared acknowledgment boundary, mark the

   crash matrix, checkpoint properties, DLQ/replay tests, and production-
   instrumentation check. On success, it writes and uploads the v0.50.0
   correctness record and index described in section 14.
2. Make every job that pushes a container, archive, release asset, or GitHub
   Release depend on `delivery-correctness`, download its index, and verify the
   ready candidate before its first push. A failed or missing correctness job
   must leave no v0.50.0 image tag or release asset published.
3. Replace the v0.47.0-only early return with tag-version-derived evidence
   selection. For v0.50.0, download the generated index, require `status` to be
   `ready`, require its candidate to equal the tag commit, and rerun the open
   P0/P1 blocker query. Keep historical v0.47.0 files immutable.
4. Derive both the final filename and `source_index` from the tag version.
   For v0.50.0 they are `release-evidence/v0.50.0-final.json` and

5. Require `release-evidence/v0.50.0-correctness.json` to exist, validate, and

### 18.4 Existing artifact support boundary

The current workflow's `core` relay archives omit Kafka and it does not publish
an extension archive. Do not turn COR-1 through COR-8 into a packaging redesign.
Before implementation, the release owner must confirm that v0.49.0 support
docs distinguish source support, `core`, `core-kafka`, and container support.
If they do not, v0.49.0 is not a valid starting point: correct or narrow that
claim before v0.50.0 work starts. Track extension-archive publication,
platform-specific Kafka artifacts, license-label consistency, signing, SBOM,
provenance, and promotion in the assigned release-hardening milestones.

## 19. v0.50.0 exit criteria

### Delivery model

- [ ] ADR-012 and the executable model use one state vocabulary.
- [ ] Every legal transition defines durable state, retry behavior, duplicate
  risk, checkpoint rule, cleanup rule, metric, structured event, and test.
- [ ] The executable model is linked from ADR-012.
- [ ] The coordinator remains the only runtime delivery engine.

### Public workflows

- [ ] PostgreSQL inbox, NATS JetStream, Kafka, and webhook each have a
  public-API black-box E2E.
- [ ] Every E2E starts the compiled relay process and packaged extension.
- [ ] No E2E mutates the relay catalog or outbox message table directly.
- [ ] Every destination proves downstream outcome, checkpoint, restart, and
  duplicate behavior.

### Crash and recovery

- [ ] Every defined crash window has an invariant and automated test.
- [ ] Every supported connector runs every applicable window.
- [ ] No checkpoint advances before the connector acknowledgment boundary.
- [ ] Crash after acknowledgment and before checkpoint can duplicate but does
  not lose an event.
- [ ] Crash after durable checkpoint does not replay automatically.
- [ ] Graceful shutdown and forced termination preserve the same invariants.
- [ ] Two relay processes prove HA takeover with no silent loss.
- [ ] Production profiles contain no failpoint or fuzz controls.

### Checkpoint and cleanup properties

- [ ] Native relay and retained consumer-group checkpoints are monotonic.
- [ ] Generated sequences never exceed the acknowledged frontier.
- [ ] Stable event identity survives retry, restart, ownership transfer, DLQ,
  and replay.
- [ ] Cleanup cannot pass any active participant frontier.
- [ ] Retry and error classification is deterministic and bounded.

### Duplicate, DLQ, and replay semantics

- [ ] All four destination duplicate boundaries are observed and documented.
- [ ] A failed or ambiguous DLQ write cannot discard the source event.
- [ ] DLQ batch persistence is atomic and idempotent.
- [ ] Replay is bounded, interruption-safe, and checkpoint-neutral.
- [ ] Active documentation makes no unqualified exactly-once claim.

### Tests and fuzzing

- [ ] Test names match the documented evidence levels.
- [ ] Misleading simulations are replaced, renamed, or deleted.
- [ ] Required parser and serializer fuzz targets run in CI.
- [ ] Every discovered fuzz defect has a minimized regression.
- [ ] Required correctness jobs pass repeatedly with zero rerun-dependent
  success.

### Release integration

- [ ] Required-test inventory version is v0.50.0 and contains every new gate.
- [ ] Packaged-extension E2Es prove a fresh v0.50.0 install.
- [ ] The 0.49.0 to 0.50.0 adjacent migration is present in every existing
  migration-chain check.
- [ ] Release evidence and final record are version-derived, not hard-coded to
  v0.47.0.
- [ ] Tag-source delivery correctness completes before any publication job.
- [ ] The staged extension and relay used by correctness tests report v0.50.0
  and have recorded digests.
- [ ] `just fmt`, lint, unit, integration, pgrx, clean-room, contract, surface,
  flake, dependency, artifact, and observability checks pass.
- [ ] No silent-loss defect remains open.
