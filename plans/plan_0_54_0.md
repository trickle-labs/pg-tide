# pg_tide v0.54.0 implementation plan

> **Status:** Proposed
> **Release theme:** Operator Experience, Documentation, and Repository Quality
> **Source:** [pg_tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.53.0 and current `main`
> **Scope rule:** Consolidate the existing operator, documentation, test,
> lifecycle, and release-evidence systems. Do not add an operator UI, another
> documentation framework, another test registry, or a breaking CLI JSON
> revision.

## 1. Release outcome

v0.54.0 is complete when an operator or contributor can start from a clean
checkout or a shipped artifact and prove these claims:

1. The primary operator path is one sequence: install, configure, validate,
   run, observe, diagnose, upgrade, and recover.
2. The documented CLI path uses `pg-tide doctor`, `pg-tide status`,
   `pg-tide config validate`, `pg-tide config export`, `pg-tide run`,
   `pg-tide replay`, and `pg-tide maintenance sweep`.
3. Every supported failure has a bounded stable code, a component, a safe
   message, a likely cause, a next action, a runbook, a retry classification,
   and an exit code where a CLI process is involved.
4. Existing v1 CLI JSON fields, types, meanings, and exit codes remain
   compatible, including the allowed field set. Actionability uses the five
   frozen diagnostic fields; retry, runbook, and exit metadata live in the
   checked operator-error catalog.
5. The primary documentation describes only the PostgreSQL outbox source, the
   four supported destinations, native and CloudEvents envelopes, and clearly
   labeled stdout and file diagnostics.
6. Every command or configuration example in the Quick Start and supported
   runbooks is marked `tested` and maps to a required CI test.
7. Installation, SQL, pipeline JSON, TOML, CLI, Docker, Helm, CloudNativePG,
   upgrade, recovery, and supported connector examples run in CI at the level
   needed to prove each example.
8. A person other than the runbook author completes every required operational
   drill and records the result against the tested runbook digest.
9. `pg-tide doctor --bundle <directory>` writes a bounded, machine-readable,
   redacted support directory without payloads, secrets, connection strings,
   certificates, internal addresses, or unbounded logs.
10. Active plans, completed release plans, retained research, ADRs, and current
    user documentation have separate locations and indexes.
11. Every retained script, schema, fixture, example, generated file, and large
    tracked file has a discoverable purpose and owner. A caller, contract,
    test, or index records why it remains where that evidence applies.
12. A clean public checkout can run `just setup`, `just fmt`, `just lint`,
    `just test`, `just docs`, and `just check` without a sibling repository,
    private dependency, or undocumented default service.
13. Release notes report the measured repository changes against the committed
    pre-v1 baseline. Missing baseline values remain missing rather than becoming
    estimates.

The release covers PostgreSQL 18, the public `tide.*` SQL API, the `pg-tide`
relay, the four supported destinations, and the existing Docker, Helm, and
CloudNativePG deployment paths.

Reuse these sources of truth:

- `connectors.toml` defines the supported connector boundary.
- `schemas/v1-contract-manifest.toml` defines frozen public contracts.
- `schemas/cli-json-v1.schema.json` defines the CLI JSON envelope.
- `schemas/v1-surface-disposition.json` defines removed and retained surfaces.
- `tests/required-tests.toml` defines blocking tests and evidence paths.
- `tests/flake-registry.toml` defines the zero-retry and quarantine policy.
- `docs/runbook-evidence.toml` inventories operational runbooks and automated
  checks.
- `release-evidence/pre-v1-baseline/` contains the comparison baseline captured
  during v0.48.0 from the exact v0.47.0 tag.
- `release-evidence/` binds release claims to tests, artifacts, reviews, and
  drill records.

Do not create another connector registry, CLI schema version, test inventory,
runbook registry, release orchestrator, or documentation site.

## 2. Preconditions and scope guard

### 2.1 Release preconditions

Before the first implementation pull request:

1. Confirm that the v0.53.0 tag resolves to the release commit on `main`.
2. Confirm that every non-deferred v0.53.0 exit criterion passes on `main`.
3. Reconcile `release-evidence/v0.53.0-index.json` and
   `release-evidence/v0.53.0-performance.json`. Keep both records `pending`
   with the performance qualification explicitly deferred to v0.56.0; do not
   invent a v0.53.0 qualification result.
4. Preserve the v0.53.0 pending records and the 8-hour qualification workflow
   contract for the v0.56.0 exact-candidate run.
5. Run the existing static gates:

   ```bash
   just check-v1-contracts
   just check-v1-surface
   just check-required-tests
   just check-flakes
   just check-lifecycle-contract
   just check-operational-budgets
   python3 scripts/check_observability.py
   python3 scripts/check_pre_v1_baseline.py --check
   ```

6. Capture the current documentation navigation, orphan-page list, script
   inventory, schema inventory, fixture inventory, direct dependencies, Cargo
   features, tracked executable files, and files larger than the chosen
   hygiene threshold. Commit the inventory to the first pull request as review
   evidence, not as a new permanent product registry.
7. Record the current CLI JSON schema and fixtures by digest before changing
   diagnostic output.
8. Record the current `docs/runbook-evidence.toml` entries and the missing
   v0.54.0 drill scenarios.
9. Confirm that the working release branch has no unrelated changes.

At the planning commit, the `v0.53.0` tag is present and both v0.53.0 evidence
files still have `status` set to `pending`. They name the missing 8-hour
qualification, reference-run review, artifact digests, and approvals. That
performance proof is explicitly deferred to v0.56.0. The first v0.54.0
implementation pull request must preserve that pending status and recorded
deferral; it must not present the gap as closed. A statement outside the
evidence index does not satisfy the release-order record.

If any non-deferred correctness, lifecycle, security, or artifact gate fails,
stop. Documentation and repository cleanup must not hide an unresolved failure.
The deferred performance gap remains visible and is not represented as a pass.

### 2.2 Frozen contract boundary

The v0.47.0 freeze still covers:

- public `tide.*` SQL signatures and documented behavior.
- pipeline JSON fields, defaults, and validation.
- metric names, labels, units, and meanings.
- health routes, response status, and readiness semantics.
- CLI JSON envelope fields, existing diagnostic fields, and exit codes.
- native and CloudEvents envelopes.
- delivery, retry, checkpoint, replay, DLQ, and HA semantics.
- the four supported destination contracts.
- adjacent-version lifecycle behavior.

v0.54.0 may add bounded error codes within the existing diagnostic fields, a
separate checked operator-error catalog, a versioned support-bundle manifest,
documentation metadata, developer commands, repository checks, and release
evidence. It must not add, rename, or remove a CLI JSON field, change a field
type, reinterpret an existing error code, change exit code 1 or clap usage exit
code 2, or remove a supported command.

The existing commandless relay startup form and `--self-test` may remain for
compatibility. Primary documentation must use `pg-tide run` and
`pg-tide doctor`.

### 2.3 Scope decisions

Use these decisions throughout implementation:

1. **The comparison baseline remains the committed pre-v1 baseline.** The
   roadmap calls it the v0.48 baseline because v0.48 created it. The artifact
   itself correctly identifies the measured source as the exact v0.47.0 tag.
   Reports must state both facts and must not relabel the artifact.
2. **A support bundle is a directory, not a custom archive.**
   `pg-tide doctor --bundle <directory>` writes a small set of JSON files.
   Operators may use their normal archive tool if they need one file. Do not
   add compression or upload dependencies.
3. **Automated runbook tests and human drills are separate evidence.** CI proves
   commands and invariants. A recorded drill proves that a non-author could
   follow the runbook.
4. **One checked operator-error definition is authoritative.** Generate the
   Rust lookup data, machine-readable catalog, and reference page from it by
   following the existing connector-generation pattern. Runtime code does not
   parse documentation or JSON files.
5. **Primary product sections contain current product documentation only.** A
   single, clearly separated Labs and Historical Material index under
   `docs/src/` may link to retained material outside the primary product
   sections. Obsolete source, sink, protocol, and tutorial pages are deleted.
   Retain only research with continuing historical or architectural use under
   `docs/archive/research/`.
6. **Git history archives obsolete source and valueless documents.** Do not
   create an archive for deleted code or preserve every old page.
7. **Existing checks grow where they already own the contract.** Extend
   `scripts/check_observability.py`, `scripts/check_v1_artifacts.py`,
   `scripts/check_v1_surface.py`, and the required-test inventory. Add one small
   repository-hygiene checker only for gaps no current checker owns.

### 2.4 Explicit non-goals

Do not include the following work:

- a web operator interface, terminal dashboard, or control plane.
- a new source, destination, wire format, transform, or routing feature.
- PostgreSQL major-version expansion.
- a new logging or metrics system.
- a breaking CLI JSON cleanup for naming consistency.
- removal of frozen compatibility aliases without a separate deprecation
  decision.
- a hosted documentation service other than the existing GitHub Pages site.
- a general documentation execution framework for arbitrary shell scripts.
- a custom archive format or automatic support-bundle upload.
- capture of logs, payloads, secrets, connection strings, certificates, or raw
  configuration in support bundles.
- a replacement for mdBook, lychee, Cargo, `just`, or the required-test runner.
- keeping every historical plan, tutorial, screenshot, or generated file.
- moving obsolete source code into `docs/archive/`.
- adding tutorials beyond the focused v1 product.
- production pilots, ownership succession, independent discipline reviews, or
  final candidate approval assigned to v0.55.0.
- tagging or publishing v0.54.0 as part of implementation.

Fix correctness, security, lifecycle, or resource defects exposed by a required
documentation example or runbook drill. Record unrelated feature requests for
a later release.

## 3. Canonical operator and repository contracts

### 3.1 Operator journey

The following table is the navigation and acceptance contract. The first
column defines order. Documentation may link to deeper reference pages, but it
must not introduce a competing primary path.

| Step | Public interface | Primary result | Required evidence |
|---|---|---|---|
| Install | packaged extension, relay archive or image, Helm, or CloudNativePG example | installed versions and verified artifacts | packaged fresh-install and deployment-example tests |
| Configure | `tide.relay_set_outbox_v2()` and `pg-tide config export` | catalog-backed pipeline configuration | SQL, pipeline-schema, and export fixture tests |
| Validate | `pg-tide config validate` and `pg-tide doctor` | valid configuration and compatible extension | CLI JSON contract and service-backed validation tests |
| Run | `pg-tide run` | relay starts with the supported profile | startup, lifecycle, and connector tests |
| Observe | health routes, Prometheus metrics, alerts, dashboards, and `pg-tide status` | bounded health, ownership, lag, checkpoint, retry, and DLQ state | observability and CLI fixture checks |
| Diagnose | stable error catalog, `pg-tide doctor`, and `pg-tide doctor --bundle` | cause, safe action, runbook, retryability, and redacted evidence | error-contract and secret-canary tests |
| Upgrade | packaged adjacent migration and documented relay-first sequence | supported v0.53.0 to v0.54.0 operation | lifecycle and fresh-versus-upgrade tests |
| Recover | `pg-tide replay`, rollback, backup, restore, and runbooks | restored service without silent loss or unsupported offset change | recovery tests and independent drills |

Primary CLI examples must use an environment variable or a URL file for
credentials. A literal URL in documentation must use obvious placeholders and
must never appear in support evidence.

### 3.2 Stable error contract

Add `operator-errors.toml` as the one authored operator-error definition. Use
the same checked-generation pattern as `connectors.toml` to produce:

- `pg-tide-relay/src/operator_errors.rs`, generated Rust descriptor data used
  by the relay.
- `schemas/operator-errors-v1.json`, the machine-readable catalog.
- `docs/src/reference/error-catalog.md`, the human reference.

The generator's check mode fails when any generated output differs. Rust tests
compare every relay and extension code mapping with the generated code set, so
the small enum-to-code matches cannot drift from the definition.

Add an `operator.errors.v1` row to
`schemas/v1-contract-manifest.toml`. The row names the catalog, generated
reference page, runtime sources, checker, owner, and additive evolution rule.

Each source row and generated catalog row must contain:

```text
code
surface
component
summary
likely_cause
next_action
runbook
retryable
cli_exit_code
safe_context_keys
since
```

Use `null` for `cli_exit_code` on SQL-only failures. Use 1 for operational CLI
failures and 2 only for catalog rows that describe clap-owned usage failures.
Do not use zero or an empty string to mean unknown. Keep code values short and
bounded. New operator codes use the existing `PGTIDE_` prefix. Preserve these
existing value domains:

- `operator.failure` remains the frozen generic CLI fallback.
- `PGTIDE_EXTENSION_VERSION_INCOMPATIBLE` remains the lifecycle code.
- `PGTIDE_CONFIG_UNSUPPORTED_SURFACE` remains the removed-surface code.
- `ConnectorFailureCode` values remain the persisted connector status codes.

Do not rename a persisted connector code to make the CLI catalog look uniform.
The catalog can describe both value domains.

Do not add properties to `pg-tide-relay/src/cmd/output.rs::Diagnostic` or to
`schemas/cli-json-v1.schema.json`. The diagnostic definition has
`additionalProperties: false`; even an optional new property would break an old
strict validator. Encode actionability through the five frozen fields:
`code`, `component`, `message`, `likely_cause`, and `next_action`. Include the
runbook ID in `next_action`. Publish retry and exit metadata in the separate
catalog, not in a v1 response.

The current source also has optional compatibility-detail fields that the
frozen schema does not admit. PR 1 must reconcile the tagged v0.53.0 artifact,
fixture, schema, and emitted bytes before v0.54.0 error work starts. If the
released artifact does not match the frozen schema, stop for an explicit
contract decision; do not silently remove fields or widen the schema in this
release.

Keep the established exit code set:

| Exit code | Meaning |
|---:|---|
| 0 | The command completed successfully. |
| 1 | A runtime, dependency, compatibility, or operational failure occurred. |
| 2 | clap rejected command usage or a required argument. |

Retryability describes whether repeating the failed operation can succeed
without a configuration or permission change. It does not select a different
process exit code and is catalog metadata only.

### 3.3 Documentation example contract

Use one HTML comment immediately before each executable or configuration code
block in `README.md` and current documentation:

```text
<!-- pg-tide-example: tested id=<stable-id> test=<required-test-id> -->
<!-- pg-tide-example: illustrative -->
<!-- pg-tide-example: historical -->
<!-- pg-tide-example: labs -->
```

Rules:

1. Tested IDs are unique across `README.md` and `docs/src/`.
2. A `tested` marker names a required-test ID from
   `tests/required-tests.toml`.
3. Quick Start and supported runbook command, SQL, JSON, TOML, and YAML blocks
   use only `tested` markers.
4. `illustrative` blocks may explain a concept but cannot appear in the Quick
   Start or a supported procedure.
5. `historical` and `labs` blocks do not appear in primary navigation.
6. Large JSON, TOML, and YAML examples use mdBook includes from canonical files
   under `examples/` when practical. The required test validates that file.
7. A `tested` label means that CI executes the command or validates the exact
   included file. Syntax highlighting or successful Markdown rendering does
   not count.
8. Test evidence names the exact tested example IDs that it covered. Other
   maturity classes need classification, not permanent IDs.

Extend `scripts/run_quickstart_sql.py` only enough to recognize the new tested
marker while preserving existing SQL extraction behavior. Add
`scripts/check_documentation.py` for navigation, orphan pages, marker syntax,
unique IDs, and required-test cross-references. Keep it in the Python standard
library.

## 7. OPS-2: Improve errors without breaking machine contracts

### 7.1 Objective

Replace generic failure guidance on supported paths with stable, actionable,
redacted diagnostics while preserving the v1 envelope.

### 7.2 Relay error classification

Add operator metadata at the shared error boundary in
`pg-tide-relay/src/error.rs`. Do not add a guard in every command caller.

Implement a descriptor lookup for `RelayError` and `ConnectorFailureCode` that
returns:

- the stable code.
- the default component class.
- a safe summary.
- a likely cause.
- a safe next action.
- the runbook ID.
- the retry class.
- the process exit code.
- the safe context keys that may be interpolated into the frozen message
  fields or support output.

Use the existing `RetryClass`, `ConnectorFailureCode`,
`RelayError::retry_class()`, and `RelayError::public_code()` behavior. Do not add
a parallel retry enum.

Update `pg-tide-relay/src/cmd/diagnostic.rs` to build `Diagnostic` from the
descriptor and explicit command context. Remove the catch-all use of raw
`Display` text for JSON. Keep `operator.failure` for errors that cannot be
safely classified, and make its action point to the general diagnostic
runbook.

Refactor command dispatch in `pg-tide-relay/src/main.rs` so every operational
command follows one failure path:

1. collect or perform the command.
2. classify the error.
3. emit one text or JSON diagnostic.
4. return exit code 1.

Do not emit a JSON failure and then let Rust print a second raw error. clap
continues to own usage diagnostics and exit code 2.

Cover at least these operational classes through the JSON diagnostic path:

- PostgreSQL unavailable.
- extension version incompatible.
- extension or catalog missing.
- permission denied.
- pipeline missing.
- pipeline invalid.
- pipeline not discovered or not owned.
- connector unavailable.
- connector authentication or authorization failure.
- TLS verification failure.
- webhook destination rejected by the SSRF policy.
- DLQ or replay input invalid.
- maintenance sweep rejected or failed.
- support-bundle output path or write failure.
- graceful shutdown failure.
- unknown internal failure.

Catalog missing PostgreSQL URL and invalid command usage separately as
clap-owned usage failures. They remain text usage diagnostics with exit code 2;
they do not produce a v1 JSON envelope because parsing and
`require_postgres_url()` exit before command dispatch.

### 7.3 SQL error codes

Add stable code metadata to `PgTideError` in
`pg-tide-ext/src/error.rs`. Preserve the existing contextual message after the
`PGTIDE_*: ` prefix byte for byte. Put the prefix in each enum display
definition so the existing `pgrx::error!("{}", error)` boundaries in
`outbox.rs`, `inbox.rs`, `relay.rs`, and `lifecycle.rs`, plus the `template.rs`

## 19. Failure handling during implementation

### 19.1 Contract regression

If an error improvement breaks an old CLI fixture or changes an existing field
type, stop and restore compatibility. Do not increment `schema_version` merely

### 19.2 Documentation example failure

1. determine whether code, packaging, configuration, or documentation is

2. fix the owning source.
3. add or retain the failing example as the regression check.
4. rerun the related public API and lifecycle gates.

### 19.3 Runbook drill failure

Keep the result `fail`. Correct the product or procedure, update its digest, and
rerun the full scenario with a non-author. Do not edit only the evidence status.

### 19.4 Redaction failure

Treat any secret-canary occurrence as a security blocker. Preserve only the
canary category and failing field in sanitized test output. Do not upload the
leaking bundle or raw bytes.

### 19.5 Cleanup uncertainty

If a script, schema, fixture, document, or dependency has an unclear caller or
owner, search source, workflows, release packaging, and Git history. Keep it
temporarily with an explicit disposition issue only when deletion could break a
supported path. An unclear purpose is not a permanent exemption.

### 19.6 Link movement failure

If archive movement breaks a current tracked link, fix the link in the same
pull request. Do not weaken lychee or add a broad archive exclusion.

### 19.7 Missing baseline data

Report `baseline_unavailable` and retain the original reason. Do not rerun a
modern tool against the old source and present the result as if v0.48 captured
it, unless the methodology and provenance are explicitly recorded as a new
retrospective measurement.

## 23. Definition of done

v0.54.0 is done only when:

1. every exit criterion above passes for the release contents.
2. a new operator can follow the canonical journey through public interfaces
   and tested documentation.
3. supported failures lead from stable code to safe action and a drilled
   runbook without revealing sensitive data.
4. existing machine consumers continue to accept the CLI JSON and exit codes.
5. all supported examples run at the evidence level they claim.
6. every required runbook has the applicable automated evidence and a
   successful independent human drill.
7. the support directory remains bounded and passes the full secret-canary
   scan.
8. primary product documentation contains only the focused supported product,
   with Labs and Historical Material clearly separated.
9. current documentation has no orphan, duplicate, conflicting, stale, or
   broken page.
10. retained repository files have a discoverable purpose and owner.
11. all six contributor recipes are exercised from a clean public checkout,
    with lint, test, and docs running once through the aggregate check.
12. the release notes and repository evidence report measured simplification
    without inventing missing baseline values.
13. version, migration, lifecycle, package, CI, and release evidence agree.
14. relevant inherited correctness, security, lifecycle, and performance gates
    pass, and no v0.54.0 release gate is waived.

If any condition fails, keep v0.54.0 pending. Do not relabel a supported
example, weaken a link or hygiene check, mark a failed drill as reviewed, add
raw diagnostics to a support bundle, or change a frozen machine contract to
preserve the release schedule.
