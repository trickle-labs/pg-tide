# pg_tide v0.42.0 Implementation Plan

> **Status:** Proposed  
> **Release theme:** Crash-Safe by Construction  
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)  
> **Starting point:** v0.41.0 and current `main`  
> **Scope rule:** Prove that every committed source event survives the supported relay paths. Do not add connectors, promote preview features, or claim transport-level exactly-once delivery.

---

## 1. Release Outcome

v0.42.0 is complete when the relay has one documented delivery state machine and black-box tests prove its invariants at every important failure boundary:

1. A source checkpoint is never advanced before the complete batch has reached a durable terminal disposition: sink acknowledgment, durable DLQ storage, or an explicitly documented operator disposition such as live dry-run.
2. A crash before source checkpoint commit causes retry or redelivery; it never causes silent loss.
3. A crash after downstream success but before checkpoint commit may cause a duplicate with the same stable event identity; it never skips the event.
4. A crash after checkpoint commit does not replay the batch unless an administrator explicitly rewinds it.
5. NATS JetStream source messages remain unacknowledged until the configured sink confirms the batch. Decode, stream, and acknowledgment errors are visible and do not discard broker messages.
6. Native outbox, consumer-group, and fan-in offset writes are monotonic by default. Fan-in remains experimental, but its stored offsets obey the same invariant.
7. Administrative rewind is the only supported offset-decrease path. It requires explicit confirmation, refuses unsafe concurrent use, authorizes the invoking role rather than the `SECURITY DEFINER` owner, and writes an audit record containing the old and new offsets.
8. DLQ insertion is all-or-nothing for a batch. The source checkpoint advances only after every failed message is durably present in the DLQ or was already present under its idempotency key.
9. Pipeline ownership is held by the exact PostgreSQL session whose lifecycle is tied to the worker. Losing that session stops the worker before another instance safely takes over.
10. Two real relay processes can contend for one pipeline, lose the active owner through process or PostgreSQL-session failure, transfer ownership, and deliver all events without a silent gap.
11. Test-only failpoints make each state boundary deterministic without adding a production runtime dependency or a user-configurable fault surface.
12. Metrics and structured logs identify publish ambiguity, checkpoint failure, DLQ failure, lock loss, and ownership transfer without logging payloads or secrets.
13. Active documentation consistently uses:
    - **atomic outbox write** for the PostgreSQL transaction;
    - **at-least-once relay transport** for cross-system delivery;
    - **effectively exactly once** only when the destination durably deduplicates the stable event ID.

The release does not promise that a network publish and a PostgreSQL offset update are one distributed transaction. It proves the safe consequence of that boundary: duplicates are possible, silent loss is not.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.41.0 is a hard prerequisite

The focused roadmap forbids starting a release while the prior release gate is incomplete. Before v0.42.0 implementation begins, confirm the v0.41.0 release checks still pass on `main`:

- clean-checkout workspace build and test;
- generated connector registry, compatibility matrix, build profiles, and release checklist are current;
- production artifacts use `core`, not `experimental-full`;
- supported connector rows have real owners and evidence paths;
- PostgreSQL support remains explicit;
- fresh v0.41.0 install and v0.40.0 to v0.41.0 upgrade are equivalent.

The repository is tagged `v0.41.0`, but the implementation must still run the current gates rather than treating the tag as evidence.

### 2.2 The supported crash-matrix scope comes from `connectors.toml`

At the v0.41.0 baseline, the production connector surfaces that affect the v0.42.0 matrix are:

| Surface | Runtime direction to prove |
|---|---|
| PostgreSQL native outbox | Source to each supported sink |
| NATS JetStream | Native outbox to NATS sink, and NATS source to PostgreSQL inbox |
| PostgreSQL inbox | Local `inbox` sink and remote `pg_outbox`/`PgInboxSink` path |

`stdin`, `stdout`, and file are diagnostics. They need state-machine unit coverage but are not production connector crash-matrix rows.

Kafka and webhook remain preview at the baseline. They must compile and preserve the common worker contract, but v0.42.0 does not promote them or block on a full connector-specific crash matrix. If their maturity changes before implementation starts, the matrix expands automatically: every `supported` source and sink direction must pass before release.

Fan-in and consumer groups receive monotonic-offset and common checkpoint tests. Fan-in remains quarantined and is not promoted by this work.

### 2.3 The durable unit is one polled batch and its source checkpoint

The worker keeps batch publishing. It does not introduce per-message offset commits or a second delivery-state table.

For one polled batch:

- the source provides the checkpoint represented by the last polled source item;
- transforms and routing may remove messages, but they do not change the checkpoint covering the original batch;
- a sink either confirms the batch according to its connector contract or returns an error;
- a partial sink-side effect is treated as an ambiguous publish and the original checkpoint remains uncommitted;
- retry uses the same stable `dedup_key`;
- the source checkpoint advances only after the whole batch has a durable terminal disposition.

For NATS sink, publishing a multi-message batch is not atomic. If the first messages succeed and a later publish fails, the entire batch is retried and the prefix may duplicate. That is the intended at-least-once behavior.

For PostgreSQL inbox sinks, the `INSERT ... UNNEST` statement is one PostgreSQL transaction. Connection loss may leave either zero rows or the complete committed batch; stable `event_id` uniqueness makes retry idempotent.

### 2.4 State names are explicit and finite

ADR-012 and code use these logical states:

```text
Polled
  -> Prepared
  -> PublishInFlight
  -> SinkAcknowledged
  -> CheckpointCommitted
  -> EligibleForCleanup
```

Alternative terminal paths are:

```text
Prepared -> DryRunObserved -> CheckpointCommitted
PublishFailed -> DlqPersisted -> CheckpointCommitted
Prepared -> IntentionallyFiltered -> CheckpointCommitted
```

Errors that do not create a terminal disposition, including decode failure, transform failure, sink failure below the DLQ threshold, and DLQ write failure, leave the source checkpoint uncommitted.

`EligibleForCleanup` is a state-machine consequence, not new v0.42.0 cleanup behavior. Pipeline-aware retention remains v0.43.0 scope.

### 2.5 “Acknowledged” means the connector’s durable success boundary

Each supported connector documents the exact point at which `Sink::publish()` may return `Ok(())`:

| Connector | Success boundary |
|---|---|
| NATS JetStream sink | Every publish acknowledgment future completed successfully |
| Local PostgreSQL inbox | The batch `INSERT ... ON CONFLICT` statement completed |
| Remote PostgreSQL inbox | The remote batch `INSERT ... ON CONFLICT` statement completed |

For source acknowledgment:

| Source | Durable checkpoint boundary |
|---|---|
| Native PostgreSQL outbox | Monotonic `relay_consumer_offsets.last_change_id` persisted |
| PostgreSQL consumer group | Monotonic `tide_consumer_offsets.committed_offset` persisted |
| NATS JetStream source | Every pending JetStream message acknowledgment completed |

An `Ok(())` that only means “queued in client memory” is not sufficient for a supported connector.

### 2.6 Dry-run remains an explicit consuming mode; replay does not

Preserve the active dry-run documentation contract: a continuously running pipeline logs the prepared messages, skips the sink, and advances its source checkpoint so it can inspect subsequent batches. Treat `DryRunObserved` as an explicit operator-selected terminal disposition.

Repair the contradictory tests and comments that claim dry-run does not advance. Native `consumed_at` is not evidence either way; tests must inspect the actual source checkpoint.

Replay is different:

- replay must never advance or rewind the live checkpoint implicitly;
- an inline replay range must read from its explicit start rather than the live offset;
- completion must not cause the coordinator to restart the same one-shot replay forever;
- any transition from replay back to live delivery is explicit;
- intentional reprocessing of live offsets uses the administrative rewind API.

If the existing continuously managed inline replay mode cannot meet those rules without becoming a second scheduler, reject it in the production profile and direct users to the one-shot replay command. Do not retain a mode whose tests simulate safety without running the real coordinator.

### 2.7 Ownership is a worker-held PostgreSQL session property

ADR-002’s session-lock decision remains, but v0.42.0 corrects the implementation:

- never acquire a session advisory lock through a pooled client that is immediately returned to the pool;
- never release a session advisory lock through an arbitrary pooled client;
- acquire the lock on a dedicated PostgreSQL connection;
- keep that connection with the worker for the worker’s entire lifetime;
- monitor the connection driver;
- cancel the worker immediately when the ownership connection ends;
- release cleanly through the same session after the worker drains;
- on hard crash or forced cancellation, let session teardown release the lock.

Use one canonical lock identity in Rust, SQL administrative checks, tests, logs, and ADRs:

```text
(relay_group_id, tenant_name, direction, pipeline_name)
```

The SQL key may continue using PostgreSQL’s two-key advisory-lock API, but one shared helper must derive both integers. Do not duplicate string construction in acquire, release, rewind, doctor, and tests.

Because v0.41.0 and v0.42.0 would derive different ownership keys, mixed relay versions are not supported. The upgrade runbook must require stop-all, upgrade, start v0.42.0.

### 2.8 Failpoints are internal test instrumentation

Use a small internal failpoint module rather than a third-party failpoint framework.

Requirements:

- gated by a non-default `test-failpoints` Cargo feature;
- excluded from `core`, `core-kafka`, `experimental-full`, Docker, and release binaries;
- inactive unless a test-specific environment variable names an allow-listed failpoint;
- supports a deterministic pause/ready handshake so the parent test can kill the real relay process at the boundary;
- supports an injected error where process death is not the behavior being tested;
- never accepts arbitrary code, SQL, duration, or command strings;
- logs only the failpoint name and pipeline;
- has a release assertion that the production binary contains no failpoint activation surface.

No new runtime dependency is needed.

### 2.9 Offset decreases are exceptional and auditable

Normal writes are monotonic at both layers:

- Rust and SQL write paths use `GREATEST` or an equivalent guarded update;
- database triggers reject a lower value from normal callers;
- equal writes are idempotent;
- negative offsets are rejected;
- in-memory positions update only after durable checkpoint success.

Administrative rewind:

- requires `confirm_reprocessing = TRUE`;
- requires the invoking `session_user` to be a superuser or a member of `pg_tide_admin`;
- records the invoking `session_user`, old offset, new offset, and complete offset identity;
- requires the target to be lower than or equal to the current value;
- locks the offset row;
- refuses to run while the corresponding live pipeline ownership lock is held;
- does not silently create a missing offset row.

The existing `tide.admin_rewind_offset()` must be corrected rather than replaced for consumer groups. Add a separate, unambiguous native relay function such as:

```sql
tide.admin_rewind_relay_offset(
    p_relay_group_id text,
    p_pipeline_id text,
    p_outbox_name text,
    p_target_offset bigint,
    confirm_reprocessing boolean default false
)
```

Fan-in uses the same relay function with the member’s `outbox_name`; no second fan-in rewind API is needed.

### 2.10 Release metadata changes last

v0.42.0 requires a real extension migration because rewind and monotonic enforcement change SQL behavior. Add the migration and validate it before changing workspace, control, and Helm versions.

Do not tag, publish, push, or create release artifacts as part of implementation unless separately requested.

| Surface | v0.41.0 state | Required v0.42.0 state |
|---|---|---|
| Delivery model | Ordering is implicit across a large `worker_inner()` match | ADR-012 and code share one finite state/terminal-disposition model |
| Original batch checkpoint | Acknowledgment often uses the last message remaining after transforms/routing | Preserve the checkpoint from the original polled batch |
| Empty transform result | Comment says acknowledge, code continues without acknowledging | Explicit `IntentionallyFiltered` disposition commits the original checkpoint |
| Dry-run | Runtime acknowledges but ignores acknowledgment errors; tests claim it does not advance | Documented consuming behavior, real coordinator test, checkpoint errors propagated |
| Replay | Tests simulate non-advancement; runtime can acknowledge and can start from the live offset | Real one-shot behavior never mutates the live checkpoint |
| NATS source | Messages are acknowledged inside `poll()` before sink success | Keep broker messages pending and acknowledge only after sink/DLQ terminal success |
| NATS decode/stream errors | Invalid JSON becomes `null`; per-message stream errors are warnings | Fail visibly and keep affected broker messages unacknowledged |
| Sink success path | Offset failure is logged and retried, but success/DLQ/dry-run paths use different code | One checkpoint-commit helper with consistent error handling |
| DLQ batch write | Per-entry loop returns success after a partial write | One atomic batch insert; no checkpoint on any unresolved DLQ write |
| DLQ acknowledgment | `source.acknowledge()` result is discarded after DLQ success | Checkpoint failure is unhealthy and retried/stopped visibly |
| Delivery receipts | Written after checkpoint and intentionally best-effort | Remain auxiliary; ADR states they are not authoritative delivery state |
| Simple offsets | Monotonic `GREATEST` upsert exists | Retain and add negative/decrease tests plus DB enforcement |
| Consumer-group offsets | SQL function has a monotonic guard | Verify equal/higher/lower concurrency and secure rewind behavior |
| Fan-in offsets | Uses `GREATEST`, but insert omits v0.40.0’s required `outbox_name` | Valid outbox-scoped monotonic upsert with affected-row verification |
| Rewind authorization | `SECURITY DEFINER` function checks/audits `current_user` | Authorize and audit the invoker (`session_user`) |
| Relay rewind | No native relay-offset administrative API | Explicit locked and audited relay rewind |
| Advisory-lock acquire | Pool connection acquires a session lock and returns to pool | Dedicated worker ownership session |
| Advisory-lock release | An arbitrary pool connection attempts unlock | Same-session release or session teardown only |
| Lock loss | Worker is not directly tied to lock-session liveness | Lock-session loss cancels worker before takeover |
| Shutdown timeout | Code may release locks while a timed-out worker task still exists | Stop/abort worker first; session release follows task termination |
| HA test | Starts B only after gracefully signalling A; checks ownership only | Two real simultaneous processes, hard failure, delivery invariants, metrics/logs |
| “Exactly once” prose | Central docs still open with broad exactly-once claims | Qualified atomic-write/at-least-once/effective-outcome language |
| Registry evidence | Existing v0.40 E2E paths are listed as several failure proofs they do not perform | Evidence paths point to actual v0.42 crash tests |

## 4. Workstream A: ADR-012 and the Delivery Contract

### A.1 Add ADR-012

Create:

```text
docs/adr/adr-012-relay-delivery-acknowledgment-and-offset-state-machine.md
```

The ADR must define:

- the batch as the unit of checkpoint advancement;
- the state names in section 2.4;
- the supported connector acknowledgment boundaries;
- how filtered, dry-run, DLQ, and replay paths differ;
- why downstream success before checkpoint commit produces duplicate risk but not loss;
- why checkpoint commit before worker-memory update is safe;
- what happens on partial multi-message NATS publish;
- stable deduplication identity requirements;
- ownership-session lifecycle;
- graceful and forced shutdown behavior;
- metrics, logs, and required tests for every transition;
- the exact qualified delivery terminology;
- the relationship to ADR-002 and ADR-011;
- why pipeline-aware cleanup is deferred to v0.43.0.

Add ADR-012 to `docs/adr/README.md` and the active architecture-decision reference page.

### A.2 Record the transition matrix in the ADR

The ADR’s normative table must include at least:

| Transition / state | Durable fact | Retry after crash | Duplicate risk | Silent-loss risk if implemented correctly | Evidence |
|---|---|---|---|---|---|
| Start -> `Polled` | None beyond source’s existing durable state | Poll/redeliver | None yet | None | pre-encode crash test |
| `Polled` -> `Prepared` | None | Poll/redeliver | None yet | None | post-prepare crash test |
| `Prepared` -> `PublishInFlight` | Sink-dependent and possibly ambiguous | Retry original batch | Possible prefix duplicate | None; checkpoint unchanged | during-publish test |
| `PublishInFlight` -> `SinkAcknowledged` | Destination confirmed according to connector contract | Retry if checkpoint absent | Yes | None | post-sink-ack crash test |
| `SinkAcknowledged` -> `CheckpointCommitted` | Source durable checkpoint advanced | Resume after batch | No automatic replay | None | post-checkpoint crash test |
| `PublishFailed` -> `DlqPersisted` | Every DLQ row durable/idempotently present | Retry DLQ insert if uncertain | Duplicate DLQ insert suppressed | None | DLQ crash/failure tests |
| `DlqPersisted` -> `CheckpointCommitted` | Source durable checkpoint advanced past DLQ batch | Resume after batch | No message redelivery | None | DLQ acknowledgment test |
| `Prepared` -> `DryRunObserved` | Structured observation emitted | Documented consuming dry-run continues | Not applicable | Operator explicitly selected no sink delivery | dry-run coordinator test |
| `Prepared` -> `IntentionallyFiltered` | Filter decision completed for whole input batch | Continue after checkpoint | None | None if original checkpoint retained | all-filtered test |
| `CheckpointCommitted` -> `EligibleForCleanup` | All relevant pipeline offsets eventually pass row | No relay retry | None | Cleanup not implemented in v0.42.0 | ADR-only until v0.43.0 |

### A.3 Amend ADR-002

ADR-002 remains accepted. Add a v0.42.0 clarification:

- the lock-holding PostgreSQL session is owned by the pipeline worker;
- pooled metadata connections cannot hold ownership locks;
- lock-session loss is a worker cancellation condition;
- lock release happens after drain or forced task termination;
- the canonical lock identity includes relay group, tenant, direction, and pipeline;
- v0.41.0/v0.42.0 mixed relay ownership is unsupported.

Do not create a competing ADR for the same advisory-lock decision.

### A.4 Extend ADR-011

Add a short relationship note rather than duplicating ADR-012:

- `last_change_id` means the greatest source row whose batch reached a durable terminal disposition;
- downstream acknowledgment precedes the monotonic checkpoint;
- administrative rewind is the only supported decrease;
- delivery receipts are evidence, not the authoritative checkpoint.

## 5. Workstream B: Make the Worker Follow the State Machine

### B.1 Preserve the original polled checkpoint

In `pg-tide-relay/src/coordinator.rs`:

1. Capture the last source checkpoint immediately after a non-empty poll.
2. Keep it separate from the mutable message vector.
3. Pass transformed/routed messages to the sink.
4. Use the original checkpoint after the batch reaches sink success, DLQ success, dry-run observation, or complete intentional filtering.
5. Never infer the checkpoint from `batch.last()` after a transform or route may have removed trailing messages.

Avoid a general workflow framework. A small local batch context containing the original checkpoint and current messages is sufficient if it makes illegal ordering difficult.

### B.2 Use one checkpoint-commit path

Extract one async helper for the final source acknowledgment transition. It must:

- call `Source::acknowledge()` with the original checkpoint;
- emit the checkpoint success metric and structured transition log only after `Ok(())`;
- update success-shaped delivery receipts only after durable checkpoint success;
- mark the pipeline unhealthy and emit a checkpoint error metric on failure;
- return the error/directive to the worker rather than discarding it.

Use it for:

- normal sink success;
- durable DLQ success;
- live dry-run;
- a fully filtered batch.

Do not retain `let _ = source.acknowledge(...)` in any production path.

For an outbox checkpoint failure, retrying the batch is valid because the source’s in-memory offset must not advance before the database write. For a broker-source acknowledgment failure, stop/recreate the worker or retry the acknowledgment without polling another batch. Do not overwrite pending broker acknowledgments by polling again.

### B.3 Make metrics describe real boundaries

Move or define counter updates according to the ADR:

- `messages_consumed_total`: source items successfully polled;
- `messages_published_total`: sink acknowledged the messages, even if checkpoint commit later fails;
- checkpoint-commit success/error: the source accepted the durable checkpoint;
- delivery latency: observe only after checkpoint commit, and document that it includes source acknowledgment;
- delivery receipts: write only after checkpoint commit;
- pipeline health: unhealthy on ambiguous publish, checkpoint failure, DLQ failure, or ownership loss.

Do not use `publish_errors_total` as the only signal for an offset/checkpoint failure.

### B.4 Handle filtered batches correctly

Add real tests for:

- every message filtered by transforms;
- only trailing messages filtered;
- routing removes every message;
- a transform error;
- a schema-policy pause.

Expected behavior:

- successful intentional filtering commits the original batch checkpoint;
- transform evaluation failure and schema-policy pause do not commit;
- no empty-batch sink call is used as a substitute for the disposition decision.

### B.5 Preserve and prove dry-run semantics

Keep dry-run as a consuming inspection mode:

- log at a bounded level without payload or secret leakage;
- commit the original source checkpoint after observation;
- propagate checkpoint errors;
- increment a dry-run/terminal-disposition metric, not sink-published metrics;
- run the real coordinator test and verify the sink remains unchanged while the offset advances.

Update `dry_run_test.rs` and active docs to remove the current contradiction.

### B.6 Make replay checkpoint-neutral

Replace simulated replay assertions with a coordinator-level test:

1. Seed a live offset.
2. Execute a bounded replay range that starts before that offset.
3. Observe the requested stable event IDs at the destination or dry-run output.
4. Verify the live offset is byte-for-byte unchanged.
5. Verify replay completion does not restart indefinitely.

The live `Source::acknowledge()` path must not run for replay. Reject invalid ranges (`from < 0`, `to < from`) before worker startup.

If inline replay remains, give it an explicit starting cursor separate from the live offset and a durable one-shot completion state. Otherwise remove it from the production runtime and keep replay in the dedicated command path. Do not build a new replay scheduler in this release.

## 6. Workstream C: Make Supported Sources Acknowledge Safely

### C.1 Fix NATS JetStream source ordering

In `pg-tide-relay/src/source/nats.rs`:

- stop acknowledging messages inside `poll()`;
- retain the raw JetStream messages for exactly the current polled batch;
- refuse a second poll while a prior batch is pending acknowledgment;
- acknowledge each retained broker message only from `Source::acknowledge()`;
- remove a pending message only after its acknowledgment future succeeds;
- return acknowledgment errors to the worker;
- clear pending state on complete success;
- rely on JetStream redelivery after worker/session loss for any unacknowledged suffix.

The source should continue exposing the stable incoming `Nats-Msg-Id` as the relay `dedup_key`. If it is absent, document the generated identity’s restart limitation and do not claim effectively exactly-once outcomes for that message.

### C.2 Fail visibly on NATS source decode and stream errors

Remove loss-shaped fallbacks:

- invalid JSON must not become `Value::Null` and then be acknowledged;
- a stream item error must not be logged and skipped while other raw messages are acknowledged;
- a failed batch remains unacknowledged;
- the pipeline becomes unhealthy with a source/decode error metric and structured log.

Routing source decode failures to DLQ may be added only if the raw message and its acknowledgment handle can remain coupled through durable DLQ success. The minimal acceptable v0.42.0 behavior is to pause visibly without acknowledging.

### C.3 Verify PostgreSQL source checkpoint behavior

For native simple mode:

- preserve the v0.40.0 `(relay_group_id, pipeline_id, outbox_name)` identity;
- keep `GREATEST` in the upsert;
- verify `RETURNING last_change_id` is at least the attempted value;
- update `self.last_offset` only after durable success;
- add the post-database-commit/pre-memory-update failpoint.

For consumer groups:

- keep `commit_offset()` monotonic;
- propagate SQL function errors;
- do not acknowledge visibility leases before terminal disposition;
- test two consumers attempting lower/higher commits concurrently.

For fan-in:

- include `outbox_name` in every v0.40.0-schema insert;
- keep one offset row per member;
- use one atomic batch upsert;
- validate the returned/affected rows cover every member;
- update every member’s in-memory offset only after the database statement succeeds.

Fan-in stays disabled and experimental after these fixes.

## 7. Workstream D: Make DLQ a Fail-Safe Terminal Disposition

### D.1 Replace partial-success DLQ insertion

In `pg-tide-relay/src/dlq.rs`, replace the per-entry best-effort loop with one parameterized batch statement or explicit transaction that is atomic for the complete batch.

Required behavior:

- all new rows insert, existing `(pipeline_name, dedup_key)` rows count as already durable, or the operation fails;
- one row error cannot return overall `Ok(())`;
- an empty input remains a no-op;
- retries are idempotent;
- the result reports how many rows were newly inserted versus already present if metrics need the distinction.

Do not add a second queue or an in-memory fallback. If PostgreSQL cannot durably record the DLQ batch, the source checkpoint remains unchanged.

### D.2 Use the common checkpoint transition after DLQ

After `DlqPersisted`:

- invoke the same checkpoint helper as normal delivery;
- propagate checkpoint failure;
- leave stable DLQ rows in place so retry is harmless;
- do not reset failure counters until both DLQ persistence and source checkpoint succeed.

### D.3 Test both DLQ failure classes

Add tests for:

- transient PostgreSQL connection failure during DLQ insert: retry, no checkpoint;
- permanent permission/configuration failure: pipeline unhealthy/paused, no checkpoint;
- crash after DLQ commit but before source checkpoint: same DLQ identity remains one row, source redelivers, retry commits checkpoint;
- crash after source checkpoint: no automatic reprocessing;
- multi-row batch where one row would previously have failed: zero partial durable disposition and no checkpoint.

Assert `dlq_write_errors_total`, pipeline health, and error logs. Do not accept “function returned an error” as the only invariant.

## 8. Workstream E: Enforce Monotonic Offsets and Safe Rewind

### E.1 Add SQL-level monotonic enforcement

The v0.41.0 to v0.42.0 migration must add monotonic enforcement for:

- `tide.tide_consumer_offsets.committed_offset`;
- `tide.relay_consumer_offsets.last_change_id`.

Use small `BEFORE UPDATE` trigger functions that:

- allow equal or higher values;
- reject negative values;
- reject a decrease from normal roles;
- permit a decrease only in extension-owner/superuser execution context used by the administrative rewind functions;
- write the decrease audit record from the trigger so no allowed decrease can bypass auditing.

The trigger audit must record `session_user` as the actor. Direct superuser/catalog manipulation cannot be made impossible, but it is not a supported API and must not weaken the function contract.

### E.2 Correct `tide.admin_rewind_offset()`

Replace its authorization and audit logic so:

- authorization checks `session_user`, not the `SECURITY DEFINER` `current_user`;
- `PUBLIC` execute is revoked unless the repository’s role model explicitly grants it;
- only superusers and `pg_tide_admin` members may call it;
- confirmation is mandatory;
- target is non-negative and not above the current offset;
- the row is selected `FOR UPDATE`;
- missing group/consumer errors;
- the trigger records old and new values with the invoker;
- function `search_path` remains fixed to `tide, pg_catalog`.

Add positive and negative pgrx/integration tests for ordinary roles, admin membership, superuser, missing rows, omitted confirmation, negative targets, forward targets, and concurrent commit attempts.

### E.3 Add native relay rewind

Add `tide.admin_rewind_relay_offset()` with the contract in section 2.9.

Before updating:

1. Resolve the pipeline and tenant/direction needed for the canonical ownership key.
2. Require the pipeline to be disabled.
3. Attempt the matching transaction-scoped advisory lock.
4. Refuse if a live relay session still holds ownership.
5. Lock the exact offset row `FOR UPDATE`.
6. Validate and update.
7. Let the monotonic trigger write the audit row.

The operator runbook must say: disable pipeline, wait for ownership to drain, invoke rewind with confirmation, inspect the audit row, re-enable pipeline, and monitor duplicate handling.

### E.4 Guard every runtime offset path

Add focused tests that attempt lower, equal, and higher updates through:

- simple native source;
- consumer-group `commit_offset()`;
- fan-in batch commit;
- replay completion;
- both administrative rewind functions.

The lower normal write must leave the stored value unchanged and return a visible error where the caller requested a forbidden change. Equal idempotent writes must not fail.

## 9. Workstream F: Tie HA Ownership to Worker Lifetime

### F.1 Introduce one ownership-session path

Refactor `Coordinator` so pipeline acquisition:

1. Resolves and validates configuration.
2. Opens a dedicated PostgreSQL connection using the same TLS policy as workers.
3. Starts and monitors that connection’s driver.
4. Attempts the canonical advisory lock on that client.
5. Spawns the worker with that same client only after acquisition succeeds.
6. Stores the stop sender, worker handle, and ownership-session lifecycle together.

Metadata discovery, config audit, and status queries continue using the pool. Only ownership locks move out of it.

Do not add database leases or an external coordinator.

### F.2 Make lock-session loss cancel the worker

The worker wrapper must race:

- normal worker completion;
- stop/drain request;
- ownership connection termination.

If the ownership connection ends:

- cancel the worker future immediately;
- do not permit another sink publish from that worker;
- mark pipeline unhealthy;
- increment lock-loss/ownership metrics;
- log relay group, tenant, direction, and pipeline;
- let PostgreSQL release the lock;
- allow another relay instance to acquire on its next reconcile.

If connection loss happens after downstream success, checkpoint persistence fails and takeover may duplicate the stable event. That is safe and must be tested.

### F.3 Fix disable, panic, and shutdown ordering

For pipeline removal, disable, worker panic, and process shutdown:

- signal stop;
- allow the current batch to finish within the configured drain timeout;
- if the timeout expires, abort the worker;
- wait until the worker future is gone;
- then release through the same live session or drop the session;
- only then report ownership removed.

Never call a pool-based `release_lock()` after removing the worker handle.

### F.4 Keep health state honest

`HealthState` must distinguish “owned” from “healthy.” Do not clear all unhealthy pipelines during reconcile merely because their worker still exists.

At minimum:

- acquired but not yet processing is not reported as successfully delivering;
- checkpoint, DLQ, or ownership-session errors make `/healthz` unhealthy;
- standby instances with zero owned pipelines may remain process-healthy;
- metrics show the number of owned pipelines independently.

## 10. Workstream G: Controlled Failpoints and the Crash Matrix

### G.1 Add fixed failpoint boundaries

Add allow-listed failpoints at:

| Failpoint | Exact location |
|---|---|
| `after_poll` | Original source checkpoint captured; before transform/prepare |
| `after_prepare` | Decode/transform/routing complete; before sink publish |
| `after_network_publish` | NATS publish accepted; before publish acknowledgment future is handled |
| `after_sink_ack` | `Sink::publish()` returned success; before source checkpoint |
| `after_checkpoint_commit` | Durable source checkpoint succeeded; before in-memory state/receipt completion |
| `during_dlq_write` | Inside the DLQ transaction before commit |
| `after_dlq_commit` | Durable DLQ batch exists; before source checkpoint |
| `ownership_connection_lost` | Induced by terminating the lock-holding PostgreSQL backend |
| `during_shutdown` | Worker has received stop while a batch is in flight |

Generic worker failpoints cover all connectors. `after_network_publish` is connector-specific because only the connector knows where network write and durable acknowledgment separate.

### G.2 Use a real child process for crash evidence

Create one crash-test harness that:

- starts the packaged PostgreSQL 18 extension;
- starts NATS JetStream when needed;
- configures pipelines only through public SQL APIs;
- spawns the real `pg-tide` binary with `CARGO_BIN_EXE_pg-tide`;
- waits for a failpoint-ready marker;
- kills the child process rather than merely dropping a Rust future;
- starts a replacement process;
- observes source checkpoint, destination state, stable IDs, metrics, health, and logs;
- uses bounded timeouts and prints useful diagnostics on failure;
- cleans up child processes and temporary marker files.

The test harness may query public catalog/status surfaces to verify offsets. It may not manually advance offsets or insert destination success rows.

### G.3 Required supported-path tests

#### Native outbox -> NATS JetStream

Prove:

- crash after poll/preparation: no NATS copy before restart; event later arrives;
- partial/during publish: offset does not advance without complete sink success;
- crash after JetStream acknowledgment before offset: event is retried with the same `Nats-Msg-Id`; stream dedup may reduce the stored count to one;
- crash after offset: event is not republished;
- restart loads the exact outbox-scoped offset;
- missing/expired JetStream dedup windows are documented as duplicate risk, not data-loss risk.

#### Native outbox -> local PostgreSQL inbox

Prove:

- crash before inbox commit: no inbox row and no source checkpoint;
- crash after inbox commit before source checkpoint: replay produces one inbox row because `event_id` is unique;
- crash after source checkpoint: no replay;
- all public SQL setup and inbox observation paths are used.

#### Native outbox -> remote PostgreSQL inbox

Prove:

- remote connection loss during `INSERT ... UNNEST` yields either zero or the complete batch;
- source offset never advances on an unconfirmed result;
- retry converges to one row per stable `event_id`;
- TLS/auth setup remains the same supported path recorded in the registry.

#### NATS JetStream -> PostgreSQL inbox

Prove:

- polling does not acknowledge NATS;
- crash before PostgreSQL commit causes JetStream redelivery;
- PostgreSQL success followed by crash before NATS acknowledgment redelivers the same stable ID and the inbox deduplicates it;
- completed NATS acknowledgment prevents automatic redelivery;
- invalid JSON and stream errors remain unacknowledged and unhealthy.

### G.4 Required common failure tests

For every supported path where the point applies:

| Failure point | Required assertion |
|---|---|
| Before publish | Retry occurs; no downstream copy exists before retry |
| During publish | Checkpoint does not advance without confirmed complete success |
| After downstream success, before checkpoint | Duplicate may occur with same identity; no event is lost |
| After checkpoint | No automatic replay |
| Relay process crash | Restart/standby resumes from durable source state |
| PostgreSQL ownership connection loss | Old worker stops and ownership transfers |
| DLQ write failure | Pipeline is visibly unhealthy/paused; source is not acknowledged |
| Shutdown | Worker finishes or is aborted before ownership is released |

### G.5 Replace misleading existing tests

Update or replace:

- `ha_failover_test.rs`, which currently starts the standby after a graceful signal and checks only health ownership;
- `exactly_once_test.rs`, whose offset tests manually mutate tables instead of running the relay;
- `graceful_shutdown_test.rs`, whose core assertions simulate database state;
- `replay_test.rs` and `dry_run_test.rs`, whose comments do not match runtime behavior;
- DLQ tests that call `insert_batch()` without exercising the coordinator checkpoint boundary.

Keep narrow database/unit tests where useful, but do not present them as crash, HA, or end-to-end proof.

## 17. Risks and Mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Pooled session locks survive or unlock on the wrong connection | Zombie ownership or split brain | Dedicated worker-held connection; same-session release; backend-termination test |
| Old and new lock keys coexist during rolling upgrade | v0.41.0 and v0.42.0 both own a pipeline | Explicit stop-all upgrade; no mixed relay versions |
| NATS batch partially publishes | Prefix duplicates on retry | Stable `Nats-Msg-Id`; checkpoint only after every ack; test partial batch |
| NATS source acknowledgment partially succeeds | Unacked suffix redelivers | Remove pending entries only after each ack; stop before a new poll on failure |
| Transform/routing drops the checkpoint-carrying message | Worker stalls or skips trailing input | Capture original checkpoint before mutation |
| DLQ partial insert followed by acknowledgment | Permanently discarded failed message | Atomic/idempotent complete-batch DLQ write |
| Rewind races an active worker | Rewind is immediately overwritten or skips intended replay | Disable requirement plus matching advisory-lock acquisition |
| `SECURITY DEFINER` checks `current_user` | Unauthorized callers appear to be the owner | Authorize/audit `session_user`; role-negative tests |
| Failpoint ships in production | Deliberate crash surface | Non-default feature, profile exclusion, release binary assertion |
| Crash tests are timing-dependent | Flaky release gate | Ready-marker handshake, fixed boundaries, bounded waits, no sleeps as proof |
| Health reports ownership as success | Operators miss stuck pipelines | Separate owned and healthy state; assert error transitions |
| Metric labels include event data | Cardinality explosion or leakage | Fixed stage/outcome labels only |
| Docs imply broker dedup is permanent | Users assume stronger guarantees than tested | Publish connector-specific dedup windows and application responsibility |
| Scope expands to preview connectors | Release becomes an unfocused connector hardening project | Matrix follows only `supported` registry rows; no promotions in v0.42.0 |
