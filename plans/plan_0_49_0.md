# pg_tide v0.49.0 implementation plan

> **Status:** Proposed
> **Release theme:** Focused Product Surface
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.48.0 and current `main`
> **Implementation branch:** `implementation-v0.49.0`
> **Scope rule:** Remove or relocate non-core product surface. Do not redesign supported delivery semantics or begin v0.50.0 correctness work.

## 1. Release outcome

v0.49.0 is complete when the source tree, runtime, SQL API, configuration schema,
documentation, CI, and release artifacts describe one product:

```text
PostgreSQL transactional outbox
  -> pg-tide relay
  -> PostgreSQL inbox, NATS JetStream, Apache Kafka, or HTTPS webhook
```

The release retains native pg_tide JSON and CloudEvents envelopes. It retains
the delivery machinery needed by those paths, including durable checkpoints,
HA coordination, retries, circuit breaking, DLQ and replay, health, metrics,
structured logs, TLS, secret references, and supported local key-file
encryption. The `stdout` and file sinks may remain for diagnostics, but product
metadata must not present them as production destinations.

The release removes preview and experimental inbound connectors, alternate
messaging systems, warehouse and data-lake connectors, ETL and notification
integrations, alternate CDC wire formats, unsupported KMS provider names,
reverse modes, DAG orchestration, managed backfill, and framework features not
used by a supported workflow. It also removes the `experimental-full` Cargo
profile and experimental release image.

The v0.48.0 pre-simplification baseline remains immutable. v0.49.0 records the
same measurements after removal so reviewers can verify that the release
reduced code, dependencies, tests, documentation, CI, and artifacts.

This release does not change the supported at-least-once delivery contract. It
must not remove or weaken PostgreSQL inbox, NATS JetStream, Apache Kafka, or
HTTPS webhook delivery.

## 2. Preconditions and scope guard

### 2.1 Release preconditions

Before the first removal commit:

1. Confirm that the v0.48.0 exit decision and required CI evidence pass on
   `main`.
2. Confirm that `release-evidence/pre-v1-baseline/baseline.json` and its
   referenced command and dependency records validate without modification.
3. Record the exact starting commit in the v0.49.0 disposition document.
4. Create the annotated `pre-v1-experimental-surface` tag at that commit and
   push the tag before deleting code.
5. Confirm that no existing local or remote tag uses that name. Never move the
   tag after removal begins.
6. Open one tracking issue for each removal slice and link it from the
   disposition record.

If the v0.48.0 gate does not pass, stop the implementation. A release tag alone
does not replace the recorded gate.

### 2.2 Freeze boundary

The following v1 surfaces remain frozen except for the reviewed subtraction of
items already classified as preview or experimental:

- public transactional outbox and idempotent inbox SQL behavior;
- supported pipeline configuration and validation behavior;
- core metric names and labels;
- health endpoint behavior;
- CLI JSON envelopes and exit-code meanings;
- native and CloudEvents envelope fields;
- the four supported destination contracts.

Any proposed removal of a frozen item must stop in SURF-1. Record why the item
was outside the v1 contract and obtain the same review required for a breaking
change. Do not hide a contract change inside connector cleanup.

### 2.3 Explicit non-goals

Do not include the following work in v0.49.0:

- changing acknowledgment, retry, checkpoint, cleanup, or duplicate-delivery
  semantics;
- adding delivery failpoints or the v0.50.0 executable state model;
- replacing any supported connector;
- adding connectors, wire formats, sources, or sinks;
- creating a plugin ABI, connector SDK, or generic Labs framework;
- redesigning stable source and sink traits that still have multiple supported
  implementations;
- general performance optimization;
- completing the v0.52.0 threat-model or supply-chain program;
- copying removed implementation code into an archive directory in this
  repository;
- rewriting historical migrations, changelog entries, release notes, or ADRs.

Tests may change when their sole subject is removed or when they enforce the
new supported boundary. Core tests may be refactored only as needed to compile
against the reduced surface.

## 3. Approved disposition boundary

SURF-1 produces the authoritative item-level decision. Start from the following
release-level decisions.

### 3.1 Retained production surface

| Area | Retained surface |
|---|---|
| Source | `outbox` using the canonical shared PostgreSQL outbox |
| PostgreSQL destination | `inbox`; retain the deprecated `pg_outbox` alias only for the frozen v1 compatibility period |
| Broker destinations | `nats` and `kafka`, outbound only |
| HTTP destination | `webhook`, outbound only |
| Event formats | `native` and `cloudevents` |
| Delivery | checkpointing, HA ownership, bounded retry, circuit breaking, DLQ, replay, graceful shutdown, and backpressure |
| Security | fail-closed PostgreSQL TLS, HTTPS and SSRF controls, secret references, HMAC signing, and `kms-local` if the supported encryption path still uses it |
| Operations | run, doctor, self-test, status, config validation, sweep, history, metrics, health, alerts, dashboards, and supported runbooks |
| Deployment | release binary, one production container line, Helm, and CloudNativePG examples |

The `pg_outbox` alias must keep the same PostgreSQL inbox behavior and must not
appear as a fifth supported destination. The migration guide must direct new
configurations to `inbox`.

### 3.2 Retained diagnostic surface

Retain `stdout` and file output only if both continue to share the existing
small diagnostic implementation. Remove `stdin` as a runtime source because
the v1 source contract contains only the PostgreSQL outbox. Diagnostic output
must remain outside production connector counts and production-support claims.

### 3.3 Removed connector and protocol surface

| Family | Remove from the main repository |
|---|---|
| Preview compatibility and inbound paths | `pg_trickle_outbox`, NATS source, Kafka source, and webhook receiver |
| Alternate queues and messaging | Redis, RabbitMQ, SQS, Kinesis, Google Pub/Sub, Azure Service Bus, Azure Event Hubs, and MQTT |
| Databases and warehouses | Elasticsearch, MongoDB, ClickHouse, BigQuery, and Snowflake |
| Object storage and data lakes | Object storage, Delta Lake, Iceberg, DuckLake, RockLake, and Arrow Flight |
| ETL and notifications | Singer, Airbyte, Slack, Discord, PagerDuty, and Fivetran-only material |
| Alternate wire formats | Debezium, Maxwell, Canal, and generic CDC JSON |
| Reverse and unavailable modes | fan-in, reverse sources, WAL logical-source groundwork, and disabled compatibility entries |
| Unsupported security providers | `kms-aws`, `kms-gcp`, and `kms-vault` feature and configuration names |

Delete implementation modules, feature flags, exclusive dependencies, tests,
examples, CI jobs, active docs, generated rows, and release artifacts for each
removed item. Preserve history through Git and the preservation tag.

### 3.4 Removed non-core framework surface

Remove the following features unless SURF-1 proves that a retained supported
workflow calls them:

- schema registry and schema-evolution integration;
- arbitrary JMESPath transforms and content-based routing;
- specialized OpenTelemetry integration;
- AsyncAPI sampling and validation that depends on removed inbound or schema
  registry paths;
- DAG orchestration and managed backfill;
- DuckLake management commands;
- multi-tenant provisioning helpers that are not part of core relay isolation;
- public partition-conversion helpers that are not required by the canonical
  outbox storage contract;
- replay extensions beyond the supported offset and DLQ recovery workflow.

Keep shared code when a supported path still calls it. For example, retain the
subject-template renderer used by supported NATS or Kafka configuration even
when arbitrary payload transforms are removed. Do not delete a shared helper
based only on its filename.

### 3.5 Labs decision

This repository has no Labs release path that satisfies the program rules.
Deletion is therefore the default disposition. A component may move to a
separate Labs repository only when, before its removal pull request merges, it
has all of the following:

- a confirmed long-term owner and security contact;
- a current protocol-level integration test;
- a real user or committed pre-v1 pilot;
- an independent release path;
- a dependency only on stable public pg_tide contracts;
- an approved destination repository.

An extraction happens in its own repository and pull request. It must not add
a compatibility layer, plugin host, or archived source copy to pg_tide. Failed
or incomplete extraction does not block deletion from the main repository.

## 6. SURF-1: Approve the v1 surface inventory

### Objective

Create one human-readable review document and one machine-readable disposition
that classify every product-facing or selectable item before deletion begins.

### Files in scope

- `plans/V1_SURFACE_DISPOSITION.md`
- `schemas/v1-surface-disposition.json`
- `connectors.toml`
- `schemas/v1-contract-manifest.toml`
- `tests/required-tests.toml`
- the v0.48.0 baseline and all sources listed below

### Inventory inputs

Inventory at least these sources:

- connector rows and generated descriptors;
- Cargo features and optional dependencies;
- source types, sink types, and wire formats accepted by runtime factories;
- public `tide.*` SQL functions and final-state catalog objects;
- CLI commands and machine-readable responses;
- pipeline JSON schema variants and fixtures;
- metric families and label values;
- health endpoints and background tasks;
- README claims, mdBook navigation, examples, and tutorials;
- Docker build arguments, image tags, labels, Helm values, and CloudNativePG
  examples;
- CI and release jobs;
- required-test and flake-registry entries.

### Machine-readable record

Each entry in `schemas/v1-surface-disposition.json` must include:

```json
{
  "id": "connector.redis",
  "kind": "connector",
  "classification": "remove",
  "last_version": "0.48.0",
  "locations": ["connectors.toml", "pg-tide-relay/src/sink/redis.rs"],
  "replacement": "nats, kafka, webhook, or postgresql-inbox",
  "owner": "@grove",
  "decision_issue": "<issue URL>"
}
```

Allowed classifications are exactly:

```text
v1-supported
diagnostic
labs
remove
internal
```

Do not invent a separate maturity scale. `classification` is a release
disposition, while connector maturity remains a support fact for retained
registry rows.

### Implementation steps

1. Generate an initial inventory from the listed sources.
2. Resolve duplicate names into one stable ID without losing any location.
3. Apply the boundary in section 3 to every item.
4. Mark a Labs item only after SURF-2 records the external repository, owner,
   test, and release path.
5. Identify frozen contract entries affected by removal and record the review
   that permits each subtraction.
6. Record the supported alternative and last available version for every
   removed runtime value.
7. Make `plans/V1_SURFACE_DISPOSITION.md` a readable rendering plus decision
   notes. Do not maintain a second independent list by hand.
8. Update the record in the same pull request whenever a later removal finds an
   omitted public item.

### Acceptance criteria

- [ ] Every connector row, feature, source, sink, wire format, CLI command,
  public SQL function, config variant, metric, docs section, image, and CI job
  has one classification.
- [ ] Every retained item maps to a supported workflow, a diagnostic use, or a
  required internal dependency.
- [ ] Every removed runtime value has `last_version` and `replacement` data.
- [ ] Labs entries include an external repository and an active owner.
- [ ] The human and machine-readable records agree.
- [ ] Reviewers approve all subtractions from frozen contract artifacts before
  implementation.

## 7. SURF-2: Preserve and extract viable Labs work

### Objective

Make experimental history recoverable without retaining experimental code or a
Labs framework in the production repository.

### Implementation steps

1. Create the annotated preservation tag required by section 2.1.
2. Include the starting commit, v0.48.0 baseline digest, and disposition record
   path in the tag message.
3. For each qualifying Labs item, copy the component through a separate
   repository workflow and prove that its test runs there.
4. Remove all dependencies on pg_tide private Rust modules from the extracted
   component. Use documented SQL, configuration, or event contracts only.
5. Mark the external repository unsupported and prevent its artifacts from
   entering the pg_tide release workflow.
6. Record the destination URL and final source commit in the disposition file.
7. If an extraction misses its removal pull request, delete the component from
   pg_tide and recover it from the tag later.

### Acceptance criteria

- [ ] `pre-v1-experimental-surface` identifies one immutable pre-removal commit.
- [ ] No removed implementation is copied under `archive/`, `labs/`, or another
  directory in this repository.
- [ ] Every `labs` entry points to an independent repository and test.
- [ ] No Labs artifact or dependency appears in a pg_tide production build.
- [ ] Deletion proceeds when no item qualifies for extraction.

## 8. SURF-3: Remove non-core connector families

### Objective

Delete non-core connectors end to end. A connector is not removed while its
feature, dependency, config value, test, docs page, or release job remains
selectable.

### Removal slices

Use separate pull requests in this order:

1. preview inbound and compatibility sources;
2. alternate queues and messaging systems;
3. databases and warehouses;
4. object storage, data lakes, and Arrow Flight;
5. ETL and notification integrations;
6. alternate wire formats;
7. reverse, fan-in, WAL, and unavailable modes;
8. unsupported cloud KMS providers and remaining stubs.

Keep `connectors.toml` as the source for the retained connector registry. Update
`scripts/generate_connector_surface.py`, then regenerate `README.md`,
`docs/src/support/connector-compatibility.md`, the connector release checklist,
`pg-tide-relay/src/descriptors.rs`, and the Cargo profile block. Do not hand-edit
generated blocks.

### Per-slice checklist

For every removed family:

1. Remove registry entries and feature flags.
2. Remove source, sink, wire-format, command, or support modules.
3. Remove factory match arms and module declarations.
4. Remove optional dependencies used only by the family.
5. Remove dev-dependencies used only by deleted tests.
6. Remove family-specific test files and fixtures.
7. Remove family-specific CI jobs, caches, services, and required-test entries.
8. Remove active docs, examples, scripts, dashboards, Helm values, and package
   claims that exist only for the family.
9. Regenerate `Cargo.lock` after the dependency change.
10. Run the supported profile and surface checks before merging the slice.

Delete `rocklake-testkit` and the sibling-checkout CI path with RockLake. Delete
`scripts/ducklake_compat_smoke.py`, DuckLake examples, and the compatibility CI
job with DuckLake. Retain an ADR or research plan only when it explains a still
relevant architectural decision, and label it historical.

### Shared-code rule

Before deleting a helper or dependency, search every caller. Keep it if a
supported path still needs it. Remove it from the same slice when all remaining
callers are removed. This rule applies in particular to `base64`, `hmac`,
`sha2`, object-store helpers, TLS code, subject templates, secret handling, and
connector failure types.

### Acceptance criteria

- [ ] `connectors.toml` contains the native outbox, PostgreSQL inbox, NATS,
  Kafka, webhook, and clearly separate diagnostic output entries only.
- [ ] Source and sink factories contain no removed type.
- [ ] `wire_format::from_config` contains only native and CloudEvents formats
  and rejects all other values.
- [ ] No removed connector module or connector-only helper remains compiled.
- [ ] No removed connector dependency remains in normal or dev dependencies.
- [ ] No test or CI job claims evidence for a removed connector.
- [ ] All four supported destinations retain their protocol and public-API
  evidence.

## 9. SURF-4: Remove `experimental-full`

### Objective

Make every build and release profile an intentional production or test profile.

### Implementation steps

1. Delete `experimental-full` from the generated feature profile block.
2. Update `scripts/generate_connector_surface.py` so it generates only approved
   profiles and rejects profiles containing removed features.
3. Retain `core` and `core-kafka`. Include required security features in those
   profiles instead of relying on an experimental image.
4. Retain `test-failpoints` only as internal crash-test instrumentation.
5. Remove `kms`, cloud KMS aliases, and other empty compatibility features when
   no retained code uses them. Keep `kms-local` only if the supported
   LocalKeyFile path remains.
6. Replace `experimental-full` commands in `justfile`, CI, and
   `tests/required-tests.toml` with the smallest supported profile matrix that
   covers `core` and `core-kafka`.
7. Delete the experimental container build, manifest merge, image tags, digest
   artifacts, and release dependencies from `.github/workflows/release.yml`.
8. Remove `latest-experimental` from README installation instructions and all
   current deployment docs.
9. Ensure the final release job cannot accept an arbitrary `CARGO_FEATURES`
   value outside the approved profile list.

Do not replace `experimental-full` with another all-features profile. Tests
compile the profiles that users can actually install.

### Acceptance criteria

- [ ] `experimental-full` does not occur in current code, build, CI, release,
  package, deployment, or active documentation files. Historical changelog,
  migration, ADR, and research records may retain the name.
- [ ] `cargo build -p pg-tide-relay --no-default-features --features core`
  succeeds.
- [ ] `cargo build -p pg-tide-relay --no-default-features --features core-kafka`
  succeeds.
- [ ] CI tests both supported profiles and no removed combination.
- [ ] The release workflow publishes no experimental image or tag.
- [ ] Production images contain no Labs or removed dependency.

## 10. SURF-5: Simplify configuration and SQL boundaries

### Objective

Reject removed configuration before a worker polls messages, stop SQL APIs from
storing new unsupported configurations, and preserve existing user data during
upgrade.

### Stable error contract

Add one error code:

```text
PGTIDE_CONFIG_UNSUPPORTED_SURFACE
```

The error payload or message must include:

- the removed source, sink, wire format, command, or feature;
- `last_version=0.48.0`;
- a supported alternative;
- a Labs URL only when SURF-2 completed an extraction.

Use `PgTideError` in `pg-tide-ext/src/error.rs` for SQL-facing validation and a
specific `RelayError` variant for relay and CLI paths. Convert errors at the SQL
boundary with `pgrx::error!()`. Do not encode the stable error as an arbitrary
substring of `InvalidConfig`.

### Runtime configuration

1. Make runtime parsing use the retained source and sink descriptors. Remove
   the current broader acceptance path.
2. Replace the unknown-wire-format fallback with explicit rejection. Only an
   absent `wire_format` defaults to `native`.
3. Remove connector field bags and schema branches used only by removed types.
4. Reject unknown and removed keys. Never ignore them during TOML, JSON, or
   catalog parsing.
5. Preserve the frozen `pg_outbox` alias behavior and mark it deprecated.
6. Regenerate `schemas/pipeline-config-v1.schema.json` and fixtures only for
   reviewed disposition changes.
7. Add table-driven tests covering at least one removed value from each family,
   an unknown value, both supported formats, all supported sinks, and the
   diagnostic output path.

The disposition file is the source for last-version and replacement metadata.
Extend the existing connector generator or checker to emit the small static
lookup used by Rust. Do not add a runtime JSON loader or a second connector
registry.

### SQL configuration boundary

Update `tide.relay_set_outbox_v2` so it accepts only the native source and the
retained sink types. Remove `source_mode = 'pg_trickle'`. Validate the sink
before writing to `tide.relay_outbox_config`.

Retire `tide.relay_set_inbox_v2` because inbound and reverse pipelines are
outside the v1 scope. Remove fan-in and managed-backfill SQL functions. Remove
tenant provisioning helpers only when SURF-1 classifies them outside the core
authorization path. Keep any internal tenant isolation needed by supported
pipelines.

Treat each public function removal as an explicit pre-v1 contract subtraction.
Update SQL reference docs and the contract manifest in the same pull request.

### Upgrade migration

Add `sql/pg_tide--0.48.0--0.49.0.sql` and include it in the pgrx migration chain
and relay migration test.

The migration must fail closed before discarding configuration or state:

1. Detect enabled catalog rows that use a removed source, sink, wire format, or
   orchestration mode.
2. Abort the upgrade with `PGTIDE_CONFIG_UNSUPPORTED_SURFACE` and list the
   affected pipeline names when such rows exist.
3. Direct the operator to the existing `pg-tide migrate-config` workflow and
   the v0.49.0 migration guide.
4. Require the operator to export and then disable, replace, or delete each
   affected pipeline before retrying the upgrade.
5. Drop feature-specific tables, functions, views, and triggers only after
   proving that their state tables are empty.
6. Preserve disabled generic catalog rows when dropping them would lose user
   configuration. The v0.49.0 relay must leave those rows disabled and report
   the stable unsupported-surface error if an operator tries to enable them.
7. Make fresh install and sequential upgrade produce the same final schema.

Update the existing `migrate-config` command rather than adding a second
migration CLI. Its check mode must inventory removed values without mutation.
Its write mode may rewrite only mappings documented in the migration guide,
such as `pg_outbox` to `inbox`; it must not guess replacements for different
protocols.

### Acceptance criteria

- [ ] Removed and unknown values fail before catalog mutation or message poll.
- [ ] The stable error identifies the item, last version, and alternative.
- [ ] Missing `wire_format` still selects native; an unknown value never does.
- [ ] Existing unsupported enabled pipelines block upgrade without data loss.
- [ ] Empty feature-specific catalogs are removed from the v0.49.0 final schema.
- [ ] Fresh install and v0.48.0 upgrade produce the same functions, tables,
  views, indexes, constraints, and privileges.
- [ ] Public SQL changes use `#[pg_extern(schema = "tide")]`, short SPI calls,
  contextual `PgTideError` variants, and no `unwrap()` or `panic!()`.

## 11. SURF-6: Simplify relay and extension internals

### Objective

Delete generic machinery whose only reason to exist was removed surface. Avoid
a broad rewrite of stable supported delivery code.

### Relay cleanup targets

- remove deleted modules from `source/mod.rs`, `sink/mod.rs`,
  `wire_format/mod.rs`, `cmd/mod.rs`, and `lib.rs`;
- reduce the source factory to the canonical outbox source;
- reduce the sink factory to PostgreSQL inbox, NATS, Kafka, webhook, and
  diagnostic output;
- delete object-store builders and optional dependency adapters with no caller;
- remove direction combinations and reverse-pipeline branches;
- remove DuckLake, backfill, and DAG commands and dispatch;
- remove schema registry, arbitrary routing, JMESPath, and specialized telemetry
  modules when no supported caller remains;
- remove metrics and labels unique to deleted features without renaming core v1
  metrics;
- delete test helpers used only by removed integrations.

Keep the existing `Source` and `Sink` traits because the supported product has
multiple sink implementations and tests use the delivery boundary. Keep the
generated connector descriptors because configuration, capability checks, and
documentation already share them. Do not add factories or traits to replace
deleted match arms.

### Extension cleanup targets

- remove the fan-in and managed-backfill Rust modules and exports;
- remove public reverse relay creation after the migration guard exists;
- remove final-state SQL catalogs and helpers owned only by deleted features;
- retain canonical outbox, inbox, relay lifecycle, retention, offset, and HA
  state used by supported workflows;
- retain historical migration files unchanged.

### Code-quality checks

After each cleanup slice:

1. Search for every removed identifier in Rust, SQL, TOML, YAML, JSON, and
   current Markdown.
2. Run `cargo tree` for both supported profiles and verify that removed direct
   and transitive dependency families are absent.
3. Run `just fmt` and `just lint` with zero warnings.
4. Run `just test-unit` after every SQL-facing or runtime change.
5. Run the focused supported connector tests affected by the slice.

### Acceptance criteria

- [ ] No branch, module, adapter, or helper remains solely for a removed item.
- [ ] Stable core delivery code changes only where a removed branch shared its
  function.
- [ ] Core metric names, labels, health behavior, and CLI JSON envelopes remain
  compatible.
- [ ] The workspace has no unreachable feature-gated code for deleted features.
- [ ] Formatting and lint pass with zero warnings.

## 16. Upgrade, rollback, and failure handling

### 16.1 User configuration safety

Before upgrade, the operator runs the migration check and exports every
configuration that uses removed surface. The upgrade refuses to proceed while
an enabled removed pipeline exists or while a feature-specific state table
contains data that the migration would drop.

The migration guide must distinguish three actions:

- **replace:** change the pipeline to a supported destination and validate it;
- **disable and retain:** preserve a generic catalog row for later manual
  recovery, but prevent the v0.49.0 relay from running it;
- **delete after export:** remove feature-specific configuration or state only
  after the operator verifies the export.

Do not silently translate one protocol into another. Do not silently delete
DLQ, checkpoint, or replay state shared with supported pipelines.

### 16.2 Code rollback

Each connector-family pull request must revert independently before REL-1. A
revert restores its registry row, code, dependency, tests, and docs together.
Do not restore only a factory arm or feature flag.

After a database has upgraded to v0.49.0, use the documented v0.48.0 rollback
procedure only if the v0.49.0 migration supplies a tested down migration or the
operator restores the pre-upgrade backup. Do not claim binary-only rollback
when SQL objects were dropped.

### 16.3 Failure rules

- If a supported workflow regresses, stop that removal slice and restore the
  shared code until the dependency is understood.
- If the surface checker produces a false positive, fix its narrow parser or
  disposition data. Do not add a broad directory exclusion.
- If dependency or artifact size does not decrease, identify the retained path
  that owns the dependency before changing the acceptance record.
- If an external Labs extraction stalls, delete from main after the preservation
  tag exists.
- If fresh and upgraded schemas differ, v0.49.0 remains open.
- If a removed configuration can still reach a worker, v0.49.0 remains open.
