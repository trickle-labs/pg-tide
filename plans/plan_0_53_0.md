# pg_tide v0.53.0 implementation plan

> **Status:** Proposed
> **Release theme:** Performance, Capacity, and Long-Run Stability
> **Source:** [pg_tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.52.0 and current `main`
> **Scope rule:** Extend the existing v0.43 operational benchmark framework into
> the versioned v1 performance contract. Measure before optimizing. Do not add a
> second benchmark runner, promise hardware-independent results, or tune removed
> experimental features.

## 1. Release outcome

v0.53.0 is complete when an operator or release reviewer can start from the
exact release commit and prove these claims:

1. Every required performance and resource metric has a reviewed v1 budget.
2. A reference result identifies one reproducible environment and rejects
   results from an incomparable environment.
3. Every named operational profile applies its stated load or failure pattern.
4. Repeated runs distinguish measurement noise, improvement, actionable
   regression, invalid environment, and missing samples.
5. A sustained run detects unbounded memory, task, connection, file descriptor,
   database storage, temporary file, log, or metric-series growth.
6. The public SQL to real relay to real destination path stays correct while
   the benchmark measures throughput, latency, and resource cost.
7. A 24-hour qualification soak passes with outages, restart, HA transfer,
   retries, DLQ traffic, cleanup, and supported configuration reload.
8. The release-readiness workflow can run a 72-hour soak against immutable
   candidate artifacts without rebuilding them from the checkout.
9. Every optimization has a measured before result, a measured after result,
   a correctness regression test, and a local rollback path.
10. The capacity guide turns measured values into conservative sizing examples
    without presenting the reference machine as a universal guarantee.

The release covers PostgreSQL 18, the public `tide.*` SQL API, the canonical
outbox source, and the four supported destinations:

- PostgreSQL inbox;
- NATS JetStream;
- Apache Kafka;
- HTTPS webhook.

Criterion benchmarks and the direct PostgreSQL insert microbenchmark remain
developer tools. They do not count as operational capacity evidence.

Reuse these existing sources of truth:

- `connectors.toml` defines the supported destination boundary.
- `schemas/v1-contract-manifest.toml` defines frozen public contracts.
- `schemas/lifecycle-compatibility-v1.json` defines adjacent version behavior.
- `tests/required-tests.toml` defines blocking test execution and evidence.
- `benchmarks/operational/` contains the current operational runner contract.
- `release-evidence/` binds results to a release commit and artifact digests.

Do not add another connector registry, performance service, result database,
test manifest, or release orchestrator.

## 2. Preconditions and scope guard

### 2.1 Release preconditions

Before the first implementation pull request:

1. Confirm that the v0.52.0 tag resolves to the release commit on `main`.
2. Confirm that every v0.52.0 exit criterion passes on `main`.
3. Reconcile `release-evidence/v0.52.0-index.json`. It is still `pending` in
   the planning starting point and cannot remain pending when v0.53 work starts.
4. Run `just check-required-tests`, `just check-v1-contracts`,
   `just check-v1-surface`, `just check-lifecycle-contract`, and
   `just check-operational-budgets`.
5. Run the current scheduled operational matrix three times on the reference
   runner. Retain the raw results as before-change evidence, even if the current
   checker rejects or misclassifies them.
6. Record the current self-hosted runner hardware, operating system,
   PostgreSQL configuration, service versions, Rust version, build flags, and
   network topology.
7. Record the current v0.43 budget file, null baseline, workflow definition,
   and capacity guide by digest.
8. Confirm that no performance or soak result has a retry, skip, or quarantine
   allowance in `tests/required-tests.toml` or `tests/flake-registry.toml`.

If the v0.52.0 gate fails, stop. Performance evidence must start from the exact
security and supply-chain baseline that v0.52.0 promises.

### 2.2 Frozen contract boundary

The v0.47.0 freeze still covers:

- public `tide.*` SQL signatures and behavior;
- pipeline JSON fields and validation;
- stable metric names and labels;
- health behavior;
- CLI JSON fields and exit codes;
- native and CloudEvents envelopes;
- delivery, retry, checkpoint, replay, and DLQ semantics;
- the four supported destination contracts.

v0.53.0 may add additive bounded telemetry, benchmark-only inputs, versioned
budget files, scheduled jobs, release evidence, and capacity documentation.
It must not weaken a correctness or security control to meet a performance
budget. An additive runtime metric must use fixed labels and update the metrics
contract, reference, dashboard checks, and cardinality budget.

### 2.3 Explicit non-goals

Do not include the following work:

- a new source, sink, connector, or wire format;
- PostgreSQL major-version expansion;
- performance work for removed, preview, or experimental features;
- a replacement for Criterion;
- a hosted benchmark-results service;
- a custom statistics dependency when Python's standard library is sufficient;
- a custom allocator or allocator replacement solely to measure heap use;
- a `tokio-console` dependency solely to count tasks;
- automatic hardware tuning;
- universal messages-per-second claims;
- architecture rewrites before a local change fails to meet a committed budget;
- hiding durability, security, or correctness cost from a benchmark;
- broad operator-documentation reorganization assigned to v0.54.0;
- production pilots or independent release reviews assigned to v0.55.0;
- execution of the final 72-hour v1 candidate soak before candidate artifacts
  exist;
- tagging or publishing v0.53.0 as part of implementation.

Fix correctness, security, or resource-leak defects that a required profile
exposes. Record unrelated findings for their planned release.

## 3. Canonical performance contract

### 3.1 One contract, not two

Create the roadmap-required files:

```text
benchmarks/budgets-v1.toml
benchmarks/reference-environment.md
```

Retain `benchmarks/operational/README.md` as the procedure for running profiles
and interpreting results. Store the reviewed aggregate baseline in:

```text
benchmarks/operational/baseline-v1.json
```

Rename these v0.43 files as superseded history in the same pull request that
enables the v1 contract:

```text
benchmarks/operational/budgets-v0.43.toml
benchmarks/operational/baseline-v0.43.json
```

Do not merge a state where both old and new files claim authority. Mark the
renamed files as historical, and keep the v0.43 files authoritative until the
v1 measurements and budgets are complete. Switch the checker, Just recipes,
CI, required-test manifest, `benchmarks/operational/README.md`, ADR-013, the
capacity guide, and release evidence atomically.

`baseline-v1.json` must contain one entry per canonical profile instance. A
profile-instance key includes the scenario, destination set, payload variant,
pipeline count, batch size, poll interval, and any supported configuration that
changes the workload. For example, `relay-large` 16 KiB and 64 KiB are separate
instances, as are pipeline density 1, 10, and 50. Each entry records the sample
count, median, median absolute deviation, raw-result bundle digest, environment
fingerprint, commit, artifact digests, and collection date. Raw time series
remain CI or release artifacts. Do not commit multi-gigabyte soak logs to the
source tree.

### 3.2 Performance invariants

Every workstream must preserve these invariants:

1. Every event enters through `tide.outbox_publish()` in an application
   transaction.
2. Every operational delivery profile starts the real `pg-tide` binary.
3. Every destination profile uses a real supported service or the same
   controlled protocol endpoint used by its black-box integration test.
4. A result is complete only when published, acknowledged, and checkpointed
   identities reconcile according to the v0.50.0 delivery model.
5. The runner never substitutes a direct table insert for the public API under
   measurement.
6. Warm-up data does not enter the measured sample.
7. A result names the exact profile, environment, commit, dirty state, binary
   digest, extension package digest, service image digests, and configuration.
8. A missing probe produces `missing_sample`. It never produces zero.
9. An unreadable process or PostgreSQL statistic invalidates the affected run.
10. An incomparable environment produces `invalid_environment`. It cannot
    update a baseline.
11. An expected backlog or DLQ increase during a fault phase is not a leak.
    The recovery phase must drain it within its budget and return to a bounded
    steady-state slope.
12. A budget update requires raw before and after artifacts, a reason, capacity
    guide impact, and reviewer approval.
13. A baseline update cannot turn a failed result into a pass without an
    explicit budget review.
14. Benchmark logs, payloads, and evidence obey the v0.52.0 secret-redaction
    contract.
15. No result from a dirty checkout can become release evidence.

### 3.3 Result and evidence model

Use three result layers:

| Layer | Location | Purpose |
|---|---|---|
| Raw run | `target/operational-benchmarks/<profile>/<run-id>.json` | One profile repetition with samples, correctness counts, and environment details |
| Comparison report | `target/operational-benchmarks/<profile>/comparison.json` | Aggregated classification against `baseline-v1.json` and `budgets-v1.toml` |
| Release record | `release-evidence/v0.53.0-performance.json` | Static policy and required-result index for the 24-hour qualification and 72-hour workflow readiness |

Add `release-evidence/v0.53.0-index.json` as the v0.53 release index. It links
the performance record and inherits the v0.50 correctness, v0.51 lifecycle,
and v0.52 security evidence by path and digest. It does not copy those results.
Exact run status and dynamic artifact digests belong in immutable required-test
and qualification artifacts keyed by commit. Do not create a self-referential
commit by writing its own hash into a tracked file.

Every raw result must include:

- schema version and profile name;
- profile parameters and phase timeline;
- environment fingerprint and captured fields;
- commit, dirty state, binary digest, extension package digest, and image
  digests;
- warm-up, measurement duration, sample interval, and repetition number;
- published, delivered, acknowledged, deduplicated, DLQ, and checkpoint
  identities or counts;
- metric values and raw resource samples;
- injected fault times and observed recovery times;
- cleanup and shutdown outcome;
- sanitized stdout and stderr byte counts;
- start and completion timestamps.

The comparison report must include one classification per metric, an overall
classification, the exact budget entry used, the sample paths and digests, and
the environment comparison result.

## 6. PERF-1: Commit versioned operational budgets

### 6.1 Objective

Make `benchmarks/budgets-v1.toml` the reviewed machine-readable performance
and resource contract for the supported v1 product.

### 6.2 Budget schema

The file must define:

- one schema version;
- one reference-environment schema version;
- required scenario names and canonical profile-instance keys;
- required metrics for each profile instance;
- unit and better direction for each metric;
- an absolute minimum or maximum;
- the allowed relative regression by CI tier;
- a non-zero absolute noise floor and optional percentage noise floor;
- the minimum sample count;
- the steady-state phases used for growth calculations;
- the owner and rationale for each absolute budget.

Keep profile-instance thresholds in the same file. Do not create one TOML file
per scenario or variant. The checker constructs the canonical instance key from
the raw result and selects that table.

Use three comparison tiers:

| Tier | Use | Samples | Policy |
|---|---|---:|---|
| `pr` | Fast microbenchmark signal and contract fixtures | 1 or more | Wider relative threshold; never updates a baseline |
| `scheduled` | Reference operational profiles | At least 3 | Median and spread comparison against the reviewed baseline |
| `release` | 24-hour and candidate qualification | At least 3 for repeated profiles, one long time series for a soak | Strict absolute budgets and no missing required probe |

A PR result with one sample may report a signal, but it cannot support a
capacity claim or baseline update.

Use stable metric names in the result schema. Keep an existing v0.43 name when
its meaning remains correct. Rename a metric only when the current name hides a
different measurement.

Use the formal metrics above to enforce these phase expectations:

| Growth metric | Stable phase expectation |
|---|---|
| Outbox rows and heap bytes | Flat after backlog recovery and cleanup |
| Outbox index bytes | Flat after backlog recovery and maintenance allowance |
| Unresolved DLQ rows | Flat outside the deliberate DLQ injection phase; zero after replay when the profile requires a full drain |
| Checkpoint rows | Bounded by the configured pipeline and relay-group count |
| Temporary files and bytes | No monotonic growth after the query or cleanup phase ends |
| Relay log bytes | Rate remains below the profile budget; no retry-loop acceleration |
| Prometheus series | Bounded by the fixed metric schema and configured pipeline count |
| PostgreSQL connections | Returns to the configured pool bound after a fault |
| Relay file descriptors | Returns to the post-warm-up band after a fault |
| Relay async tasks | Returns to the expected owned-task inventory after restart or reload |

### 6.4 Budget-setting procedure

Set each absolute budget only after the profile emits a truthful measurement:

1. Run at least three repetitions on the validated reference environment.
2. Verify correctness counts and sample completeness before reading speed.
3. Calculate the median and median absolute deviation.
4. Identify the operator requirement that the metric protects.
5. Set a rounded absolute budget above measured noise but inside that
   operational requirement.
6. Record the rationale and raw result bundle digest.
7. Review the corresponding capacity guide statement.
8. Approve the budget independently from the person who changed the runner.

Do not generate budget values automatically from the newest baseline. Do not
fill a missing probe with zero or copy an unrelated profile's threshold.

Existing v0.43 thresholds may carry forward only when the measurement meaning,
profile, environment, and operator requirement still match. Re-measure them
before approval.

### 6.5 Acceptance criteria

- [ ] `benchmarks/budgets-v1.toml` passes schema validation.
- [ ] Every required profile instance has an explicit metric set.
- [ ] Every required metric has a unit, direction, absolute bound, comparison
      rule, owner, and rationale.
- [ ] `baseline-v1.json` contains no null, `TBD`, or pending value.
- [ ] Every baseline profile instance has enough comparable samples.
- [ ] Every baseline profile instance links a raw bundle digest.
- [ ] Renamed v0.43 budget and baseline files are marked historical and no
      longer claim authority.
- [ ] A budget change cannot bypass evidence and review checks.

## 7. PERF-2: Standardize the reference environment

### 7.1 Objective

Make a result reproducible enough to compare with the committed baseline and
strict enough to reject a different machine or configuration.

### 7.2 Reference document

Create `benchmarks/reference-environment.md` with the exact accepted values
from the self-hosted reference runner. Do not invent hardware values in code or
copy a hosted-runner description.

Record:

- CPU vendor, model, architecture, physical cores, logical cores, and enabled
  frequency policy;
- total memory and swap policy;
- storage device type, filesystem, mount options, capacity, and free-space
  floor;
- operating system, kernel, and cgroup version;
- PostgreSQL package version, extension package digest, enabled extensions,
  locale, data checksums, and relevant `SHOW ALL` digest;
- pinned NATS and Kafka image digests, plus the controlled webhook binary or
  source digest;
- PostgreSQL inbox target version and configuration;
- loopback, container bridge, and any network shaping used by a profile;
- Rust toolchain from `rust-toolchain.toml`;
- locked build command, profile, features, and compiler flags;
- relay CLI flags, pool size, batch size, poll interval, and log level;
- dataset seed, event-size distribution, compressibility, headers, and metadata;
- warm-up duration, measurement duration, sample interval, and repetitions;
- cleanup between runs;
- scheduled raw-result retention and release-result retention;
- the owner of the runner and procedure for replacing it.

Document the scheduled raw-artifact retention from repository policy and set
the same `retention-days` value on workflow uploads. Keep release qualification
summaries and bundle digests for the supported life of the release. Name the
immutable storage location for raw 24-hour and 72-hour bundles. Do not put
those bundles in Git.

### 7.3 Environment fingerprint

Extend the existing raw result environment object. At minimum, capture:

- a schema version;
- stable runner identifier;
- CPU model and core counts;
- memory bytes;
- kernel and operating system;
- filesystem and storage identifiers;
- PostgreSQL full version and settings digest;
- extension version and package digest;
- service image or controlled-endpoint code digests;
- Rust version;
- relay binary digest and build profile;
- payload distribution;
- pipeline count, batch size, poll interval, and destination set;
- network-shaping parameters;
- warm-up, duration, and sample interval.

The checker compares fields declared `identity` in the v1 budget contract.
Profile parameters may differ only when the selected profile table declares
them. A large-message result must compare with the large-message baseline, not
with `relay-core`.

The reference preflight must also prove that:

- `pg_stat_statements` is installed, preloaded, and readable by the benchmark
  role;
- `pgstattuple` is installed and the required functions are executable by the
  benchmark role;
- the benchmark and relay PostgreSQL URLs set a unique run-scoped
  `application_name` prefix;
- the sampler can read the relay and complete PostgreSQL process trees from the
  host PID namespace;
- the harness assigns a known metrics port and can scrape relay readiness and
  `/metrics` before load starts.

Discover the PostgreSQL process tree from `pg_backend_pid()` and the verified
parent postmaster process, then include its descendants. If PostgreSQL runs in
a container, run the sampler where the host PID mapping is visible and record
that mapping. Do not claim PostgreSQL CPU from one backend process.

### 7.4 Automation

Keep environment validation in `scripts/check_operational_budgets.py`. Add a
mode that validates a captured environment against the reference contract
before the expensive run begins. Do not add a second environment checker.

Update `.github/workflows/performance.yml` to:

1. check the runner label and free-space floor;
2. capture the environment;
3. reject a fingerprint mismatch;
4. verify candidate or locally built artifacts by digest;
5. run the profile;
6. capture the environment again;
7. invalidate the result if a stable field changed during the run.

Pin service images by digest. Record the controlled webhook code digest. Remove
the current `nats:latest` start and the `"nats_version": "latest"` result
value. Start the relay on a known run-scoped metrics address and wait for its
readiness endpoint instead of using an undiscoverable `127.0.0.1:0` address.

### 7.5 Acceptance criteria

### 9.1 Objective


Use Python `statistics.median` and a small local median absolute deviation
function. Do not add NumPy, SciPy, pandas, or a benchmark service.

### 9.3 Comparison order

For each profile:

1. Validate the budget and baseline schema.
2. Validate every raw result schema and correctness status.
3. Require the tier's minimum sample count.
4. Require identical comparable environment fields.
5. Require the profile's full metric set.
6. Calculate the current median and median absolute deviation.
7. Compare the median with the absolute budget.
8. Compare the directional change with the baseline median.
9. Calculate the noise band as the largest of the metric's non-zero absolute
   noise floor, three baseline median absolute deviations, and three current
   median absolute deviations.
10. Calculate the tier regression allowance from the baseline median and the
    tier percentage. For a zero or near-zero baseline, use the metric's
    absolute regression allowance and do not calculate a percentage.
11. Compare a worsening directional delta with the larger of the noise band
    and the tier regression allowance.
12. Emit one classification and reason.

Use these classifications:

| Classification | Meaning | Exit behavior |
|---|---|---|
| `noise` | The directional change stays inside the accepted noise band and absolute budget | Pass |
| `improvement` | The median improves beyond noise and remains correct | Pass |
| `actionable_regression` | The result violates an absolute budget or worsens beyond both noise and the tier threshold | Fail |
| `invalid_environment` | A comparable environment, profile, artifact, or stable field does not match | Fail; no performance claim |
| `missing_sample` | Too few runs, a required metric is absent, or a probe failed | Fail |

An absolute budget failure is always actionable, even when baseline variance
is high. A statistically visible slowdown inside the absolute budget still
fails when it exceeds the tier's relative threshold.

`noise` is a pass only after the absolute budget, correctness, environment, and
sample-completeness checks pass. Treat one 24-hour or 72-hour time series as a
single long-run qualification with absolute, high-water, rate, and slope gates.
Do not pretend that it is three repeated samples. Run the shorter reference
profile instances at least three times separately.

## 16. Failure handling during implementation

### 16.1 Invalid measurements

Classify and stop a run when:

- the environment fingerprint differs;
- the checkout is dirty;
- an artifact digest differs;
- a service version or digest differs;
- a required probe fails;
- correctness identities do not reconcile;
- the system clock moves in a way that invalidates wall-clock timestamps;
- the sample process changes unexpectedly;
- disk free space crosses the reference floor;
- a service or evidence upload fails.

Keep the raw diagnostics and mark the result non-comparable. Do not merge it
with successful repetitions.

### 16.2 Failed qualifications

A failed 24-hour or 72-hour run is one failed result. Do not resume it from a
checkpoint, retry only the failed phase, or combine the beginning of one run
with the end of another.

After a code, config, dependency, environment, or artifact change:

1. invalidate the old qualification;
2. create new artifact digests;
3. run the environment preflight;
4. restart the full duration;
5. retain the failed bundle for diagnosis.

### 16.3 Resource exhaustion safety

The soak runner must stop before it damages the shared reference environment.
Set hard safety ceilings for disk free space, process memory, connection count,
and log bytes above the committed product budget but below host exhaustion.
Crossing a safety ceiling stops the workload, captures diagnostics, and fails
the run.

Do not turn a host safety ceiling into a product budget. They answer different
questions.

### 16.4 Benchmark-data cleanup

Use unique run IDs for application rows, outboxes, pipelines, subjects, topics,
inboxes, and DLQ entries. Normal completion removes all run-owned state. Failed
runs retain enough state for diagnosis, then use one bounded cleanup procedure
that verifies the exact run ID before deletion.

Never run a broad recursive file cleanup or unscoped database delete from the
benchmark workflow.

## 18. Risks and controls

| Risk | Control |
|---|---|
| Existing scenario labels look more complete than their behavior | Make each profile select one explicit handler and assert its declared phase |
| One null baseline gets replaced with plausible but invented numbers | Accept budgets only after repeated comparable raw results and review |
| Large and density profiles compare with the one-pipeline baseline | Store and select one baseline entry per profile variant |
| A missing `/proc` or PostgreSQL probe becomes zero | Classify the run as missing or invalid and fail |
| Benchmark speed improves by skipping durability work | Reconcile destination identities and checkpoints before accepting metrics |
| Performance work weakens v0.52 security | Run security gates and reject any unverified transport or redaction change |
| A fault phase looks like a resource leak | Tag phases and evaluate bounded growth only in declared steady-state and recovery windows |
| A real leak hides inside expected backlog growth | Require the post-recovery row, storage, memory, connection, task, and descriptor slopes to return to budget |
| Metric task counting creates new cardinality | Use one fixed `kind` label and test the complete allowed value set |
| Relay logs block the child process | Drain stdout and stderr continuously to bounded files and enforce a byte safety ceiling |
| Self-hosted runner drift creates false regressions | Validate the environment before and after each run and reject drift |
| Three noisy samples overstate confidence | Use robust medians, spread, absolute budgets, and stricter release thresholds |
| Baseline updates normalize a regression | Require raw before and after digests, capacity impact, and independent review |
| A 24-hour retry hides instability | Use zero retries and restart the full duration after any change |
| The 72-hour job rebuilds different code | Download and verify immutable candidate artifacts by digest |
| Mixed-destination profile becomes four unrelated benchmarks | Publish one identity set and reconcile four terminal destination sets and checkpoints |
| PostgreSQL CPU sampling misses worker processes | Validate and sample the complete reference process tree |
| Cleanup measurements hide vacuum or index cost | Report heap, indexes, WAL, dead tuples, locks, and rows separately |
| Optimization expands into a rewrite | Require a failed budget, localized evidence, local attempt history, and rollback path |
| Raw soak evidence bloats Git | Commit summaries and digests; retain raw bundles in immutable artifact storage |
| Reference numbers become universal marketing claims | Label them as environment-specific and use conservative examples |
| Version bump creates an unnecessary schema change | Use the minimum adjacent migration unless a measured extension fix requires DDL |
