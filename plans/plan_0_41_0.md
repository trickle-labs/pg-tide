# pg_tide v0.41.0 Implementation Plan

> **Status:** Proposed  
> **Release theme:** Promise Only What We Prove  
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)  
> **Starting point:** v0.40.0 and current `main`  
> **Scope rule:** Make connector maturity, build contents, tests, documentation, and compatibility claims truthful. Do not add a connector or promote one without the evidence required by the roadmap.

---

## 1. Release Outcome

v0.41.0 is complete when a contributor can clone only this repository and obtain the same focused, auditable product surface that the project publishes:

1. `cargo build --workspace` and `cargo test --workspace` work without a sibling `rocklake2` checkout.
2. One root `connectors.toml` records every selectable relay connector, its maturity, owner, build gate, directions, tested versions, documentation, and test evidence.
3. A standard-library-only generator produces the public connector table, compatibility matrix, Cargo build-profile aliases, and connector release checklist from that registry.
4. CI fails when generated output is stale, a runtime connector is absent from the registry, a claimed test file does not exist, a connector lacks an owner, or a production profile includes a connector below `supported` maturity.
5. The normal relay binary and Docker image use the generated `core` profile. They contain only production-supported connectors plus explicitly labeled stdout/file diagnostics.
6. `core-kafka` is available as an explicit build profile. It is not presented as a production artifact unless Kafka satisfies the same `supported` gate.
7. The former “full” build is named and labeled `experimental-full`; no release artifact describes every compiling backend as supported or integration-tested.
8. Test names and CI job names describe what they actually prove. The authoritative NATS public-API test remains the end-to-end proof; direct SDK, emulator, request-shape, and database-only tests use narrower labels.
9. Historical assessments and implementation plans are archived separately from active product documentation and the focused roadmap.
10. The support policy explicitly states the PostgreSQL versions, architectures, deployment modes, connector versions, patch-maintenance window, and experimental-feature terms covered by v0.41.0.
11. PostgreSQL 17 is either added with a maintained test matrix equal to the supported PostgreSQL 18 path, or rejected with a checked-in feasibility report naming the exact blockers.

Compiling a connector is not evidence that it works. A connector with missing production evidence remains `preview` or `experimental`, is excluded from the production image, and appears with its missing evidence in the generated release checklist.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.40.0 is a hard prerequisite

The roadmap forbids starting a release while the previous release gate is incomplete. Before v0.41.0 work begins, confirm every checkbox in [the v0.40.0 plan](./plan_0_40_0.md#19-release-exit-checklist) passes on `main`, including:

- public API outbox to NATS JetStream end-to-end delivery;
- restart recovery and stable duplicate identity;
- fail-closed ACL behavior;
- canonical shared-table polling and monotonic offsets;
- executable Quick Start SQL;
- real v0.39.0 to v0.40.0 upgrade parity.

If a v0.40.0 gate is red, repair v0.40.0 first. Do not relabel an incomplete v0.40.0 behavior as preview to make v0.41.0 start.

### 2.2 Maturity words have one meaning

Use exactly these registry values:

| Maturity | Meaning | Public claim allowed |
|---|---|---|
| `supported` | Meets every item in the roadmap’s definition of production-supported and has current evidence paths in the registry | Production-supported; eligible for the normal image |
| `preview` | Real user workflow exists and has meaningful integration coverage, but at least one production-supported requirement is missing | Evaluation or pilot use; not production-supported |
| `experimental` | Compiles, is partially implemented, is a protocol adapter without a complete workflow, or has only unit/contract evidence | Evaluation only; may change or be removed |

`stdout`, file output, and stdin are diagnostics, not production integrations. Record them with `kind = "diagnostic"`; they may be present in `core`, but generated prose must not count them as supported connectors.

Do not introduce a second phrase such as “conditionally supported.” If a connector does not meet the production checklist, it is not `supported`.

### 2.3 Registry scope and authority

`connectors.toml` is authoritative for release-facing connector facts only. It does not become a runtime plugin registry and the relay does not parse it at startup.

The registry must account for:

- every `source_type` accepted by `build_source()`;
- every `sink_type` accepted by `build_sink()`;
- every feature-gated connector module under `pg-tide-relay/src/source/` and `pg-tide-relay/src/sink/`;
- every connector page linked from the active documentation;
- disabled or unavailable surfaces that are still documented, such as fan-in or an unregistered DuckLake source;
- diagnostic adapters separately from production connectors.

README-only names without a selectable implementation are not connectors. Remove claims for Twilio, SendGrid, Firebase, or other webhook use cases unless the active docs describe them accurately as generic webhook destinations. Fivetran must be described as a webhook/signature flavor or archived; the relay does not currently accept `source_type = "fivetran"` or `sink_type = "fivetran"`.

### 2.4 Registry format

Use a flat `[[connector]]` table per user-facing connector. Keep the schema explicit so review does not depend on generator behavior. The minimum record is:

```toml
schema_version = 1

[[connector]]
id = "nats"
name = "NATS JetStream"
kind = "connector" # connector | diagnostic | compatibility
maturity = "preview" # supported | preview | experimental
owner = "@verified-github-handle"
security_contact = "@verified-github-handle"
cargo_feature = "nats" # omitted for built-in behavior
source_types = ["nats"]
sink_types = ["nats"]
default_build = false
tested_versions = ["<version or version range actually exercised>"]
docs = ["docs/src/sinks/nats.md", "docs/src/sources/nats.md"]
contract_tests = ["pg-tide-relay/tests/nats_test.rs"]
integration_tests = []
e2e_tests = ["pg-tide-relay/tests/public_api_outbox_to_nats_e2e.rs"]
failure_before_publish_tests = []
failure_after_publish_tests = []
restart_tests = ["pg-tide-relay/tests/public_api_outbox_to_nats_e2e.rs"]
duplicate_tests = ["pg-tide-relay/tests/public_api_outbox_to_nats_e2e.rs"]
auth_tests = []
tls_tests = []
redaction_tests = []
metrics_evidence = ["pg-tide-relay/src/metrics.rs"]
runbooks = []
upgrade_tests = []
```

The exact NATS values above are illustrative until the evidence audit is complete. The generator must reject a `supported` row if any production-supported evidence category is empty. A path may satisfy multiple categories, but every path must exist and the generated checklist must show which categories it supports.

All connectors require a real `owner`. `TBD`, team-shaped placeholders, and nonexistent handles fail validation. `security_contact` is mandatory for `supported` connectors.

### 2.5 Connector inventory to reconcile

The audit starts from the actual runtime factories, not the README count.

| Group | Runtime/config surface to account for |
|---|---|
| PostgreSQL core | native `outbox`; local `inbox`; remote `pg_outbox`/PostgreSQL inbox |
| Core candidates | NATS, webhook, Kafka |
| Compatibility | `pg_trickle_outbox` |
| Diagnostics | stdin, stdout, file |
| Messaging | Redis, SQS, RabbitMQ, Pub/Sub, Kinesis, Service Bus, Event Hubs, MQTT |
| Data/search | Elasticsearch, object storage, ClickHouse, MongoDB, BigQuery, Snowflake, Delta, Iceberg, DuckLake, RockLake, Arrow Flight |
| Notifications | Slack, Discord, PagerDuty |
| Connector protocols | Singer, Airbyte |
| Disabled/partial | fan-in, DuckLake reverse source registration, WAL logical-replication source |

This table is an inventory, not a maturity assignment. The implementation audit sets maturity from evidence. Native PostgreSQL outbox behavior may be recorded as a product capability rather than an external connector, but it must still appear in the generated matrix because every relay pipeline depends on a source.

### 2.6 Build profiles are availability bundles, not proof

Generate these Cargo feature aliases in a bounded marker block in `pg-tide-relay/Cargo.toml`:

```toml
default = ["core"]
core = [/* generated supported connector gates + diagnostics */]
core-kafka = ["core", "kafka"]
experimental-full = [/* generated complete set of non-profile features */]
```

Rules:

- `core` contains only registry rows with `default_build = true` and `maturity = "supported"`, plus diagnostics.
- The intended core candidates are PostgreSQL inbox, NATS, and webhook. A candidate that lacks evidence is excluded rather than promoted by intent.
- Native outbox to NATS is the minimum useful production profile established by v0.40.0. If its audit exposes a bounded missing test or document, close that evidence gap in v0.41.0. If it exposes missing connector behavior, do not publish an empty or misleading production profile: the release remains gated until the scope is explicitly revised.
- `core-kafka` is an explicit opt-in bundle. Generated docs show its maturity as the lowest maturity of its members. Do not publish it as production-supported while Kafka is below `supported`.
- `experimental-full` contains every feature that currently compiles, including wire formats, observability options, KMS/WAL groundwork, and experimental connectors. It is never the normal binary or image.
- Production release jobs must not use `--all-features`.
- CI may compile `experimental-full`, but the job must be named as an experimental compile/test job.

Make existing no-op features truthful where profile containment depends on them. In particular, either make `pg-inbox` gate the local and remote PostgreSQL inbox sink modules/factory arms or remove the feature and document that the behavior is built in. Do not leave a feature that claims to control code while controlling nothing. Apply the same rule to `stdout` if it remains a named profile member.

### 2.7 RockLake dependency disposition

Use a pinned Git revision for `rocklake-testkit` as the first-choice minimal fix:

```toml
rocklake-testkit = {
  git = "https://github.com/trickle-labs/rocklake.git",
  rev = "<immutable commit for the tested v0.27.14 source>"
}
```

Do not pin only a branch or mutable tag. Update `Cargo.lock` and prove `cargo package` still succeeds. If Cargo packaging rejects the Git dev-dependency, move the RockLake tests to a small, workspace-excluded external test crate with the pinned Git dependency. Do not vendor the whole RockLake repository and do not retain any `../../rocklake2` path.

### 2.8 Test taxonomy

Publish and use this vocabulary:

| Tier | Required boundary |
|---|---|
| Unit | One function/module; no external process required |
| Contract | Request, response, serialization, or protocol shape against a local boundary or faithful stub |
| Integration | At least two real components interact through their real protocol |
| End-to-end | Documented public user API through the real coordinator to the final observable result |
| Chaos | A failure is deliberately induced and a safety/recovery invariant is verified |

Rust’s `tests/` directory is a Cargo layout term, not evidence that every test in it is a product integration test. Test names, module comments, CI jobs, README claims, and registry evidence must use the product taxonomy above.

### 2.9 Archive boundary

Keep these active under `plans/` during v0.41.0:

- `pg-tide-roadmap-to-focused-production-grade.md`;
- `plan_0_41_0.md`.

Move completed assessments, superseded roadmaps, and older implementation plans to `docs/archive/plans/`. This includes `plan_0_40_0.md`, every `overall_assessment*`/`overall-assessment*` file, relay CLI phase plans, ecosystem plans, documentation plans, Portage plans, bootstrapping, Riverbank recommendations, and the wire-format implementation plan.

Move the old root `ROADMAP.md` to the archive and replace it with a short current roadmap pointer. Preserve history with `git mv`; update live links rather than copying files or leaving duplicate sources.

### 2.10 PostgreSQL support decision

The supported baseline remains PostgreSQL 18 unless PostgreSQL 17 passes a full feasibility gate. A compile-only result is insufficient.

To support PostgreSQL 17, all of the following must be maintained in CI:

- a `pg17` feature in `pg-tide-ext/Cargo.toml` using the same pinned pgrx release;
- extension compile and clippy on PostgreSQL 17;
- `cargo pgrx test pg17`;
- packaged fresh install and public SQL smoke tests;
- the same core relay workflow used for PostgreSQL 18, including the public NATS path;
- documentation and packaging that do not reduce or skip the PostgreSQL 18 gate.

If any requirement fails or doubles the matrix beyond what maintainers will own, remove the spike changes and publish `docs/src/support/postgresql-17-feasibility.md` with commands, results, blockers, and the exact PostgreSQL 18 dependency. The release passes with an explicit PostgreSQL 18-only policy.

### 2.11 Release versioning

v0.41.0 changes release metadata even if it adds no catalog columns. Add a `0.40.0 -> 0.41.0` extension upgrade script that updates extension comments/version semantics without rewriting user data. Register it in the pgrx fresh-install chain and prove fresh/upgrade parity.

Do not tag, publish, or push release artifacts as part of implementation unless separately requested.

## 4. Workstream A: Make the Workspace Self-Contained

### A.1 Replace the sibling path dependency

In `pg-tide-relay/Cargo.toml`:

1. Replace `rocklake-testkit = { path = "../../rocklake2/..." }` with the immutable Git revision selected in section 2.7.
2. Keep it a dev-dependency used only by `rocklake_test.rs`.
3. Update comments to describe the pinned external test boundary rather than a required sibling layout.
4. Update `Cargo.lock` and record the commit in the RockLake registry evidence.

If the preferred form fails `cargo package`, use the workspace-excluded external test crate fallback. Do not invent an abstraction around the testkit.

### A.2 Remove repository-shape workarounds

Delete the RockLake checkout/move steps from:

- every job in `.github/workflows/ci.yml`;
- release binary and crate-publish jobs in `.github/workflows/release.yml`;
- the Docker build stage.

Remove comments, symlink steps, and historical setup that exist only for `../../rocklake2`. Keep the dedicated RockLake integration job, but let Cargo fetch the pinned revision normally.

### A.3 Add a clean-checkout gate

Add one CI job that starts from a normal `actions/checkout`, installs the documented Rust/pgrx/PostgreSQL prerequisites, and runs:

```bash
cargo build --workspace --locked
cargo test --workspace --locked
cargo package --package pg-tide-relay --locked --allow-dirty
```

The job must not create a sibling directory. Add an explicit assertion that `../rocklake2` does not exist before Cargo runs so a future workaround cannot mask the contract.

If the complete workspace test is too slow, split it across existing CI jobs but retain one aggregate required check whose commands and prerequisites are documented. The roadmap’s clean-checkout contract may not be weakened to `cargo test --no-run`.

## 5. Workstream B: Make Test Claims Truthful

### B.1 Publish the test-level standard

Create `docs/src/support/test-levels.md` with the definitions in section 2.8 and short pg_tide examples:

- NATS sink request/header validation: contract;
- SDK or broker publish/consume without pg_tide: integration;
- public SQL -> coordinator -> NATS consumer: end-to-end;
- killed coordinator after sink acknowledgment with offset invariant: chaos.

Link the standard from `CONTRIBUTING.md`, the generated release checklist, and the support section in `docs/src/SUMMARY.md`.

### B.2 Inventory every test and CI job

Produce a review table during implementation containing:

- test file and test function;
- current name/comment;
- components actually started;
- whether public SQL and the coordinator are used;
- final observable assertion;
- assigned taxonomy tier;
- connector evidence category, if any.

The table may be temporary review material; the durable result is accurate source names/comments and registry evidence. Do not add a permanent test catalog separate from `connectors.toml`.

### B.3 Correct known overstatements

At minimum:

- rename Kinesis, Pub/Sub, MQTT, object-storage, and similar direct SDK/emulator `*_end_to_end_*` functions to `*_transport_integration_*` or `*_protocol_integration_*`;
- describe `wire_format_test.rs` as format contract/round-trip coverage, not product end-to-end coverage;
- describe RockLake’s in-process PG-wire harness as integration coverage, not public API end-to-end delivery;
- keep `public_api_outbox_to_nats_e2e.rs` and its CI job as the authoritative end-to-end path;
- change CI groups named “integration” when they only run configuration/unit/contract tests;
- rename `load_test.rs` and its CI job to the PostgreSQL operation actually measured;
- correct the load threshold prose to match the constant and stop writing `benches/baseline.json` from a test;
- correct `pg-tide-relay/benches/throughput.rs` module comments so serialization, batch construction, template rendering, and parameter construction are called microbenchmarks.

File renames are required only where the filename itself overstates the tier. Function/comment/job renames are enough elsewhere.

### B.4 Remove tautological tests

Delete or replace:

- `test_bigquery_sink_publish_does_not_panic()`;
- `test_snowflake_sink_publish_does_not_panic()`.

Assertions equivalent to `result.is_ok() || result.is_err()` prove nothing. Prefer deletion when existing constructor and request-payload tests already cover the reachable behavior. Add a replacement only if it asserts an observable request, response, or error classification through a faithful local boundary.

### B.5 Reclassify Fivetran evidence

`fivetran_test.rs` tests webhook signature and payload shapes. Rename its module/comments as webhook/Fivetran contract coverage. It must not satisfy a Fivetran connector integration or E2E field in the registry.

Rewrite active Fivetran docs to use the real `webhook` source/config if that workflow exists. Otherwise move those pages to the archive and mark the feature experimental/unavailable in the matrix.

## 6. Workstream C: Connector Registry and Generated Artifacts

### C.1 Add `connectors.toml`

Populate the complete inventory from section 2.5. For each record:

1. Verify every runtime type against the relevant coordinator factory arm.
2. Verify the Cargo feature against `pg-tide-relay/Cargo.toml`; omit it only for truly built-in behavior.
3. Assign an actual owner and, for supported rows, security contact.
4. Link only tests that match the taxonomy after Workstream B.
5. Record connector/protocol versions that CI actually exercises; use `unknown` only for preview/experimental rows and expose that gap in generated output.
6. Set maturity after the evidence fields are complete.
7. Set `default_build = true` only for supported connectors and diagnostics.

The first review should be conservative: missing evidence lowers maturity. Do not add tests merely to preserve a desired tier in this release; full connector promotion is v0.46.0 work.

### C.2 Add one small generator

Create `scripts/generate_connector_surface.py` using only Python’s standard library (`tomllib`, `pathlib`, `re`, and `argparse` are sufficient).

Supported modes:

```text
python3 scripts/generate_connector_surface.py          # rewrite generated sections/files
python3 scripts/generate_connector_surface.py --check  # validate and fail on drift
```

The generator owns only bounded outputs:

- the text between connector markers in `README.md`;
- `docs/src/support/connector-compatibility.md`;
- the marked build-profile block in `pg-tide-relay/Cargo.toml`;
- `docs/src/support/connector-release-checklist.md`.

Do not build a template framework. Small deterministic rendering functions and checked-in output are enough.

### C.3 Registry validation

`--check` must fail on:

- unsupported registry schema version;
- duplicate connector ID, runtime source type, or runtime sink type;
- invalid maturity/kind value;
- empty or placeholder owner;
- missing security contact on `supported` rows;
- nonexistent Cargo feature, docs path, test path, metric evidence, or runbook path;
- `default_build = true` on preview/experimental connectors;
- missing production evidence on a supported connector;
- connector pages or coordinator factory types absent from the registry;
- generated README, matrix, profile block, or checklist drift;
- `experimental-full` omitting a non-profile Cargo feature that is expected to compile.

For runtime completeness, scan only the bounded `match source_type` and `match sink_type` factory blocks. Fail with the unregistered literal. Do not introduce a Rust runtime metadata API solely for documentation generation.

### C.4 Generated README surface

Replace the “30 Sink Backends ... all integration-tested” feature bullet and handwritten sink table with a generated table containing:

- connector name;
- direction;
- maturity;
- normal-build availability;
- tested protocol/service versions;
- owner;
- link to the compatibility matrix.

Use counts only if generated from the registry and split by maturity. Do not call a compile-only test integration evidence.

### C.5 Generated compatibility matrix

The matrix must show, for every row:

- maturity definition/link;
- source and sink availability;
- Cargo feature/profile;
- tested versions;
- auth, TLS, restart, duplicate, and real-protocol evidence status;
- owner;
- active docs and test evidence links;
- known missing production criteria.

The absence of evidence is visible as `not yet proved`, not a green check derived from `Result` return types or source-file presence.

### C.6 Generated release checklist

Generate a connector-by-criterion checklist matching `docs/src/support/production-supported.md`. It is a release-review artifact, not a promise that unchecked items are implemented.

The generator fails the release if:

- a supported connector has an unchecked criterion;
- a production profile contains a non-supported connector;
- an owner or security contact is absent;
- evidence paths are stale.

Preview and experimental rows may contain unchecked items; those gaps are the point of the checklist.

### C.7 Developer and CI entry points

Add:

```text
just generate-connectors
just check-connectors
```

Run `just check-connectors` in the normal required CI path and before release generation. Document that connector changes update the registry first, then regenerate outputs.

## 7. Workstream D: Focused Build and Release Profiles

### D.1 Align feature gates with runtime code

Audit `pg-tide-relay/Cargo.toml`, `source/mod.rs`, `sink/mod.rs`, and the coordinator factory arms together.

Required corrections:

- make `pg-inbox` a real gate if PostgreSQL inbox is optional in generated profiles, or remove the misleading feature and classify it as built in;
- make `stdout` accurately gate stdout/file diagnostics if retained as a feature;
- put the DuckLake source module behind the same `ducklake` feature as its implementation;
- either register the DuckLake source as experimental and test its factory config, or mark it unavailable and remove active configuration claims;
- keep fan-in disabled and experimental; do not re-enable it in a profile;
- keep WAL source and KMS provider groundwork out of production profiles.

Do not refactor connector traits or factories. This work aligns existing gates and match arms only.

### D.2 Generate and verify profile aliases

After registry generation, verify these builds independently:

```bash
cargo build --package pg-tide-relay --no-default-features --features core
cargo build --package pg-tide-relay --no-default-features --features core-kafka
cargo build --package pg-tide-relay --no-default-features --features experimental-full
```

Use `core` as the workspace/default release path. The experimental build may be slower and may run in a separate non-production CI job, but it must compile before claiming “everything that compiles.”

### D.3 Make Docker profile selection explicit

In `Dockerfile`:

- remove the RockLake clone;
- add `ARG CARGO_FEATURES=core`;
- build with `--no-default-features --features "$CARGO_FEATURES"`;
- add an OCI label recording the selected profile;
- retain the non-root runtime user and existing multi-architecture target handling.

Do not accept a free-form shell `CARGO_FLAGS` string when the only required choice is a feature profile.

### D.4 Change release artifacts

In `.github/workflows/release.yml`:

- build standard relay archives with `core` on every advertised target;
- stop maintaining handwritten per-platform feature lists;
- validate `core-kafka` on targets where `rdkafka` is supported, without calling it a production artifact until its registry row is supported;
- build the normal Docker image with `CARGO_FEATURES=core`;
- rename `docker-full` jobs and `*-full` tags to `experimental-full` jobs and `*-experimental` tags;
- build the experimental image with `CARGO_FEATURES=experimental-full`;
- label the experimental manifest description as evaluation-only;
- ensure release creation depends on the registry check and core profile gates, not on support claims inferred from an experimental build.

Do not publish `latest-full` as a silent alias. Document its removal and the replacement tag in `CHANGELOG.md`. If compatibility telemetry proves a transition alias is required, it must carry the experimental description and be removed on a stated date; otherwise skip it.

### D.5 Split production and experimental CI claims

Reshape CI labels without duplicating test execution:

- required core build/test job: supported profile and supported evidence only;
- connector registry drift job;
- experimental-full compile/job: proves compilation, not support;
- connector-specific integration jobs: named by connector and taxonomy tier;
- authoritative NATS E2E job unchanged in scope;
- RockLake integration job explicitly experimental.

Replace normal `--all-features` clippy/build commands with `experimental-full` where the intent is broad compile coverage. Keep one explicit broad feature gate so experimental code cannot rot.

## 8. Workstream E: Product Documentation, Archive, and Support Policy

### E.1 Publish the production-supported definition

Create `docs/src/support/production-supported.md` from the roadmap checklist. Include:

- the exact maturity definitions;
- the evidence required for promotion;
- a statement that compile, construction, or request-shape tests are insufficient;
- the release-review rule that missing evidence downgrades the connector rather than weakening the gate;
- links to the generated connector checklist and test taxonomy.

### E.2 Publish the support policy

Create `docs/src/support/support-policy.md` and make it the authoritative current policy. It must state:

1. **PostgreSQL:** PostgreSQL 18 only unless the PG17 gate passes; do not say “18+” because PostgreSQL 19 is not yet tested.
2. **Extension/relay pairing:** only version combinations actually exercised by upgrade/E2E CI are supported. Remove the current unproved blanket claim that newer relays are backward compatible with older extensions.
3. **Architectures:** distinguish build artifacts from runtime-tested targets. A compiled Windows/macOS binary is not automatically a supported deployment target.
4. **Deployment modes:** label standalone binary, Docker, Helm, and CloudNativePG according to actual install/upgrade tests. Modes awaiting v0.45.0 operator gates remain preview.
5. **Connector versions:** link to the generated matrix; no handwritten duplicate list.
6. **Experimental best effort:** no compatibility, upgrade, response-time, or retention guarantee; features may change or be removed; security reports are still accepted.

## 13. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Roadmap core candidates do not yet meet the formal supported checklist | Evidence decides maturity; exclude them from production profile instead of weakening “supported” |
| Unconditional sink/source code bypasses profile containment | Make existing no-op gates real or explicitly classify the behavior as built in before generating profiles |
| Registry becomes another stale list beside runtime factories | Bounded factory scan plus generated-output drift check in required CI |
| Boolean evidence fields become unsupported green checks | Store concrete paths and show missing categories in the generated checklist |
| Generator rewrites unrelated Cargo/README content | Restrict writes to marker blocks and deterministic generated files |
| Pinned Git dev-dependency breaks crate packaging | Run `cargo package`; fall back to a workspace-excluded external test crate |
| Removing `latest-full` surprises users | Changelog migration note and explicit `latest-experimental` replacement; no silent support claim |
| Default feature changes break downstream source builds | Keep explicit core-kafka/experimental-full escape hatches and document feature changes |
| Test renames preserve a misleading assertion | Require the audit to name the final observable outcome, not just change words |
| Archive moves break hundreds of historical links | Use `git mv`, update references with `rg`, and run the link checker before merging |
| Historical docs remain searchable as current advice | Archive README warning and removal from active mdBook navigation |
| PG17 grows into a second release project | Time-box the feasibility gate; support only if the full maintained matrix passes |
| Release comments change but schema parity drifts | Add minimal adjacent migration and reuse real fresh/upgrade parity checks |
| Owners are assigned as placeholders | Registry validation rejects `TBD`, empty, or unverified handles |
| `experimental-full` is mistaken for tested support | Artifact/tag/job names and OCI descriptions always include “experimental” |
