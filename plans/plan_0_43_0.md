# pg_tide v0.43.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** A Good PostgreSQL Citizen
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Starting point:** v0.42.0 and current `main`
> **Scope rule:** Make PostgreSQL load, relay resource use, retention, cleanup, partitioning, and recovery capacity measurable and bounded. Do not add connectors, promote preview features, or publish performance claims without reproducible evidence.

---

## 1. Release Outcome

v0.43.0 is complete when an operator can predict the cost of pg_tide, retain every message still needed by a configured consumer, and bound storage growth without relying on `consumed_at` or unverified benchmark claims:

1. A reproducible black-box benchmark uses the public SQL API, packaged PostgreSQL 18 extension, real `pg-tide` process, and real NATS JetStream service.
2. The benchmark reports `outbox_publish()` p50/p95/p99 overhead, relay throughput and delivery latency, relay CPU/RSS, PostgreSQL WAL, table/index growth, vacuum behavior, sweep cost, outage recovery, backpressure behavior, and HA interruption.
3. Criterion remains only a microbenchmark suite. The current direct-insert `load_test.rs` is renamed and cannot be cited as relay throughput or end-to-end evidence.
4. Every required operational metric has a reviewed numeric budget in a machine-readable file. Deterministic query-count budgets run on pull requests; environment-sensitive latency, throughput, memory, WAL, bloat, and recovery budgets run on a scheduled reference job.
5. Native cleanup uses the minimum safe checkpoint across every configured native relay pipeline and consumer group for an outbox. A disabled pipeline remains retention-protected until it is explicitly deleted.
6. A configured pipeline with no checkpoint blocks deletion for its outbox. One fast pipeline can never make rows eligible while a slower sibling still needs them.
7. Cleanup requires both conditions: the row is older than the outbox retention window and its ID is at or below the safe cleanup checkpoint.
8. Cleanup is bounded, supports dry-run, reports blockers and remaining work, records successful progress, surfaces failures, and never turns an error into a zero-row success.
9. Administrative rewind refuses a target below the highest deleted message ID and explains that the requested history is no longer retained.
10. Native lag, status, and cleanup views derive from per-pipeline offsets rather than `consumed_at` or arithmetic on globally gapped IDs.
11. Public publishing and native polling use a short PostgreSQL advisory-lock fence so a long-running transaction cannot commit a lower message ID after the relay has advanced past it.
12. Optional partitioning keeps `tide.tide_outbox_messages` as the only public parent relation and partitions it by global message-ID ranges. The canonical `(outbox_name, id)` polling query remains unchanged and benefits from partition pruning.
13. Partition creation, default-partition recovery, polling across boundaries, safe removal, multiple outboxes, long transactions, and rollback are tested. The old per-outbox/time-partition conversion path is no longer advertised as production-ready.
14. Scheduled soak tests prove bounded memory and storage behavior during sustained load, sink outage/recovery, relay restart, PostgreSQL connection loss, concurrent cleanup, and catalog reload churn.
15. The capacity guide contains only measured data and answers message rate, pipeline count, message size, claim-check, disk, indexes, autovacuum, and partitioning questions for a named reference environment.

The release does not promise a universal messages-per-second number. Results are tied to payload size, pipeline shape, PostgreSQL settings, sink acknowledgment behavior, and the recorded benchmark environment.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.42.0 is a hard prerequisite

Before v0.43.0 implementation starts, rerun the v0.42.0 release gate on `main`, including:

- supported connector crash-window tests;
- monotonic offset and rewind tests;
- two-instance ownership transfer;
- DLQ failure safety;
- public API PostgreSQL-to-NATS delivery;
- fresh v0.42.0 install and v0.41.0-to-v0.42.0 upgrade parity;
- `core` build without `test-failpoints`.

If a no-silent-loss, ownership, checkpoint, or migration gate is red, repair v0.42.0 first. Performance work must not normalize an incorrect delivery path.

### 2.2 Supported benchmark scope

The mandatory v0.43.0 operational benchmark is:

```text
public tide.outbox_publish()
  -> tide.tide_outbox_messages
  -> real pg-tide process
  -> NATS JetStream acknowledgment
  -> relay_consumer_offsets checkpoint
```

NATS is the reference sink because it is supported, locally reproducible, and has a durable acknowledgment boundary. PostgreSQL inbox receives a smaller retention/round-trip regression scenario, but v0.43.0 does not duplicate the complete connector matrix from v0.42.0.

Preview and experimental connectors do not block the operational budget gate. Their compilation remains covered by `experimental-full`.

### 2.3 Benchmark taxonomy

Use these names consistently:

| Name | Boundary | Release use |
|---|---|---|
| Microbenchmark | In-process serialization, batching, routing, hashing, or direct SQL insert cost | Developer optimization only |
| Operational benchmark | Public API through real relay and service, with process and PostgreSQL resource measurements | Capacity evidence and performance budgets |
| Soak test | Operational benchmark held under load long enough to detect growth, leaks, and recovery drift | Scheduled/release stability gate |

`pg-tide-relay/benches/throughput.rs` remains a Criterion microbenchmark. It is not renamed to “end to end” and does not provide capacity numbers.

Keep the required matrix small:

|---|---:|---:|---|

### 2.5 Performance budgets are reviewed data, not constants guessed in code

Add `benchmarks/operational/budgets.toml`. It must contain numeric gates for:

- maximum p50/p95/p99 `outbox_publish()` overhead over a matched business-only transaction;
- minimum acknowledged relay throughput;
- maximum p99 end-to-end delivery latency;
- maximum incremental relay RSS per in-flight message and per idle worker;
- maximum relay CPU per delivered message for the reference profile;
- maximum catalog discovery queries per relay per minute;
- maximum offset writes per acknowledged batch and per delivered message;
- maximum PostgreSQL WAL bytes per published and cleaned message;
- maximum table/index bytes per retained message;
- maximum sweep p95 duration and lock wait for the default batch;
- maximum dead-tuple/bloat ratio under the representative retention policy;
- maximum time and lag slope while recovering from a sink outage;
- maximum HA delivery interruption;
- maximum memory and storage growth slope during soak.

The first benchmark work records the v0.42.0 baseline. Exact limits are reviewed and committed before performance changes are accepted. Missing required budget keys fail validation; a baseline update never silently changes a budget.

### 2.6 Retention participants

For a native outbox, cleanup participants are:

1. Every row in `tide.relay_outbox_config` whose `config.source_type` is `outbox` and whose `config.source.outbox` matches the outbox.
2. Every relay-group offset row belonging to those configured pipelines.
3. Every row in `tide.tide_consumer_groups` for the outbox, using the minimum committed offset across that group’s consumers.
4. Any enabled experimental fan-in configuration that names the outbox. An enabled fan-in member without a valid member offset blocks cleanup; fan-in remains disabled by default.
5. Any active consumer lease whose range overlaps a cleanup candidate.

Rules:

- Disabled forward pipelines remain participants. Disable means “pause,” not “discard replay history.”
- Deleting a pipeline or consumer group explicitly retires that participant.
- A configured participant with no offset has safe offset `0`.
- Orphan relay offsets whose pipeline config was deleted do not block cleanup.
- A new relay group created after older rows were already removed can start only from the earliest retained row; retention cannot recreate expired history.
- `relay_delivery_receipts` and `consumed_at` are not cleanup authority.

The safe cleanup offset is the minimum participant offset. With no participants, age-based retention may clean the outbox because the outbox’s configured retention window is the only remaining contract.

### 2.7 Bounded sweep API

Add one authoritative API:

```text
tide.outbox_sweep(
    p_outbox_name text default NULL,
    p_batch_size integer default 1000,
    p_dry_run boolean default false
) -> jsonb
```

Contract:

- `p_batch_size` must be between 1 and 10,000.
- One call processes at most one batch per selected outbox.
- Candidate selection uses `FOR UPDATE SKIP LOCKED` and deterministic ID order.
- Dry-run inspects at most `batch_size + 1` candidates and reports `has_more`; it does not perform an unbounded `COUNT(*)`.
- The result includes outbox, retention cutoff, safe offset, participant/blocker details, eligible-in-batch, affected rows, `has_more`, highest deleted ID, duration, and partition action.
- A failed outbox is an error, not `0 deleted`.

Keep `tide.outbox_truncate_delivered(text default NULL) -> bigint` as a deprecated compatibility wrapper over one 1,000-row bounded sweep. Current callers continue to work, but documentation directs automation to `outbox_sweep()`.

Extend `pg-tide sweep` with:

```text
--batch-size <1..10000>
--max-batches <bounded count>
--dry-run
```

The command processes each outbox in a separate transaction, prints blockers/progress, and exits non-zero if any outbox fails. It must remove the current `unwrap_or(0)` behavior.

### 2.8 Long-running transaction fence

The global identity sequence is not commit ordered. Without an additional protocol:

1. Transaction A inserts ID 10 and remains uncommitted.
2. Transaction B inserts and commits ID 11.
3. The relay sees 11 and commits offset 11.
4. Transaction A commits ID 10, which `id > 11` will never poll.

v0.43.0 must close this gap before partition removal is trusted.

Use a dedicated per-outbox advisory-lock namespace:

- `tide.outbox_publish()` acquires a transaction-scoped shared advisory lock before inserting.
- `tide.outbox_publish_large()` remains covered because it delegates to `outbox_publish()`.
- Native polling acquires the matching exclusive lock, then performs the row query in a fresh `READ COMMITTED` statement/transaction snapshot.
- The poller releases the lock immediately after rows are fetched, before payload decoding or sink I/O.
- Multiple publishers for one outbox remain concurrent because shared locks are compatible.
- Publishers for unrelated outboxes do not block one another.
- Cleanup uses the same fence before calculating/deleting candidates.
- Whole-partition removal acquires all affected outbox fence locks in sorted name order.

Direct inserts into `tide.tide_outbox_messages` remain unsupported for delivery guarantees and appear only in explicitly named database microbenchmarks.

### 2.9 Partitioning is by message ID, not by time

ADR-006’s range-on-`created_at` design does not match the canonical polling query and cannot preserve the current `PRIMARY KEY (id)` because PostgreSQL requires partitioned unique constraints to contain the partition key.

The v0.43.0 layout is:

```text
tide.tide_outbox_messages
  PARTITION BY RANGE (id)
```

Decisions:

- The parent name and columns remain canonical and public.
- All logical outboxes continue sharing the parent and global identity sequence.
- Child names are derived from numeric ID bounds, not user-controlled outbox names.
- Default partition span is 10,000,000 IDs with two future partitions pre-created.
- A small default partition catches unexpected out-of-range rows; maintenance drains it into bounded range partitions and alerts if it is non-empty.
- Every child has the canonical `(outbox_name, id)` polling index and the cleanup-supporting indexes selected by measured query plans.
- Polling prunes partitions wholly below `last_change_id`.
- Retention remains time based per logical outbox. A whole ID partition may be removed only when every row in it is older than its outbox retention cutoff and below that outbox’s safe cleanup offset.
- If one outbox prevents a whole-partition drop, bounded row deletion still removes eligible rows for other outboxes.
- `retention_partitions` is deprecated; age plus participant offsets, not a fixed child count, determines safety.

Add a singleton catalog such as `tide.outbox_storage_config` to record `heap` versus `id_range`, partition span, premake count, and last maintenance time. Do not parse child names as configuration.

### 2.10 Conversion support boundary

Replace the misleading per-outbox live-conversion claim with one global maintenance-window operation:

```text
tide.admin_convert_outbox_storage(
    p_partition_span bigint default 10000000,
    p_premake integer default 2,
    confirm_blocking_copy boolean default false
) -> jsonb
```

Requirements:

- conversion applies to the complete canonical parent, not one outbox;
- explicit confirmation is mandatory;
- all relay workers must be drained and publishing must be in a maintenance window;
- the function takes an `ACCESS EXCLUSIVE` lock, creates an ID-range shadow parent, copies all rows, verifies row count/min/max/checksum samples, swaps atomically, and updates storage config;
- the operation runs in one PostgreSQL transaction so error, connection loss, or explicit `ROLLBACK` restores the original parent;
- preflight reports required temporary disk and refuses insufficient free-space evidence when it can be determined;
- existing noncanonical/dedicated layouts are detected and rejected with remediation instructions rather than guessed;
- the deprecated `outbox_convert_to_partitioned(name, strategy, ...)` refuses new conversions and points to the global operation.

This is a blocking maintenance conversion. Zero-downtime/live conversion remains Preview and is not a v0.43.0 production claim.

### 2.11 Release metadata changes last

Add and validate the v0.42.0-to-v0.43.0 migration before changing workspace, control, Helm, or changelog versions. Do not tag, publish, push, or deploy v0.43.0 unless separately requested.

## 7. Workstream D: Pipeline-Aware Retention and Bounded Cleanup

### D.1 Add cleanup state and status

Add:

```text
tide.outbox_cleanup_state
tide.outbox_retention_status
tide.relay_pipeline_lag
```

`outbox_cleanup_state` stores one row per outbox:

- last successful run;
- last safe offset used;
- highest deleted ID;
- last batch rows;
- cumulative rows deleted;
- last duration;
- last partition action.

Update it in the same transaction as deletion or partition removal.

`outbox_retention_status` exposes:

- retained row count and bytes;
- oldest/newest retained timestamps;
- retention cutoff;
- participant count;
- safe offset;
- eligible rows capped for status cost;
- blocker names and offsets;
- cleanup progress/highest deleted ID;
- current storage layout/default-partition rows.

`relay_pipeline_lag` reports exact `COUNT(*) WHERE outbox_name = ... AND id > last_change_id` per relay group/pipeline/outbox. It must not subtract a globally gapped ID from an offset.

### D.2 Implement safe candidate selection

For each selected outbox:

1. Acquire the outbox maintenance fence.
2. Resolve every retention participant.
3. Compute the minimum safe offset; missing participant offsets become zero.
4. Refuse or report an overlapping active lease.
5. Select at most `batch_size` rows satisfying both age and offset conditions.
6. Lock candidates with `FOR UPDATE SKIP LOCKED`.
7. In dry-run, return the candidate summary without deletion.
8. Otherwise delete candidates and update cleanup state atomically.
9. Release the fence before moving to another outbox.

Use parameterized SQL. Do not construct relation names from outbox input.

### D.3 Preserve disabled-pipeline history

Add tests proving:

- two pipelines at offsets 100 and 80 clean only through 80;
- a disabled pipeline at 50 still blocks at 50;
- deleting that pipeline allows cleanup to advance;
- a configured pipeline with no offset blocks all rows;
- an unrelated outbox/pipeline does not affect the target;
- multiple relay groups use the minimum known group offset;
- consumer-group offsets and leases are honored;
- `consumed_at` values cannot make a native row eligible.

### D.4 Make rewind retention-aware

Extend both administrative rewind functions:

- reject `target_offset < highest_deleted_id`;
- include outbox, target, and retained floor in the error;
- continue requiring disable, ownership drain, authorization, confirmation, and audit;
- permit rewind to the exact retained boundary;
- leave normal monotonic writes unchanged.

Add fresh-install and upgrade tests for retained-boundary success and expired-history failure.

### D.5 Fix status and CLI behavior

- Update `outbox_status()` to expose retained rows, native safe offset, exact lag summary, and cleanup state.
- Preserve old JSON keys only where their meaning remains truthful; mark `consumed_at`-based fields deprecated rather than silently changing semantics.
- Update `pg-tide status` to use `relay_pipeline_lag` and exact offset identity.
- Update `pg-tide sweep` to parse `outbox_sweep()` results, continue across independent outboxes if configured to do so, and return a failure exit code if any failed.
- Add `pg-tide doctor` checks for stale cleanup, blocked cleanup, excessive default-partition rows, missing cleanup indexes, and storage-config/schema mismatch.

### D.6 Expose cleanup observability

Add fixed-cardinality output/metrics where the long-running relay has relevant state:

- cleanup rows and duration are primarily SQL/status surfaces because sweep is an explicit command;
- alerts use `outbox_retention_status` through a PostgreSQL exporter;
- logs include outbox, safe offset, rows, duration, dry-run, blocker count, and partition action;
- logs never include payloads;
- direct SQL errors remain PostgreSQL errors and CLI errors include the outbox and next action.

Do not add a PostgreSQL background worker or a second cleanup daemon.

## 8. Workstream E: Long-Transaction Safety and Shared-Parent Partitioning

### E.1 Add the publisher/poller fence

Implement one canonical lock-key helper and use it in:

- `outbox_publish()`;
- native poll;
- row cleanup;
- partition removal;
- partition conversion tests;
- doctor diagnostics.

Native poll must:

1. Begin a short database transaction.
2. Acquire the exclusive outbox fence.
3. issue the canonical parent query;
4. copy rows out of the result;
5. commit/release the fence;
6. decode payloads and perform claim-check reads afterward.

Rollback and release explicitly on query failure. Do not hold the fence during NATS publish, transform, DLQ, or checkpoint writes.

### E.2 Add the long-running transaction black-box test

Through public APIs:

1. Begin transaction A and publish a message without committing.
2. Publish and commit transaction B.
3. Start or nudge the real relay.
4. Prove B is not checkpointed past the invisible A row while A holds the shared fence.
5. Commit A.
6. Prove A and B are both delivered with stable IDs and the checkpoint advances after both.
7. Repeat across an ID-partition boundary.

The test must fail against the unfenced v0.42.0 behavior.

### E.3 Add ID-range storage configuration

The v0.43.0 migration creates and initializes `outbox_storage_config` by introspecting the actual parent:

- unpartitioned canonical table -> `heap`;
- canonical ID-range parent -> `id_range`;
- old `created_at` or dedicated-table layout -> explicit `legacy_noncanonical` preflight state and doctor failure.

Do not trust the old per-outbox `partition_strategy` value when physical storage disagrees. Deprecate `partition_strategy` and `retention_partitions` in comments/docs; do not drop them in this release.

### E.4 Provision and route partitions

Add one maintenance helper used by sweep:

```text
tide.outbox_maintain_partitions(
    p_ahead integer default 2,
    p_dry_run boolean default false
) -> jsonb
```

It must:

- read span/premake from `outbox_storage_config`;
- derive the current global identity range;
- create missing future children with bounded identifiers;
- create required child indexes;
- move rows from the default partition in bounded batches;
- refuse overlapping bounds;
- record created/drained/dropped events in `tide_partition_events`;
- be idempotent and concurrency-safe.

No `pg_partman` dependency is required.

### E.5 Remove partitions safely

A partition is removable only when:

- no active transaction can later publish an ID into it (all affected outbox fences held);
- every row is older than its logical outbox retention cutoff;
- every row ID is at or below that outbox’s safe cleanup offset;
- no active lease overlaps it;
- cleanup state can advance transactionally with the drop.

Use `DETACH PARTITION`/`DROP TABLE` only after the predicate is proved. Otherwise perform bounded row cleanup and leave the partition attached.

### E.6 Validate query plans and bounded catalog growth

Tests must assert:

- the canonical parent query returns rows across child boundaries in strict ID order;
- `EXPLAIN (FORMAT JSON)` prunes partitions below the offset;
- each scanned child uses the intended `(outbox_name, id)` index;
- retention candidate queries do not sequence-scan every retained child for a small bounded batch;
- partition count remains bounded by retained ID ranges plus premade/default children;
- 100 logical outboxes do not create 100 public parent tables.

Avoid brittle assertions on exact planner cost numbers.

### E.7 Test conversion and rollback

Test:

- heap-to-ID-range conversion with empty, small, and multi-outbox parents;
- sequence/identity continuity after swap;
- public publish and relay delivery after conversion;
- explicit outer transaction `ROLLBACK` restores the heap layout;
- terminated conversion transaction leaves the original canonical parent;
- insufficient confirmation, active ownership, and noncanonical layout fail before destructive work;
- temporary disk estimate and row-count verification;
- old per-outbox conversion function refuses with a clear migration path.

Do not label the operation live or zero-downtime.

## 15. Risks and Mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Disabled pipeline blocks cleanup indefinitely | Storage continues growing during a long pause | Intentional safe default; status names blocker; delete pipeline to retire it |
| New relay group expects expired history | Starts below retained floor and silently misses rows | Document earliest-retained boundary; status/rewind checks reject impossible history |
| Participant query misses a config shape | Unsafe deletion | Restrict native cleanup to validated `source_type = outbox`; unknown/fan-in state blocks |
| Global ID is not commit ordered | Lower ID appears after checkpoint | Publisher/poller advisory fence and black-box long-transaction test |
| Fence raises publish latency | Application transaction regression | Per-outbox shared locks, short exclusive fetch, explicit publish-overhead budget |
| Poller holds fence during decode/network | Publisher stalls | Copy rows and release before decode, transforms, sink I/O, or checkpoint |
| ID-range child contains outboxes with different retention | Slow outbox delays whole-child drop | Bounded row cleanup proceeds; drop only when every row is safe |
| Default partition accumulates unnoticed | Polling cost and unbounded storage return | Premake two ranges, doctor/status warning, bounded drain, soak assertion |
| Conversion needs roughly 2x disk | Disk exhaustion or long outage | Dry preflight/estimate, explicit confirmation, blocking maintenance boundary |
| Old created-at partition layout exists in the wild | Upgrade guesses and loses access | Detect physical layout, fail closed, publish remediation; no automatic reinterpretation |
| Time-partition APIs remain discoverable | Operators use contradicted procedures | Deprecate/refuse old conversion and rewrite active docs/ADRs |
| Sweep batch is still expensive for large payloads | WAL and lock spikes | 1,000 default, 10,000 hard cap, measured duration/WAL budgets |
| Dry-run performs a full count | Dry-run itself overloads PostgreSQL | Inspect only `batch_size + 1`, report `has_more` |
| Rewind crosses deleted rows | Apparent replay succeeds with missing events | Highest-deleted-ID guard and explicit error |
| Benchmark runner noise | False regressions or meaningless baselines | Same environment, warmup, three runs, median, absolute correctness gates |
| Baseline update masks regression | Capacity erodes unnoticed | Separate budget file and reviewed change policy |
| Soak tests leak child processes | Runner/resource instability | Exact process handles/PIDs and cleanup guards |
| Stats extensions alter production requirements | Hidden runtime dependency | Use `pg_stat_statements`/`pgstattuple` only in benchmark environment; production remains optional |
| Scope expands into autoscaling/backpressure redesign | v0.43.0 misses its trust gate | Measure/document actual behavior; defer new admission-control protocol |
