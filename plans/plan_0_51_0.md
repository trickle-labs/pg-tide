# pg_tide v0.51.0 implementation plan

> **Status:** Proposed
> **Release theme:** Upgrade, Rollback, and Recovery Integrity
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.50.0 and current `main`
> **Implementation branch:** `implementation-v0.51.0`
> **Scope rule:** Make supported lifecycle transitions repeatable with packaged
> artifacts. Do not add connectors, delivery semantics, PostgreSQL major-version
> upgrades, a general deployment test framework, or automatic repair of manually
> modified catalogs.

## 1. Release outcome

v0.51.0 is complete when an operator can install, upgrade, roll back the relay,
restore PostgreSQL, and recover from an interrupted migration by following tested
public procedures. No supported procedure may require a direct write to a
PostgreSQL system catalog or a pg_tide catalog table.

The supported production upgrade floor for v1 is v0.47.0. A v0.47.0 extension
may upgrade to v0.51.0 through the packaged adjacent migration chain. Engineering
tests may continue to run the older SQL chain, but those tests do not extend the
support promise below v0.47.0.

The release proves these lifecycle paths:

```text
fresh v0.51.0 install

v0.47.0 extension
  -> v0.48.0
  -> v0.49.0
  -> v0.50.0
  -> v0.51.0

v0.50.0 extension + v0.50.0 relay
  -> mixed v0.50.0 and v0.51.0 relays
  -> v0.51.0 extension
  -> v0.51.0 relays
  -> optional relay rollback to v0.50.0

PostgreSQL backup or recovery point
  -> clean PostgreSQL 18 cluster
  -> restored business rows, pg_tide state, and stable event identities
  -> relay restart and at-least-once recovery
```

v0.51.0 does not promise that PostgreSQL state can roll back an external
destination. Restoring a checkpoint to an earlier point may redeliver an event
that NATS, Kafka, or a webhook already accepted. The restored relay must use the
same stable event identity, and the destination must apply its documented
deduplication rule.

Reuse PostgreSQL extension updates, `pg_dump`, `pg_restore`, `pg_basebackup`,
archived WAL, the existing clean-room runner, the existing real relay process
harness, Docker, Helm, and CloudNativePG. Do not build a second migration engine,
backup format, or cluster orchestrator.

## 2. Preconditions and scope guard

### 2.1 Release preconditions

Before the first implementation pull request:

1. Confirm that every v0.50.0 exit criterion passes on `main`.
2. Confirm that the v0.50.0 tag resolves to the current release baseline.
3. Run `just check-required-tests`, `just check-v1-contracts`, and
   `just check-v1-surface`.
4. Record the exact v0.47.0, v0.50.0, and starting `main` commits in the
   v0.51.0 tracking issue.
5. Confirm that required lifecycle tests have `max_retries = 0` and that no
   release blocker is quarantined.
6. Preserve the v0.50.0 relay image digest and binary archive digest used by
   mixed-version and rollback tests.
7. Run the current real extension parity job once and retain its output as
   before-change evidence. Its present limitations must remain visible in the
   tracking issue.

If the v0.50.0 gate fails, stop. Lifecycle work must test a known delivery
baseline rather than absorb unresolved delivery defects.

### 2.2 Frozen contract boundary

The v0.47.0 contract freeze still covers:

- public `tide.*` SQL signatures;
- pipeline JSON fields and validation;
- core metric names and labels;
- health behavior;
- CLI JSON fields and exit codes;
- native and CloudEvents envelopes;
- the four supported destination contracts.

v0.51.0 may add an internal compatibility check and versioned lifecycle
evidence. It must not add a pipeline field, connector option, delivery state,
or administrative repair API merely to make a lifecycle test convenient.

### 2.3 Explicit non-goals

Do not include the following work:

- support for upgrading from every historical v0.x release;
- automated PostgreSQL 17 to PostgreSQL 18 or PostgreSQL 18 to PostgreSQL 19
  upgrades;
- bidirectional logical replication or cross-region disaster recovery;
- a new backup file format or a pg_tide backup daemon;
- logical restore support for preview partitioned storage layouts;
- automatic reconciliation of manually edited extension catalogs;
- exactly-once recovery claims for external destinations;
- mixed-version guarantees for experimental connectors or removed relay
  surfaces;
- new pipeline configuration fields for a rollback fixture;
- Kubernetes distribution coverage beyond the declared test environment;
- supply-chain policy, SBOM, provenance, and signing work assigned to v0.52.0,
  except checksums needed to bind lifecycle results to exact artifacts;
- the long-run soak and performance-budget work assigned to v0.53.0;
- broad documentation cleanup assigned to v0.54.0.

Fix lifecycle defects exposed by required tests. Record unrelated findings for
their planned release.

## 3. Canonical lifecycle contract

### 3.1 One machine-readable policy

Add `schemas/lifecycle-compatibility-v1.json` as the source of truth for:

- the v1 extension upgrade floor;
- the current target version;
- supported extension and relay combinations;
- the adjacent relay rollback target;
- every supported migration step;
- migration transaction, lock, relay, reversibility, and recovery policy;
- logical, physical, and PITR recovery limits;
- the exact compatibility error code.

Keep the file small. The relay can embed it with `include_str!()` and parse it
with the existing `serde_json` dependency. Add no version or configuration
dependency.

Add `scripts/check_lifecycle_contract.py` to verify that:

1. every supported forward migration names an existing SQL file;
2. every migration marked reversible names an existing reverse SQL file;
3. the chain starts at v0.47.0 and ends at the workspace version;
4. every supported mixed-version row has an executable test case;
5. version compatibility documentation contains the generated matrix;
6. `tests/required-tests.toml` contains the required lifecycle gates;
7. the workspace, control files, chart, examples, and evidence target agree on
   v0.51.0.

Do not duplicate version ranges in several Rust modules. The startup check,
doctor output, status output, tests, and generated documentation must read the
same policy.

### 3.2 Supported upgrade policy

Adopt this policy for v0.51.0:

| Question | v0.51.0 answer |
|---|---|
| Supported production extension floor | v0.47.0 |
| Supported target | v0.51.0 |
| Required path | Every adjacent SQL migration from v0.47.0 through v0.51.0 |
| Direct `ALTER EXTENSION ... TO '0.51.0'` | Supported because PostgreSQL selects the adjacent scripts |
| Skipping or deleting an adjacent script | Unsupported and blocked by packaging checks |
| Relay procedure from v0.47.0 through v0.49.0 | Stop, upgrade the extension, then start the target relay |
| Rolling relay window for v0.51.0 | v0.50.0 and v0.51.0 only |
| Extension rollback after the v0.51.0 migration | Restore or PITR, because v0.51.0 adds backup metadata |
| Relay rollback after the v0.51.0 extension | v0.50.0 only |

The v0.48.0 to v0.49.0 preflight remains authoritative. An enabled removed
surface or nonempty removed state blocks the entire floor-to-target update
without committing a partial version.

### 3.3 Supported mixed-version matrix

Test and publish this bounded matrix:

| Extension | Relay | Status | Purpose |
|---|---|---|---|
| v0.50.0 | v0.50.0 | Supported | Starting state |
| v0.50.0 | v0.51.0 | Supported | Relay-first rolling upgrade |
| v0.51.0 | v0.50.0 | Supported | Relay rollback window |
| v0.51.0 | v0.51.0 | Supported | Target steady state |
| v0.50.0 | mixed v0.50.0 and v0.51.0 | Supported | Rolling replacement before extension update |
| v0.51.0 | mixed v0.50.0 and v0.51.0 | Supported | Rolling replacement and rollback after extension update |
| earlier than v0.50.0 | v0.51.0 | Rejected | Outside the rolling runtime window |
| later than v0.51.0 | v0.51.0 | Rejected | Unknown future schema |

The upgrade floor and the mixed runtime window are different promises. An
operator may start at v0.47.0, but must use stop-upgrade-start until the
extension reaches v0.50.0.

Historical binaries cannot acquire a new compatibility check. The migration
guide must require all pre-v0.50.0 relays to stop before the extension update.
The v0.51.0 relay must reject every extension outside its declared window
before it creates a coordinator, acquires ownership, polls, replays, sweeps, or
publishes.

### 3.4 Migration policy from the upgrade floor

Record this initial classification in the lifecycle policy and verify it
against the SQL:

| Migration | Catalog effect | Relay mode | Reversibility | Recovery after failure |
|---|---|---|---|---|
| v0.47.0 to v0.48.0 | No schema change | Relays stopped for a floor upgrade | Reversible no-op | Retry the update |
| v0.48.0 to v0.49.0 | Fails closed, then removes unsupported functions, fan-in state, and backfill state | Relays stopped | Irreversible after commit | Before commit, correct the preflight or retry. After commit, restore or continue forward |
| v0.49.0 to v0.50.0 | No catalog change | Relays stopped for a floor upgrade; adjacent mixed operation is not a v0.50.0 promise | Reversible no-op | Retry the update |
| v0.50.0 to v0.51.0 | Registers supported persistent state for logical backup and records v0.51.0 metadata | v0.50.0 and v0.51.0 relays supported | Data preserving, not extension-downgrade reversible | Retry before commit. Restore or PITR after commit if the extension must return to v0.50.0 |

Add reverse SQL only for the no-op steps where it represents an exact schema
transition. A reverse script must update the extension comment and must have a
representative-data test. Do not add a v0.51.0 to v0.50.0 no-op reverse script,
because it would leave v0.51.0 backup metadata while claiming a complete
downgrade.

### 3.5 Recovery invariants

Every lifecycle test must preserve these invariants:

1. A failed or interrupted `ALTER EXTENSION` leaves `extversion`, schema,
   privileges, ownership, configuration, messages, offsets, and DLQ data at
   the last committed version.
2. A successful upgrade preserves every committed business row and outbox
   event.
3. Fresh v0.51.0 and upgraded v0.51.0 installations have the same supported
   catalog state unless the lifecycle policy records a deliberate data-only
   difference.
4. The relay never polls before the extension compatibility check succeeds.
5. A relay rollback never decreases a checkpoint or changes an event identity.
6. Logical restore preserves the supported heap-layout pg_tide state, dynamic
   inbox tables, owners, privileges, sequence continuity, large objects, and
   extension version.
7. Physical restore preserves the complete PostgreSQL cluster state for both
   supported heap storage and preview partitioned storage fixtures.
8. A restored checkpoint never exceeds the highest restored source event.
9. Restore before checkpoint commit may redeliver an event. It must not skip
   that event.
10. Restore after checkpoint commit must resume after the committed frontier.
11. DLQ rows retain their deduplication identity through backup and restore.
12. Runtime leases, ownership sessions, and heartbeats are not restored as
    active authority. New relay processes must reacquire them.
13. External destinations are not assumed to roll back with PostgreSQL.
14. Every test result names the source and target artifact digests.

## 6. UP-1: Declare and enforce the lifecycle policy

### Objective

Make the supported version boundary explicit in one file and enforce it before
the relay can touch a pipeline.

### Files and symbols

Add or update:

- `schemas/lifecycle-compatibility-v1.json`;
- `scripts/check_lifecycle_contract.py`;
- `pg-tide-relay/src/compatibility.rs`;
- `pg-tide-relay/src/lib.rs`;
- `pg-tide-relay/src/main.rs`;
- `pg-tide-relay/src/cmd/self_test.rs`;
- `pg-tide-relay/src/cmd/doctor.rs`;
- `pg-tide-relay/src/cmd/status.rs`;
- `pg-tide-relay/src/error.rs`;
- `docs/adr/adr-014-upgrade-rollback-and-recovery-contract.md`;
- `docs/src/reference/version-compatibility.md`.

### Runtime design

Add one strict compatibility function that accepts the relay version and the
installed `pg_extension.extversion`. It returns either the matching policy row
or `RelayError::IncompatibleExtensionVersion`.

The parser must accept only `MAJOR.MINOR.PATCH` release values used by the
policy. Remove the lexicographic fallback from `self_test.rs`. A malformed
version is an error, not a best-effort comparison.

For `pg-tide run`:

1. Connect to PostgreSQL through `pg_tls::connect()`.
2. Read `pg_extension.extversion::text` for `pg_tide`.
3. Evaluate the embedded lifecycle policy.
4. Emit one structured success or failure event with relay version, extension
   version, policy version, and compatibility class.
5. On failure, exit nonzero before creating the coordinator pool, LISTEN
   connection, metrics server, advisory-lock session, or worker.
6. On success, continue through the existing startup preflight.

Do not add a command-line bypass. An override would turn an unsupported
combination into an untracked production mode.

`doctor`, `status`, and `--self-test` must report the same decision. Diagnostic
commands may connect and print the incompatibility so an operator can diagnose
the problem, but they must not describe the relay as runnable.

Use one bounded public error code, such as
`PGTIDE_EXTENSION_VERSION_INCOMPATIBLE`, in text, JSON, and structured logs.
Include installed version, relay version, supported range, and the documented
next action. Never include the PostgreSQL URL.

### Required tests

Add pure tests for:

- every supported matrix row;
- the lower bound;
- the upper bound;
- a malformed extension version;
- a prerelease or future version not listed in policy;
- a missing extension;
- deterministic text and JSON error fields.

Add process tests that prove an incompatible v0.51.0 relay:

- exits nonzero;
- emits the bounded compatibility error;
- never acquires a pg_tide advisory lock;
- never advances a checkpoint;
- never creates a delivery receipt;
- never reaches the destination.

### Acceptance criteria

- [ ] One machine-readable policy defines every lifecycle version promise.
- [ ] `pg-tide run` checks compatibility before coordinator startup.
- [ ] Malformed and future versions fail closed.
- [ ] Doctor, status, self-test, logs, and JSON output agree.
- [ ] No bypass can enable an unsupported target relay combination.
- [ ] The documented matrix is generated from or checked against the policy.

## 7. UP-2: Build packaged fresh-install and upgrade parity

### Objective

Compare a real v0.51.0 install with a real upgrade from the supported floor
using the files an operator receives.

### Stage one extension artifact

Add `scripts/package_extension.sh` as the one extension staging path. It must:

1. run `cargo pgrx package --package pg-tide-ext --pg-config <pg18 pg_config>
   --out-dir <root>`;
2. copy every supported adjacent forward SQL file into the staged PostgreSQL
   18 extension directory;
3. copy every declared reverse SQL file;
4. verify the control file, current install SQL, shared library, and all policy
   migration files exist;
5. reject a file whose version endpoints are absent from the lifecycle policy;
6. produce a deterministic archive and SHA-256 manifest.

Reuse this script in clean-room tests, parity tests, lifecycle tests, candidate
images, and the release workflow. Remove ad hoc workflow copies of only the
latest migration.

The v0.50.0 release did not publish an extension archive. For the one-time
source fixture, stage v0.47.0 and v0.50.0 packages from their immutable tags in
a clean checkout and record the tag commit plus artifact digest. Do not compile
historical sources in the database under test. Starting with v0.51.0, publish
the staged PostgreSQL 18 extension archive so later releases can consume a
released artifact directly.

### Supported parity paths

Run both:

- fresh v0.51.0 versus v0.50.0 to v0.51.0;
- fresh v0.51.0 versus v0.47.0 to v0.51.0 through every packaged adjacent
  script.

The floor path must execute one public command:

```sql
ALTER EXTENSION pg_tide UPDATE TO '0.51.0';
```

Do not manually run migration SQL in the supported parity test. PostgreSQL
must select the packaged path.

### Seed representative state

Before each upgrade, create representative state through public APIs where the
source version provides them:

- an application table and committed business row;
- an outbox and pending event;
- an inbox and one processed identity;
- a supported relay pipeline;
- an existing durable checkpoint produced by a real relay;
- an unresolved DLQ row produced through a controlled permanent delivery
  failure for the adjacent v0.50.0 fixture;
- publisher and tenant grants created through public functions;
- non-default ownership and privileges;
- a large payload that uses the out-of-line storage path when supported.

Use direct table assertions only to inspect the result. Do not seed supported
state with catalog inserts.

### Normalize the catalog

Add one snapshot helper under `scripts/` that emits stable JSON for:

- schemas and extension membership;
- tables, views, sequences, and relation persistence;
- columns, types, collations, nullability, defaults, identity, and generated
  expressions;
- functions, identity arguments, result types, languages, volatility,
  parallel safety, strictness, and security-definer state;
- indexes and predicates;
- constraints and definitions;
- triggers and definitions;
- owners and explicit ACLs;
- comments used as version or operational contracts;
- `pg_extension.extversion`, `extconfig`, and `extcondition`;
- supported generated contract artifact digests.

Normalize OIDs, physical file names, timestamps, sequence current values, and
other instance-specific data. Do not sort a plain `pg_dump` and call it a
complete catalog comparison.

After catalog comparison, run the same public smoke workflow on both databases
and compare behavior. A catalog snapshot cannot prove that Rust-backed SQL
functions load and execute.

### Replace misleading checks

Replace the hard-coded `real-extension-parity` workflow steps with the shared
artifact runner. Delete or repurpose the current `schema-diff` job because its
fresh and upgrade databases both apply the same base file and the same
migration loop.

Keep `migration_test.rs` as engineering evidence for the historical raw SQL
chain. Rename comments and CI labels so it does not claim packaged parity.

### Acceptance criteria

- [ ] Tests install only staged extension artifacts into PostgreSQL.
- [ ] The supported floor upgrades through PostgreSQL's extension mechanism.
- [ ] Fresh, adjacent-upgrade, and floor-upgrade catalog snapshots match.
- [ ] Every deliberate difference is listed in the lifecycle policy and has a
  test.
- [ ] Public SQL behavior matches after fresh install and upgrade.
- [ ] Representative rows, ownership, privileges, and large payloads survive.
- [ ] Tautological schema comparisons are removed.

## 8. UP-3: Test sequential and interrupted migrations

### Objective

Prove that each supported migration either commits completely or leaves the
previous version intact and recoverable.

### Sequential migration tests

Retain the raw SQL engineering chain from v0.1.0, then add a packaged lifecycle
suite that:

1. installs the v0.47.0 extension artifact;
2. records the v0.47.0 catalog snapshot and representative data identities;
3. installs the v0.51.0 files without changing `extversion`;
4. runs each adjacent update separately and captures a snapshot after each;
5. repeats from v0.47.0 with one direct update to v0.51.0;
6. compares the two final snapshots and public behavior;
7. confirms that the v0.48.0 to v0.49.0 preflight aborts the direct chain when
   removed enabled state exists;
8. corrects that state through documented APIs, retries, and reaches v0.51.0.

### Interruption method

Use PostgreSQL transactions and real backend termination. Do not add test-only
branches to production migration SQL.

For the v0.48.0 to v0.49.0 DDL migration:

1. Hold a lock that lets the preflight complete but blocks a later DDL
   statement, such as the `outbox_retention_status` replacement.
2. Start `ALTER EXTENSION` in a second session.
3. Wait until `pg_stat_activity.wait_event_type = 'Lock'` for that backend.
4. Terminate the migration backend.
5. Release the blocker and restart PostgreSQL.
6. Assert that `extversion`, dropped functions, tables, columns, rows, owners,
   privileges, and extension membership still match v0.48.0.
7. Retry and verify a complete v0.49.0 state.

For v0.50.0 to v0.51.0, interrupt the real update process while its transaction
is open if a stable catalog lock point exists. If PostgreSQL completes the
metadata-only step too fast for a deterministic pause, test explicit
transaction rollback and server restart around the update instead. Mark the
process-kill case not applicable in the policy with the exact reason. Do not
add `pg_sleep()` to shipping SQL.

### Migration documentation contract

For each migration from v0.47.0, generate or check documentation for:

- whether PostgreSQL runs it in one transaction;
- the strongest expected lock and affected object;
- whether relays must stop;
- whether publishers may continue;
- whether the migration is reversible;
- the reverse script or restore boundary;
- interruption behavior;
- operator recovery steps;
- a public verification query.

### Acceptance criteria

- [ ] Adjacent and direct floor upgrades produce the same v0.51.0 state.
- [ ] A blocked migration leaves no committed partial DDL after termination.
- [ ] PostgreSQL restart preserves the previous committed version.
- [ ] Retry succeeds without manual catalog edits.
- [ ] The v0.49.0 fail-closed preflight remains atomic.
- [ ] Every supported migration has lock, relay, recovery, and verification
  documentation.

## 9. UP-4: Define and test mixed-version operation

### Objective

Exercise the real old and new relay artifacts against old and new extension
artifacts, including simultaneous ownership attempts.

### Artifact rules

Use:

- the released v0.50.0 relay binary or image by digest;
- the staged v0.50.0 extension fixture by digest;
- the candidate v0.51.0 relay binary or image by digest;
- the candidate v0.51.0 extension bundle by digest.

Before publishing, assert `pg-tide --version` and
`pg_extension.extversion` for every case. A test built from the current source
and labeled as an old version is invalid.

### Supported cases

For each supported matrix row:

1. Install the declared extension.
2. Configure a PostgreSQL inbox pipeline through public SQL.
3. Start the declared relay process or both relay versions with the same relay
   group.
4. Publish committed business transactions before, during, and after the
   transition.
5. Verify one active advisory-lock owner per pipeline.
6. Verify destination identities and the durable checkpoint.
7. Terminate the owner at an acknowledged-before-checkpoint boundary.
8. Verify takeover and allowed duplicate behavior.
9. Confirm that no source identity is missing.

Mixed process tests must prove both ownership directions: v0.50.0 owns first
and v0.51.0 takes over, then v0.51.0 owns first and v0.50.0 takes over.

### Unsupported cases

Run the v0.51.0 relay against:

- v0.49.0 extension;
- v0.47.0 extension;
- a malformed extension version fixture;
- a future extension version fixture.

Each case must fail before polling with the bounded compatibility error. Use
an isolated extension metadata fixture for malformed and future versions. Do
not mutate a production-like database catalog in place.

The lifecycle policy and docs must state the historical-binary limit:
v0.49.0 and earlier relays do not contain the v0.51.0 guard. Operators must
stop them before crossing into the v0.51.0 runtime window.

### Acceptance criteria

- [ ] Every supported row uses exact old and new artifacts.
- [ ] Mixed versions retain one owner per pipeline.
- [ ] Checkpoints remain monotonic through both takeover directions.
- [ ] Every v0.51.0 unsupported case fails before poll or publish.
- [ ] Compatibility errors are bounded, actionable, and secret-free.
- [ ] Tests do not claim that historical binaries gained a new guard.

## 10. UP-5: Rehearse relay rollback

### Objective

Prove that the previous supported relay can resume safely while the v0.51.0
extension remains installed.

### Required scenarios

Use the released v0.50.0 relay and candidate v0.51.0 relay for:

- rollback before either relay processes a message;
- rollback after a durable checkpoint exists;
- rollback after the destination accepted an event but before checkpoint
  commit;
- rollback after a retryable destination failure;
- rollback with unresolved and resolved DLQ rows;
- rollback after graceful drain;
- rollback after forced termination;
- rollback with every optional pipeline field that v0.51.0 can persist and
  v0.50.0 must read.

v0.51.0 adds no pipeline config field. Record the roadmap's "new optional
field" case as not applicable for this release, then prove that the canonical
JSON emitted by v0.51.0 remains accepted by v0.50.0. If implementation adds a
field despite this plan, the case becomes required and the v0.50.0 parser must
either accept it safely or refuse before polling.

### Assertions

Every rollback test must assert:

- the old relay's version and artifact digest;
- extension compatibility before the old relay starts;
- the checkpoint before and after rollback;
- stable event identity;

Do not downgrade the extension for a relay rollback. The supported rollback
unit is the relay artifact while the v0.51.0 extension stays installed.

### Acceptance criteria

- [ ] v0.50.0 resumes safely from every tested v0.51.0 durable state.
- [ ] Rollback cannot decrease or skip a checkpoint.
- [ ] Ambiguous acknowledgment may duplicate but cannot lose an event.
- [ ] DLQ state remains readable and recoverable.

## 11. UP-6: Define extension rollback behavior

### Objective

Replace the blanket and incorrect claim that PostgreSQL extensions cannot
downgrade with a migration-by-migration policy.

### Required work

1. Audit every forward and reverse SQL file from v0.47.0 through v0.51.0.
2. Record the catalog and data effect of each step in the lifecycle policy.
3. Add reverse no-op SQL for v0.48.0 to v0.47.0 and v0.50.0 to v0.49.0 if the
   catalog snapshots prove exact equivalence.
4. Keep v0.48.0 to v0.49.0 irreversible because it removes supported objects
   and state.
5. Keep v0.50.0 to v0.51.0 irreversible at the extension version boundary if
   backup registration cannot be removed through supported PostgreSQL APIs.
6. Test every provided reverse script with representative rows, owners,
   privileges, checkpoints, and DLQ data.
7. Verify that an unsupported target has no packaged reverse path and that the
   runbook directs the operator to restore or PITR.
8. Update `scripts/check_upgrade_completeness.sh` so reverse files do not alter
   forward-chain discovery.

Never write directly to `pg_extension`, `pg_depend`, or another PostgreSQL
system catalog to simulate a downgrade. PostgreSQL's extension update
mechanism and packaged SQL files are the only supported schema transition.

### Rollback procedure classes

Publish three distinct terms:

- **Relay rollback:** replace v0.51.0 relay processes with v0.50.0 while the
  v0.51.0 extension remains installed.
- **Extension reverse migration:** run a declared reverse SQL path where the
  lifecycle policy marks it exact and safe.
- **Database restore:** restore or use PITR when a migration is irreversible.

Do not use "rollback" without naming which class applies.

### Acceptance criteria

- [ ] Every migration from the floor is classified.
- [ ] Every declared reverse path has SQL and a representative-data test.
- [ ] Irreversible steps have tested restore instructions.
- [ ] No no-op reverse script implies safety across incompatible state.
- [ ] Active docs no longer claim that PostgreSQL cannot run extension reverse
  migrations.

## 12. UP-7: Add backup, restore, and disaster-recovery tests

### Objective

Prove that PostgreSQL recovery preserves the source event, destination
identity, checkpoint, DLQ, and operator security state required to resume.

### Persistent and transient state classification

Register supported persistent extension tables with
`pg_extension_config_dump()` in the v0.51.0 migration and fresh install path.
The final audited list must cover:

- outbox and inbox configuration;
- outbox messages;
- consumer groups and committed offsets;
- relay pipeline configuration and relay checkpoints;
- publisher and tenant grants;
- DLQ rows;
- cleanup high-water state;
- supported audit and delivery receipt rows needed by the documented
  retention and recovery contract.

Include retained disabled configuration that the v0.49.0 migration preserves
for export. Exclude removed experimental state from the production recovery
promise.

Do not restore these rows as active authority:

- consumer leases;
- advisory locks;
- relay runtime heartbeats;
- process ownership tokens;
- transient retry timers.

For each registered table, verify that bootstrap rows do not conflict during
restore. Use `pg_extension_config_dump()` conditions for extension-supplied
rows. If a mutable bootstrap singleton cannot restore without a duplicate key,
change its initialization or exclude it with a documented derivation rule. Do
not add a post-restore catalog repair script.

The production logical-backup promise covers the canonical heap outbox layout.
ID-range partitioning remains preview and receives physical backup evidence,
not a new v0.51.0 logical reconstruction tool.

### Logical backup and restore

Test a complete database backup, not only `--schema=tide`:

1. Install the candidate extension artifact in the source and target
   PostgreSQL 18 clusters.
2. Create application rows and publish outbox events in the same transactions.
3. Create a PostgreSQL inbox, process one event, leave one event pending, create
   a checkpoint, and create DLQ data.
4. Create non-default owners and grants through supported SQL.
5. Include a large out-of-line payload.
6. Capture global roles with `pg_dumpall --globals-only --no-role-passwords`.
7. Capture the database with `pg_dump --format=custom`.
8. Restore roles, then restore the database into a clean cluster.
9. Verify extension version, catalog snapshot, state identities, owners,
   privileges, sequences, dynamic inbox tables, and large objects.
10. Publish the next event and prove that generated IDs do not collide.
11. Start the real relay and prove pending delivery plus checkpoint recovery.

If logical restore requires credential reset because role passwords are not in
the artifact, document and test that step. Never put passwords in backup
evidence.

### Physical backup and restore

Use PostgreSQL 18 `pg_basebackup` with WAL streaming:

1. Seed the same representative state.
2. Stop or checkpoint the relay at a declared delivery boundary.
3. Take the physical backup.
4. Start a new PostgreSQL 18 instance from that backup with the exact extension
   shared library available.
5. Verify heap and preview ID-range partition fixtures separately.
6. Start the relay against the restored primary.
7. Verify event identities, checkpoint behavior, DLQ rows, ownership
   reacquisition, and allowed duplicates.

### PITR boundaries

Use a local archived-WAL fixture in scheduled and release CI. Create named
restore points around:

- application and outbox transaction commit;
- destination acknowledgment before checkpoint commit;
- checkpoint commit;
- DLQ commit.

Restore to each applicable point and assert:

| Restored boundary | Required PostgreSQL state | Required relay result |
|---|---|---|
| Before business transaction commit | Neither business row nor outbox event exists | Nothing delivers |
| After business and outbox commit, before destination acknowledgment | Business row and source event exist, old checkpoint remains | Event delivers |
| After external acknowledgment, before checkpoint commit | Source event exists and old checkpoint remains | Retry or dedup is allowed; no loss |
| After checkpoint commit | Source event and committed checkpoint agree | Automatic relay resumes after the event |
| After DLQ commit, before checkpoint commit | DLQ disposition exists and checkpoint remains old | Idempotent DLQ recovery completes without loss |

The external destination is outside PITR. Tests must retain its observed
effects while PostgreSQL moves backward so duplicate behavior is real.

### Failover recovery

Use a PostgreSQL primary and standby or the CloudNativePG cluster from UP-8:

1. Publish continuously through bounded transactions.
2. Terminate the primary during an in-flight relay batch.
3. Promote the standby.
4. Verify reconnect, advisory-lock reacquisition, checkpoint reload, and lag
   drain.
5. Assert stable identities and no missing source event.

### Documentation

Add `docs/src/operations/runbook-backup-restore.md` and link it from
`docs/src/SUMMARY.md`, `operations/runbooks.md`, and `operations/maintenance.md`.
Document:

- the exact logical and physical commands;
- the heap-layout logical backup boundary;
- role and credential handling;
- extension artifact prerequisites;
- large-object behavior;
- sequence verification;
- external destination deduplication after restore;
- PITR selection and verification;
- when to use relay rollback, reverse migration, restore, or PITR.

### Acceptance criteria

- [ ] A normal full `pg_dump` captures supported persistent pg_tide state.
- [ ] Logical restore into a clean PostgreSQL 18 cluster resumes delivery.
- [ ] Owners, privileges, sequences, large objects, checkpoints, and DLQ rows
  survive.
- [ ] Transient leases and ownership do not restore as active authority.
- [ ] Physical backup works for heap and the preview partition fixture.
- [ ] PITR tests all declared consistency boundaries.
- [ ] External destination resynchronization and deduplication are explicit.
- [ ] No recovery procedure requires a direct catalog edit.

## 17. Migration and failure handling during implementation

### 17.1 Schema policy

Prefer no user-table shape change in v0.51.0. The required SQL migration should
only register logical-backup state, add exact extension metadata, and update the
extension comment unless testing exposes a restore defect that requires a
minimal schema correction.

If restore testing requires a schema change:

1. identify the failed invariant;
2. change the canonical object once;
3. update both fresh install and upgrade paths;
4. classify the new lock and reversibility effect;
5. rerun fresh, adjacent, floor, interruption, and restore parity.

Do not add a shadow schema or duplicate catalog for migration tests.

### 17.2 Failure rules

- If the v0.47.0 tag cannot build in the pinned clean room, record the exact
  toolchain conflict and build the smallest immutable fixture needed. Do not
  lower the upgrade floor without a roadmap change.
- If fresh and upgraded catalogs differ, stop and fix the migration or record a
  deliberate compatibility difference before adding an allowlist.
- If a historical relay artifact cannot run in the declared matrix, narrow the
  matrix and update the policy. Do not patch or relabel the old binary.
- If logical restore omits authoritative state, fix extension backup
  registration. Do not add manual INSERT instructions.
- If PITR produces a checkpoint beyond restored source data, treat it as a P0
  blocker.
- If a platform test requires source mounts or an in-pod build, fix artifact
  staging before accepting the test.
- If an unsupported v0.51.0 combination reaches a poll, treat it as a P1
  blocker.
- If an external destination duplicates after PostgreSQL restore, verify the
  stable identity and documented deduplication boundary. Do not classify an
  allowed duplicate as data loss.

### 17.3 Evidence hygiene

Keep failed migration logs, PostgreSQL logs, relay structured logs, catalog
snapshots, Kubernetes events, and artifact digests. Redact URLs, secrets,
payloads, and role passwords before upload.

Do not mark a lifecycle record complete from a local run, a different commit,
or a rebuilt artifact with a different digest.
