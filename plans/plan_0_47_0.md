# pg_tide v0.47.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** Public Beta and API Freeze
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Starting point:** v0.46.0 and current `main`
> **Scope rule:** Freeze and validate the supported product contract. Add no connector, transport, wire format, orchestration mode, or headline feature. The only behavior changes allowed are release-blocking corrections discovered while completing the v0.46.0 gate, freezing a currently ambiguous contract, running pilots, or resolving independent-review findings.

---

## 1. Release Outcome

v0.47.0 is complete when one release-candidate contract has been reviewed, recorded, exercised by external pilots, and protected from accidental breaking changes:

1. The frozen v1 contract covers the supported public SQL API, pipeline JSON schema, core Prometheus metric families, health endpoints, CLI machine-readable output, native pg_tide and CloudEvents envelopes, and the direction-aware connector support matrix.
2. Each frozen surface has one human-readable normative document and one machine-checkable artifact generated from or tested against the implementation.
3. Compatibility rules say exactly which changes are breaking, additive, deprecating, or outside the supported contract.
4. Pull-request and release CI reject unreviewed drift between runtime behavior, generated schemas, documentation, examples, and the frozen artifacts.
5. The freeze applies only to documented production-supported surfaces. Preview, experimental, diagnostic, and internal Rust surfaces remain explicitly outside the v1 guarantee unless the contract manifest names them.
6. Any last breaking correction is completed, migrated, documented, and revalidated before the freeze baseline is approved. The baseline is not repeatedly rewritten to make later drift pass.
7. Four external pilot profiles complete the public core workflow using release-candidate artifacts:
   - moderate-volume PostgreSQL outbox to NATS JetStream;
   - PostgreSQL outbox to Kafka under strict operational requirements;
   - PostgreSQL outbox to a remote pg_tide inbox;
   - PostgreSQL outbox to HTTPS webhook with induced failure and retry.
8. Every pilot completes installation, steady-state delivery, a planned failure, restart recovery, upgrade, rollback rehearsal, duplicate observation, and operator diagnosis through public interfaces.
9. Pilot feedback is represented by repository issues with severity, affected contract surface, reproduction/evidence, owner, and disposition. Private anecdotes do not count as release evidence.
10. Independent reviewers other than the primary author approve the release candidate from PostgreSQL extension, Rust async/concurrency, distributed delivery semantics, security, and operations perspectives.
11. Review approvals identify the exact commit and artifact digests reviewed. A material contract or core-path change invalidates affected approvals until the reviewer rechecks the new candidate.
12. `SECURITY.md`, `SUPPORT.md`, `GOVERNANCE.md`, `.github/CODEOWNERS`, a release-manager checklist, vulnerability disclosure process, deprecation policy, and connector promotion policy are public and internally consistent.
13. The supported-version, ownership, security-contact, compatibility, and production-profile claims continue to come from `connectors.toml` and its generated outputs rather than a new connector registry.
14. No open P0 or P1 issue remains at release time. Missing evidence, an unavailable reviewer, or an unresolved pilot incident blocks the release rather than being reclassified for schedule.
15. Fresh install, v0.46.0-to-v0.47.0 upgrade, relay rollback, extension rollback where supported, and the documented mixed-version window all pass with the frozen contract intact.
16. v0.42.0 crash safety, v0.43.0 PostgreSQL and capacity budgets, v0.44.0 security boundaries, v0.45.0 operator contracts, and v0.46.0 four-connector evidence remain green on the final candidate.

The release does not promise v1.0.0 GA, exactly-once transport, new supported connectors, a stable Rust library API, stability for preview or experimental features, or compatibility for undocumented behavior.

## 2. Preconditions and Decisions to Lock Before Implementation

### 2.1 v0.46.0 is a hard prerequisite

Do not freeze an incomplete connector release. Before v0.47.0 contract work begins, rerun the complete v0.46.0 exit gate and verify:

- exactly four outbound destinations are production-supported: PostgreSQL inbox, NATS JetStream, Apache Kafka, and HTTPS webhook;
- every supported connector has complete happy-path, failure-window, restart, duplicate, authentication, TLS, redaction, metrics, runbook, upgrade, and rollback evidence;
- the connector registry is direction-specific and generated support claims match actual release profiles;
- NATS/Kafka/webhook inbound paths remain independently classified;
- supported config is strict and validated before ownership or polling;
- connector errors have bounded codes and explicit retry classes;
- source checkpoints advance only after the declared downstream acknowledgment;
- supported service versions and release artifacts are immutable and reproducible.

The current tree already has the core registry, generated compatibility material, pipeline schema, operator commands, metrics, and health endpoints needed as inputs. It also exposes likely carry-in checks that must be resolved before freezing:

- `schemas/pipeline-config-v1.schema.json` currently presents a broad connector field bag and enumerates preview/experimental types beside supported types;
- supported connector records in `connectors.toml` must be checked against the full production-supported evidence checklist, not merely the evidence entries currently listed;
- CLI JSON is assembled in command modules and lacks checked-in per-command schemas;
- metric constants and health routes exist in runtime code but are not represented by a complete frozen descriptor;
- native and CloudEvents serializers have tests but no single normative compatibility artifact;
- `docs/src/stability-guarantees.md` and `docs/src/v1-scope.md` still describe the earlier pre-freeze policy;
- the requested top-level governance and support files are absent.

If an item is an unmet v0.46.0 acceptance criterion, finish it under that owning scope before taking the v0.47.0 baseline. Do not disguise prerequisite feature work as API-freeze work.

### 2.2 Freeze only the supported contract

Classify every externally visible surface as one of:

| Classification | v0.47.0 treatment |
|---|---|
| Frozen | Covered by v1 compatibility and drift checks |
| Supported but intentionally extensible | Stable structure and semantics; explicitly documented additive rules |
| Preview | Publicly usable but may change; excluded from v1 compatibility |
| Experimental | Evaluation only; excluded from support and freeze |
| Diagnostic | Useful for local diagnosis; not a production integration |
| Internal | No compatibility promise |

The native transactional outbox, idempotent inbox, relay catalog APIs, supported sink configuration, core operator surfaces, and supported outbound connector matrix are frozen. Inbound connector surfaces, fan-in, DAG orchestration, managed backfill, data-lake connectors, KMS providers not already fully supported, and internal Rust types are not promoted by being present in the repository.

The pipeline schema and generated connector documentation must make this boundary obvious. Do not accidentally freeze every experimental connector key simply because one broad schema currently contains it.

### 2.3 Compatibility rules are part of the contract

Publish one compatibility policy with surface-specific rules:

| Surface | Breaking after freeze | Allowed after freeze |
|---|---|---|
| Public SQL | Remove/rename a function; change argument order, name, type, default, return shape, volatility, strictness, security behavior, or documented semantics | Add a new function through normal review; correct a security/correctness bug without violating documented invariants |
| Pipeline JSON | Remove/rename a supported key; change type/default/meaning; add a required key; narrow a valid range; silently accept unknown keys | Add an optional key with a defined default after compatibility review; add preview/experimental variants outside the frozen supported subset |
| Metrics | Rename/remove a family; change type, labels, units, or label meaning; add unbounded labels | Add a new bounded family; improve help text without changing meaning |
| Health | Remove/rename an endpoint; change success/failure status codes, readiness meaning, or stable body/content type | Add a separate endpoint without changing existing behavior |
| CLI JSON | Change envelope version, field name/type/nullability, error-code meaning, command identity, or exit-code mapping | Add a documented optional field only when consumers are required to ignore unknown fields |
| Event envelopes | Remove/rename a field; change type, requiredness, ID/dedup semantics, timestamp meaning, or payload encoding | Add a versioned optional extension under the published evolution rules |
| Support matrix | Remove a supported connector/version/profile without the support and deprecation process | Add a version after compatibility evidence; promote a connector through the published gate |

Text log wording, source layout, internal Rust APIs, SQL migration statement ordering, and experimental surfaces remain outside the freeze unless separately documented.

### 2.4 One contract manifest, not seven unrelated checks

Add one versioned manifest under `schemas/` that identifies:

- contract surface ID and version;
- normative documentation;
- machine-checkable schema or snapshot;
- generator or test command;
- implementation owner and CODEOWNER;
- stability classification;
- compatibility rules;
- last reviewed release.

Use existing sources of truth:

- extension installation/catalog for SQL;
- `schemas/pipeline-config-v1.schema.json` for supported pipeline config;
- `pg-tide-relay/src/metrics.rs` for emitted metrics;
- `pg-tide-relay/src/cmd` for CLI JSON;
- `pg-tide-relay/src/wire_format` and connector serialization for envelopes;
- `connectors.toml` for maturity and compatibility.

The manifest references these sources; it does not duplicate connector maturity, owners, versions, or capability facts.

### 2.5 Freeze the release candidate, not a moving branch

Use this order:

1. Close v0.46.0 carry-in gaps.
2. Inventory and review current external behavior.
3. Make any final breaking corrections.
4. Land migrations and documentation for those corrections.
5. Generate and approve the v1 baseline.
6. Build signed or checksum-addressed release-candidate artifacts.
7. Run all pilots and reviews against that exact candidate.
8. Permit only blocker fixes.
9. Regenerate affected evidence and obtain targeted reapproval.
10. Cut v0.47.0 only after the final candidate is unchanged by all gates.

### 2.6 Pilot evidence must be useful without leaking customer data

Pilot artifacts may record versions, topology, workload shape, timings, counts, resource use, bounded error codes, and scenario outcomes. They must not contain:

- application payloads;
- connection strings, credentials, or certificates;
- customer names without explicit consent;
- internal hostnames, IP addresses, or account IDs;
- raw logs that have not passed the existing secret-canary/redaction checks.

Use stable pseudonymous pilot IDs and link public issues to sanitized evidence.

### 2.7 Release metadata changes last

Do not bump versions while contract, pilot, review, or blocker gates are open. After all gates pass:

- update the workspace version;
- update both extension control files;
- add `sql/pg_tide--0.46.0--0.47.0.sql`, using a reviewed no-schema-change migration if the frozen SQL surface requires no DDL;
- update Helm chart/application versions and image references;
- add the changelog and claim-to-evidence release notes;
- rerun version, migration-chain, fresh-install, upgrade, rollback, packaging, SBOM, signature, and provenance checks.

## 4. Workstream A: Contract Inventory and Freeze Infrastructure

### A.1 Create the v1 contract manifest

Add a small checked-in manifest, for example `schemas/v1-contract-manifest.toml`, with one record for:

- `sql.public.v1`;
- `pipeline.config.v1`;
- `metrics.core.v1`;
- `health.http.v1`;
- `cli.machine.v1`;
- `event.native.v1`;
- `event.cloudevents.v1`;
- `connectors.supported.v1`.

Each record names its normative document, artifact, check command, owner, classification, and evolution rule. Keep the format declarative and validate it with Python's standard library or already-installed tooling; do not add a dependency or general schema-registry framework.

### A.2 Add one contract check entry point

Add `just check-v1-contracts` backed by one focused script that:

1. validates the manifest and referenced files;
2. runs or compares the surface-specific generators/snapshots;
3. fails on uncommitted generated drift;
4. rejects missing version/classification/owner/documentation;
5. verifies that only supported connector rows enter the frozen matrix;
6. reports a concise surface-specific diff and update command.

Provide a separate explicit update command for maintainers while establishing the baseline. After freeze approval, CI must never update artifacts automatically.

Reuse `scripts/generate_connector_surface.py`, `scripts/generate_pipeline_schema.sh`, and existing observability checks. Extend them or call them from the contract entry point instead of replacing them.

### A.3 Publish the compatibility policy

Rewrite `docs/src/stability-guarantees.md` for the v0.47.0 public beta and add the detailed evolution rules from Section 2.3. Update:

- `docs/src/v1-scope.md`;
- `docs/src/support/production-supported.md`;
- connector compatibility and release checklist pages;
- CLI, metrics, health, SQL, and wire-format references;
- README headline claims where they imply a broader guarantee.

The policy must state that v0.47.x is the v1 release-candidate contract and that a breaking change after freeze requires:

1. a documented critical security/correctness reason;
2. explicit release-manager and CODEOWNER approval;
3. migration/deprecation treatment;
4. regenerated artifacts;
5. renewed affected pilot/reviewer evidence.

### A.4 Add drift tests, not hash-only assertions

Artifacts must remain reviewable:

- JSON Schema for structured JSON;
- sorted JSON or TSV for installed SQL catalog facts;
- OpenMetrics descriptor text or sorted JSON for metrics;
- request/response fixtures plus semantic tests for health;
- exact JSON fixtures for event envelopes;
- generated Markdown/TOML-derived matrix for connectors.

Checks should produce meaningful field-level diffs. A checksum may identify a reviewed artifact, but a checksum alone is not the contract.

### A.5 Workstream acceptance

- Every frozen surface appears exactly once in the manifest.
- Every manifest entry has normative docs and executable evidence.
- `just check-v1-contracts` passes from a clean checkout.
- Changing a field, metric label, SQL signature, route behavior, or supported matrix row causes a focused failure.
- Preview/experimental/internal surfaces are visibly excluded.
- Existing generators remain authoritative for the surfaces they already own.

## 5. Workstream B: Public SQL Contract Freeze

### B.1 Capture the installed public SQL surface

Build and install the release-candidate extension into fresh PostgreSQL 18, then query `pg_catalog` for every documented `tide` function/procedure. Record at minimum:

- schema and name;
- identity arguments and argument names/modes;
- defaults;
- result type and `RETURNS SETOF`/table shape;
- function/procedure kind;
- volatility;
- strictness;
- parallel safety;
- security definer/invoker behavior;
- relevant execution configuration;
- documented privilege expectations.

Also identify public views or catalog tables explicitly promised as operator APIs. Do not freeze every implementation table merely because it exists in schema `tide`.

Generate a sorted artifact from the installed extension, not from regex over Rust source. Keep the `#[pg_extern(schema = "tide")]` check as a source lint, not as the proof of the installed signature.

### B.2 Reconcile documentation and migration aliases

Before approval:

- compare SQL reference pages and executable Quick Start blocks to the installed artifact;
- resolve deprecated positional relay APIs according to the existing migration policy;
- verify canonical v2 JSONB relay functions, outbox/inbox APIs, replay/rewind controls, retention functions, and operator views;
- explicitly classify compatibility functions and planned removals;
- remove undocumented aliases from supported examples or document them as deprecated;
- verify GRANT and role behavior against the v0.44.0 privilege model.

No undocumented overload becomes frozen accidentally.

### B.3 Add compatibility fixtures

Add tests that compare:

1. fresh v0.47.0 install against the SQL contract snapshot;
2. v0.46.0-to-v0.47.0 upgrade against the same snapshot;
3. sequential historical upgrade against the same supported result;
4. relay rollback against the documented mixed-version SQL subset.

The existing schema-diff and migration-chain checks remain necessary but are not sufficient: two schemas can match while public function attributes differ.

### B.4 Define post-freeze SQL evolution

Document:

- additive functions require new tests and docs but do not modify existing signatures;
- deprecated functions remain callable through the published deprecation window;
- a changed return column is breaking even if PostgreSQL accepts `CREATE OR REPLACE`;
- security corrections may tighten authorization only through the published exception process;
- internal tables may evolve through migrations unless explicitly listed as public operator contracts.

### B.5 Workstream acceptance

- Fresh and upgraded installs produce the same frozen public SQL artifact.
- Every supported SQL reference entry maps to an installed object.
- Every frozen installed object has a supported documentation entry.
- Deprecated and compatibility functions are clearly marked and tested.
- A signature or behavior-relevant attribute change fails CI.
- Public views/tables are intentionally listed; internal catalogs are not over-frozen.

## 6. Workstream C: Pipeline JSON Schema and Connector Matrix Freeze

### C.1 Resolve the supported-schema boundary

The current v1 schema contains a broad connector object and all runtime types. Before freezing, choose one unambiguous representation:

- the normative v1 schema validates the supported product path and clearly references maturity metadata for non-supported variants; or
- supported and experimental schemas are separated, with the supported v1 schema as the compatibility promise.

Do not leave a schema that appears to guarantee every experimental connector. Do not create per-connector hand-maintained schemas that drift from `connectors.toml` and runtime descriptors.

### C.2 Make supported connector variants strict

For native outbox plus the four supported sinks, the frozen schema must express:

- `schema_version = 1`;
- required and optional fields;
- exact field types and defaults;
- secret-reference-only fields;
- connector-specific unknown-key rejection;
- numeric and size limits from capabilities;
- mutually exclusive fields;
- allowed authentication/TLS modes;
- supported profile/feature availability;
- deprecated aliases and their migration path.

Runtime `config validate`, `doctor`, startup preflight, generated JSON Schema, docs, and fixtures must accept and reject the same values.

### C.3 Freeze pipeline semantics, not only syntax

Normative documentation must define:

- catalog JSONB as the authoritative pipeline configuration;
- process TOML boundaries;
- source/sink direction and ownership;
- batch-size and byte-limit behavior;
- retry and DLQ defaults;
- checkpoint and acknowledgment timing;
- secret resolution;
- unknown-key handling;
- compatibility alias behavior;
- how preview/experimental types are represented without support.

Snapshot valid and invalid examples for every supported path.

### C.4 Freeze the supported connector matrix

Use `connectors.toml` to generate a v1 supported matrix containing:

- stable connector ID and direction;
- runtime type/aliases;
- maturity;
- owner and security contact;
- production profile/platform;
- minimum/recommended service and client versions;
- capability contract;
- evidence IDs;
- deprecation state.

The matrix must render exactly one native source capability and four supported outbound destinations. Diagnostics remain diagnostics; inbound and all other connectors retain their current lower maturity unless independently promoted in a later release.

### C.5 Workstream acceptance

- Supported config variants are strict and runtime-equivalent.
- Experimental presence cannot be mistaken for v1 support.
- Valid/invalid fixtures cover all four supported sinks and native source.
- Schema drift check is deterministic.
- Connector matrix is generated only from `connectors.toml`.
- Exactly four supported destination rows and their release profiles are frozen.

## 7. Workstream D: Metrics and Health Contract Freeze

### D.1 Inventory core metrics

From a real coordinator run that exercises success, retry, permanent failure, DLQ, lag, ownership, and checkpoint transitions, capture the core metric descriptor:

- family name;
- type;
- unit/suffix;
- help text meaning;
- label names and bounded-value policy;
- when the series appears;
- reset/lifecycle semantics;
- owning subsystem.

Freeze the operational families required to answer health, lag, success, failure, retry, ownership, cleanup, and PostgreSQL-cost questions. Explicitly classify experimental connector and fan-in metrics outside the core guarantee.

### D.2 Enforce metric compatibility

CI must reject:

- renamed/removed core families;
- counter-to-gauge or gauge-to-counter changes;
- label addition/removal/rename;
- unit or semantic changes;
- unbounded labels such as payload, URL, exception text, topic, subject, or credentials.

Adding a new bounded metric is allowed after documentation and dashboard review. Dashboard and alert checks must continue to prove all referenced names exist.

### D.3 Canonicalize health behavior

Document and test:

| Endpoint | Intended contract |
|---|---|
| `/livez` | Process HTTP server is alive; returns the frozen success status/body |
| `/readyz` | Startup preflight complete, PostgreSQL reachable, coordinator ready, and no release-defined unhealthy pipeline condition |
| `/health` and `/healthz` | Either documented compatibility aliases for readiness or deprecated before freeze |
| `/metrics` | Prometheus text output and stable failure behavior |

Lock exact success/failure status codes, bodies, content types, and readiness transition semantics. Test startup, healthy operation, PostgreSQL loss, permanent pipeline failure, recovery, and shutdown.

### D.4 Align health, metrics, status, and runbooks

The same state transition must not say:

- ready through HTTP;
- unhealthy through `status`;
- healthy through a metric;
- unknown in the runbook.

Add cross-surface tests for representative states and update dashboard/alert/runbook references. Keep liveness independent of downstream reachability so orchestration does not restart a process that should remain alive for diagnosis.

### D.5 Workstream acceptance

- Core metric descriptor is generated from emitted metrics.
- Names, types, labels, units, and semantics are documented and checked.
- Health endpoints have exact status/body/content-type fixtures.
- Startup, outage, failure, recovery, and shutdown transitions agree across surfaces.
- Compatibility aliases are intentionally frozen or removed before baseline.
- No unbounded label enters the frozen core.

## 8. Workstream E: CLI Machine-Readable Contract Freeze

### E.1 Inventory machine-consumable commands

Inventory every command supporting JSON or other automation output, including at least:

- `doctor`;
- `status`;
- `config validate`;
- `config export`;
- replay operations;
- maintenance/sweep operations;
- any release-supported history or DAG command.

For each command record:

- command identity;
- shared envelope;
- success payload;
- error payload;
- null/unknown/stale representation;
- bounded diagnostic and connector codes;
- stdout/stderr routing;
- exit-code mapping;
- redaction rules.

Preview/experimental commands may remain outside the freeze, but the CLI reference must say so.

### E.2 Version and schema the shared envelope

Freeze the current envelope concepts:

- `schema_version`;
- `command`;
- `ok`;
- `observed_at`;
- `data`;
- `error`.

Freeze diagnostic fields and bounded meanings. Decide all remaining ambiguity before baseline, including whether unknown values are `null` or sentinel strings and whether partial results are success or failure. Apply one rule consistently rather than snapshotting command-specific accidents.

### E.3 Add per-command schemas and golden fixtures

Use typed serializable output structures where practical instead of spreading new untyped `serde_json::json!` shapes. Generate or maintain small JSON Schemas and exact normalized fixtures for:

- successful empty state;
- successful populated state;
- validation or operational failure;
- stale/unknown values where applicable.

Tests should deserialize representative output against the schema and verify exit codes and channel routing. Normalize timestamps and other nondeterministic values without weakening field/type assertions.

### E.4 Define evolution rules

Document:

- consumers must inspect `schema_version` and tolerate documented optional additions;
- a field rename/type change requires a new schema version;
- bounded code meanings do not change silently;
- human-readable text may improve without compatibility review;
- secrets and raw upstream errors never enter either format;
- commands outside the stable list carry no v1 machine-output guarantee.

### E.5 Workstream acceptance

- Every supported machine-readable command has a schema and fixtures.
- Shared envelope and diagnostics are consistent.
- JSON success/failure and process exit code agree.
- Unknown/stale/null behavior is uniform and documented.
- Raw secrets/errors cannot enter the output.
- A breaking output change fails CI with a command-specific diff.

## 9. Workstream F: Event Envelope Freeze

### F.1 Identify supported envelopes and transport mappings

Freeze only:

- native pg_tide JSON;
- CloudEvents 1.0 JSON.

Document for each:

- field names, types, requiredness, and defaults;
- stable event ID/deduplication key derivation;
- event type/subject meaning;
- operation values;
- payload and header representation;
- source/outbox identity;
- timestamp source and precision;
- message key and transport-header mapping;
- null and absent-field behavior;
- maximum encoded size interaction with connector capabilities.

Debezium, Maxwell, Canal, CDC JSON, and other formats remain preview/experimental unless the supported matrix independently says otherwise.

### F.2 Resolve ambiguity before snapshot

Review `RelayMessage`, native format, CloudEvents format, and connector-specific serialization together. Resolve before freeze:

- whether the native envelope needs an explicit version marker;
- which identifier is the canonical cross-retry event ID;
- whether `outbox_id`, `outbox_name`, headers, and creation time are guaranteed;
- how one logical event maps to a Kafka key, NATS message ID, webhook idempotency key, and inbox `event_id`;
- whether unsupported pg_trickle compatibility fields appear in native output;
- how batches preserve per-event identity.

If the chosen canonical shape differs from v0.46.0 output, make the change once, provide migration/compatibility documentation, and complete all connector regressions before taking the baseline.

### F.3 Add schemas and cross-connector fixtures

Create JSON Schemas and canonical fixtures for native and CloudEvents envelopes. Exercise the same event through PostgreSQL inbox, NATS, Kafka, and webhook and prove:

- field and payload equivalence within each format;
- stable IDs across retry and crash recovery;
- timestamps and headers retain documented meaning;
- connector wrappers do not silently change the envelope;
- decoding into pg_tide inbox preserves the documented fields;
- invalid version/required-field/type inputs fail explicitly.

### F.4 Publish evolution rules

Define:

- new required fields require a new envelope version;
- optional extensions must not change existing semantics;
- CloudEvents additions follow the CloudEvents extension model;
- field removal/rename/type changes wait for a major version and migration path;
- receivers must deduplicate by the documented stable ID rather than transport offset;
- no unqualified exactly-once claim follows from the envelope.

### F.5 Workstream acceptance

- Native and CloudEvents schemas match actual serialized bytes.
- Cross-connector fixtures preserve event identity and semantics.
- Versioning and extension rules are explicit.
- Retry/crash tests prove stable identifiers.
- Non-core wire formats are not accidentally frozen or advertised.
- Any final envelope correction lands before pilot artifacts are built.

## 10. Workstream G: External Production Pilots

### G.1 Establish the pilot protocol

Add a concise pilot guide and sanitized evidence template containing:

- pilot ID and profile;
- release-candidate commit and artifact digest;
- PostgreSQL, relay, connector service, deployment, and platform versions;
- topology and workload shape;
- installation and configuration outcome;
- publish/delivery latency summary;
- event and byte counts;
- relay/PostgreSQL CPU, memory, WAL, and storage observations;
- duplicates observed and deduplication boundary;
- induced failure and recovery result;
- upgrade and rollback result;
- documentation gaps and incidents;
- linked issues;
- operator sign-off.

Use public APIs and release artifacts only. No direct catalog mutation, test-only failpoint, or private setup can satisfy a pilot scenario.

### G.2 NATS pilot

Profile:

- PostgreSQL 18 native outbox;
- moderate representative event volume;
- NATS JetStream supported minimum or recommended version;
- real stream retention and duplicate window;
- HA relay deployment where the pilot topology permits.

Required scenarios:

1. Clean install and first pipeline from public docs.
2. Representative steady-state delivery and latency/resource capture.
3. Relay restart or ownership transfer.
4. NATS outage and recovery.
5. Duplicate observation inside and, where practical, outside the configured duplicate window.
6. DLQ/replay or equivalent permanent-failure diagnosis.
7. v0.46.0-to-release-candidate upgrade.
8. Relay rollback and documented recovery.

### G.3 Kafka pilot

Profile:

- supported `core-kafka` artifact;
- Kafka minimum or recommended supported version;
- explicit topic/partition/ACL setup;
- strict operational monitoring and acknowledgment requirements.

Required scenarios:

1. Install/config validation and topic delivery.
2. Representative one- and multi-partition workload.
3. Broker outage or leader unavailability and recovery.
4. Authorization failure diagnosis.
5. Relay restart after broker acknowledgment but before checkpoint commit.
6. Duplicate and per-partition ordering observation.
7. Upgrade, mixed-version window, and rollback.
8. Operator use of status, metrics, alerts, and runbook.

### G.4 PostgreSQL inbox pilot

Profile:

- separate source and destination PostgreSQL 18 systems;
- canonical remote inbox configuration;
- verified TLS and least-privilege roles.

Required scenarios:

1. Destination provisioning through public inbox APIs.
2. Transactional publish and destination deduplication.
3. Destination restart/failover and reconnect.
4. Permission or schema mismatch diagnosis.
5. Relay crash after destination commit and before source checkpoint.
6. Replay without duplicate destination effect.
7. Source extension/relay upgrade and relay rollback.
8. Capacity and cleanup observations on both databases.

### G.5 Webhook pilot

Profile:

- receiver-controlled HTTPS endpoint;
- verified certificate;
- HMAC and idempotency-key validation;
- intentional retry and timeout responses.

Required scenarios:

1. Signed successful delivery.
2. Retryable 429/5xx and timeout behavior.
3. Permanent 4xx diagnosis.
4. Ambiguous disconnect after body receipt.
5. Receiver deduplication using the stable idempotency key.
6. Certificate failure and safe diagnostic.
7. Relay restart and recovery.
8. Upgrade and rollback.

### G.6 Convert feedback into issues

Every finding gets an issue before pilot sign-off. The issue must include:

- `pilot/<profile>` label;
- P0-P3 severity;
- affected frozen surface or `non-contract`;
- sanitized reproduction/evidence;
- owner;
- target milestone;
- fix, documentation, accepted limitation, or duplicate disposition.

P0/P1 cannot be accepted limitations for v0.47.0. P2/P3 may remain only when the documented contract remains true and the release manager records why the item is not a release blocker.

### G.7 Pilot completion gate

A pilot completes only when:

- all required scenarios have outcomes;
- no unresolved P0/P1 remains;
- all feedback is linked to issues;
- evidence contains no sensitive data;
- the operator, not only a pg_tide maintainer, confirms the workflow and runbook are usable;
- the candidate commit/artifact is recorded;
- any material fix is rerun against the pilot's affected scenarios.

## 17. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Freezing before v0.46.0 is actually complete | Make the full v0.46.0 gate Phase 0 and track carry-in failures in their owning scope |
| Accidentally promising all experimental config variants | Separate the supported schema boundary and generate maturity from `connectors.toml` |
| Snapshot tests bless bad behavior | Review normative semantics first; make final corrections before creating the baseline |
| Contract tooling becomes a platform | One manifest and one standard-library check entry point; reuse existing generators |
| Opaque hashes hide meaningful drift | Store reviewable schemas/descriptors/fixtures and produce semantic diffs |
| SQL source inspection misses installed behavior | Generate from a fresh installed PostgreSQL catalog and compare upgrades to the same artifact |
| Additive JSON fields break strict consumers | Publish unknown-field rules and require compatibility review for every addition |
| Metric label changes break dashboards silently | Freeze family type/labels/units and retain dashboard/alert validation |
| Health aliases perpetuate accidental behavior | Decide deprecation or compatibility before baseline; test exact routes/status/bodies |
| CLI commands retain inconsistent unknown/null behavior | Normalize semantics before snapshot and use per-command typed schemas |
| Internal `RelayMessage` is mistaken for the wire contract | Freeze actual encoded bytes and transport mappings, not internal Rust layout |
| CloudEvents compliance is assumed from field names | Validate against CloudEvents 1.0 rules and exact fixtures |
| Pilots use different candidate builds | Record commit and artifact digest; invalidate/rerun affected evidence after material fixes |
| Pilot evidence leaks customer information | Use pseudonymous IDs, sanitized aggregates, canary scans, and consent rules |
| Pilot workload is unrepresentative | Define topology/workload shape and require failure, upgrade, rollback, and operator scenarios, not only volume |
| Feedback remains private anecdote | Require a linked issue for every finding before pilot completion |
| Primary author effectively self-reviews | Require independent discipline approvals and CODEOWNER/release-manager enforcement |
| Review approval becomes stale after fixes | Define material-change invalidation and targeted reapproval |
| Security findings cannot be public immediately | Track privately during disclosure and publish blocker status/sanitized outcome |
| Governance promises response capacity the team lacks | Use realistic roles and expectations; do not invent committees or SLAs |
| CODEOWNERS drifts from connector ownership | Check supported owner consistency against `connectors.toml` |
| P0/P1 issues are relabeled to meet a date | Publish severity rules and require recorded rationale for changes |
| A GitHub outage blocks issue query | Treat inability to prove zero blockers as a release block; rerun when evidence is available |
| Last-minute release metadata changes alter artifacts | Update metadata last, rebuild, and rerun all artifact/contract gates |
| Public beta is marketed as GA | Use explicit beta language and preserve the v1.0.0 trust-release gate |
