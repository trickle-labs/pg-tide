# pg_tide v0.46.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** Four Connectors, Fully Trusted
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Starting point:** v0.45.0 and current `main`
> **Scope rule:** Promote exactly four outbound connector surfaces through executable evidence. Do not add connectors, broaden reverse-pipeline support, or call a connector production-supported because it compiles, constructs a request, or has an evidence path that does not prove the claimed behavior.

---

## 1. Release Outcome

v0.46.0 is complete when the canonical transactional outbox can deliver through the real relay to four production-supported destinations with explicit, tested protocol contracts:

1. The production-supported destination matrix contains exactly:
   - PostgreSQL inbox;
   - NATS JetStream;
   - Apache Kafka;
   - HTTPS webhook.
2. The supported claim applies to the outbound sink path from the canonical PostgreSQL outbox. NATS, Kafka, and webhook source/reverse paths retain their independently earned maturity and are not promoted by association.
3. The native PostgreSQL outbox remains a core product source, not a fifth destination connector. `stdout` and `file` remain diagnostics, not production integrations.
4. One direction-aware connector registry records maturity, ownership, tested versions, production profiles, capability data, and exact evidence for each runtime surface.
5. One generated Rust descriptor surface drives connector lookup, compile-time availability, strict configuration, capability reporting, and factory selection. There is no second hand-maintained connector list.
6. Each supported sink declares a code-represented capability contract covering maximum batch size, ordering, acknowledgment, deduplication, retryable and permanent errors, TLS, authentication, message size, backpressure, and shutdown.
7. Pipeline validation rejects a batch or message limit that exceeds the selected sink's supported contract before the worker acquires ownership or polls the outbox.
8. Connector failures carry a stable, bounded error code and an explicit retry class. Runtime behavior never infers retryability from display strings or treats every wrapped sink error as transient.
9. Every supported connector has a black-box happy-path test that starts a fresh PostgreSQL 18 instance, installs the packaged extension, configures the pipeline through public SQL, starts the real coordinator, reaches a real service or faithful protocol endpoint, and verifies the downstream result through a public interface.
10. Every supported connector proves failure before publish, failure after downstream acceptance but before offset commit, restart recovery, and documented duplicate behavior without advancing the durable checkpoint early.
11. PostgreSQL inbox tests prove event-ID deduplication, transaction rollback, destination failover, permission denial, schema mismatch, authentication, and verified TLS.
12. NATS tests prove JetStream acknowledgment, `Nats-Msg-Id` duplicate behavior, unavailable stream handling, reconnect/recovery, subject validation, authentication, and verified TLS.
13. Kafka tests prove producer acknowledgment settings, idempotent producer configuration, broker unavailability, topic authorization failure, message-too-large handling, partition ordering, authentication, and verified TLS.
14. Webhook tests prove success/retry status policy, timeout handling, verified TLS failure, outbound HMAC signing, SSRF rejection, deterministic idempotency headers, and redirect refusal.
15. Compatibility documentation names immutable minimum and recommended versions for PostgreSQL, NATS, Kafka, connector client libraries, and relevant TLS stacks. CI runs both service-version tiers before release.
16. Every connector has a concise support runbook and a public configuration example executed in CI against the release artifact.
17. Metrics, status, doctor output, logs, dashboards, and runbooks use the same bounded connector error classes and never expose credentials, URLs with user information, request bodies, or raw upstream errors.
18. Release artifacts intentionally include each supported connector on the platforms named in the compatibility matrix. Kafka may remain in a separate supported `core-kafka` profile where native build constraints require it.
19. Registry generation fails if a supported surface has missing capabilities, mutable/unknown tested versions, incomplete evidence, an untested production profile, or evidence that belongs to a different direction.
20. v0.42.0 crash-safety, v0.43.0 operational budgets, v0.44.0 security boundaries, and v0.45.0 operator contracts remain green for all four paths.

The release does not promise exactly-once transport, promote inbound NATS/Kafka/webhook sources, add SQS or any other destination, create a generic connector SDK, or turn protocol emulators into evidence for behavior they do not reproduce.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.45.0 is a hard prerequisite

Do not begin connector promotion while the v0.45.0 release gate is red. Rerun at least:

- packaged fresh install and v0.44.0-to-v0.45.0 upgrade;
- strict pipeline validation and generated schema drift checks;
- startup preflight before ownership acquisition;
- `doctor`, `status`, stable JSON output, and exit-code contracts;
- ownership, retry, last-success, last-error, lag, and DLQ status transitions;
- liveness/readiness, dashboard, alert, and runbook-evidence checks;
- relay rollback and the supported v0.44.0/v0.45.0 rolling window;
- v0.42.0 crash-window, v0.43.0 budget, and v0.44.0 security gates.

v0.46.0 consumes those operator and reliability contracts. If the current implementation still has duplicated connector availability lists, broad untyped connector objects, or factory-only validation that v0.45.0 required to remove, finish that prerequisite in the owning v0.45.0 scope rather than creating a v0.46.0 parallel path.

### 2.2 Support is direction-specific

The public support matrix must distinguish runtime direction:

| Surface | v0.46.0 target | Meaning |
|---|---|---|
| Native PostgreSQL outbox source | Core product capability | Required source for the supported outbound product path |
| PostgreSQL inbox sink | Supported | Same-database or remote pg_tide inbox delivery |
| NATS JetStream sink | Supported | Outbox to JetStream publish path |
| Apache Kafka sink | Supported | Outbox to Kafka producer path |
| HTTPS webhook sink | Supported | Outbox to receiver-controlled HTTPS endpoint |
| NATS source | Preview unless separately proved | Not promoted by NATS sink evidence |
| Kafka source | Preview unless separately proved | Not promoted by Kafka sink evidence |
| Webhook receiver source | Preview unless separately proved | Not promoted by webhook sink evidence |
| `stdout` and `file` | Diagnostic | Never presented as production integrations |
| All other source/sink types | Preview or experimental | No v0.46.0 promotion |

Split any bidirectional registry row whose source and sink evidence differs. A test for a sink must not fill a source evidence field, and a source test must not promote a sink.

Generated README and support pages must render core source capabilities, production destination connectors, diagnostics, preview, and experimental surfaces as separate categories. The roadmap's "exactly four" rule applies to destination integrations; it does not demote the canonical outbox source.

### 2.3 PostgreSQL inbox has one canonical public contract

Resolve the current naming and behavior mismatch before v0.47.0 freezes the API:

- `sink_type = "inbox"` is the canonical PostgreSQL inbox destination.
- `sink.inbox` is the canonical inbox name.
- An omitted `sink.postgres_url` selects the relay's PostgreSQL database.
- A `sink.postgres_url` secret reference selects a remote PostgreSQL destination.
- Both modes write the pg_tide inbox schema and deduplicate on `event_id`.
- The existing `pg_outbox` runtime type is treated as a compatibility alias for the remote inbox behavior it actually implements. It is not advertised as remote outbox replication or counted as another supported connector.
- Documentation using unsupported `target_url`, `inbox_name`, or remote-outbox semantics is corrected. Do not add aliases solely to preserve examples that never matched runtime behavior.

The compatibility alias must route through the canonical parser, capability descriptor, error classifier, and factory. Its deprecation/freeze decision must be recorded before v0.47.0; it may not retain separate behavior.

### 2.4 One capability vocabulary

Extend the existing connector registry schema instead of introducing a second manifest. Each direction-specific surface must declare:

| Capability | Required representation |
|---|---|
| Batch limit | Maximum messages per publish and any byte-based batch bound |
| Ordering | None, per pipeline, per subject, or per Kafka partition, with the concurrency assumption stated |
| Acknowledgment | The exact downstream event after which `publish` may return success |
| Deduplication | Durable destination constraint, broker dedup window, producer-session idempotence, receiver contract, or none |
| Retry classes | Stable bounded connector error codes that may be retried |
| Permanent classes | Stable bounded connector error codes that pause/fail the pipeline |
| TLS | Required/optional modes, certificate verification behavior, and supported trust configuration |
| Authentication | Only modes exercised by release CI |
| Message limit | Maximum encoded event size and whether the limit is local or service-config dependent |
| Backpressure | How queue saturation, rate limiting, and publish timeouts surface |
| Shutdown | Flush/drain behavior, timeout, and the point after which no new publish starts |

Use enums and bounded values in generated Rust, not free-form strings consumed by runtime code. Human descriptions may accompany those values in generated documentation.

The registry is authoritative for static capability facts and release evidence. Connector implementations remain authoritative for protocol operations, but must return only error codes declared by their descriptor. CI joins the two and rejects drift.

### 2.5 Capability values are conservative, tested limits

Do not copy theoretical protocol maxima into the product contract. During baseline work, choose a concrete supported maximum for each sink from:

1. the lower bound of the minimum supported service version's default limit;
2. the relay's measured memory and latency budgets from v0.43.0;
3. the connector client's encoded request behavior;
4. the largest value exercised in compatibility CI.

Every supported descriptor must contain a concrete value by release. `unknown`, `unbounded`, mutable `latest`, and prose such as "depends on the server" are not valid supported values. If an upstream limit is operator-configurable, declare the conservative pg_tide limit and document how validation reports a stricter downstream limit.

### 2.6 Delivery and duplicate semantics remain at-least-once

The coordinator checkpoint remains authoritative and advances only after the sink's declared acknowledgment boundary. Connector-specific deduplication narrows duplicate effects but does not change transport to exactly-once.

Required language:

- **PostgreSQL inbox:** duplicate `event_id` values are durably ignored by the destination unique constraint.
- **NATS JetStream:** `Nats-Msg-Id` suppresses duplicate storage only within the stream's configured duplicate window.
- **Kafka:** idempotent producer mode prevents a class of producer retry duplicates within the producer session; it does not deduplicate a replay after relay restart for consumers.
- **Webhook:** pg_tide supplies a stable idempotency key; the receiver decides whether and how long to deduplicate it.

For NATS and Kafka, a multi-message publish can succeed for a prefix before a later record fails. The coordinator still withholds the batch checkpoint and retries according to the v0.42.0 state machine. Tests and docs must make the resulting duplicate window explicit rather than adding a second offset authority.

### 2.7 Connector errors are typed before coordinator policy

Replace the current assumption that a generic `SinkPublish` wrapper is transient. Use one connector error model containing at least:

- connector ID and direction;
- stable bounded code;
- retry class (`transient` or `permanent`);
- safe operator summary;
- optional retry-after duration;
- redacted internal source for logs only.

The coordinator consumes the explicit class. Metrics, status, JSON diagnostics, and DLQ entries consume the bounded code and class. Raw SDK errors, SQL text, HTTP bodies, broker addresses, URLs, credentials, and certificate contents never become public fields or metric labels.

Do not classify by substring matching. Each connector maps protocol-native status codes, SQLSTATE values, SDK error enums, and validation failures at its boundary.

### 2.8 Real services and faithful boundaries

Use real protocol implementations for release evidence:

- PostgreSQL inbox: two PostgreSQL 18 instances for remote delivery and failover scenarios;
- NATS: a real `nats-server` started with JetStream, a configured stream, and real publish acknowledgments;
- Kafka: a real Apache Kafka broker in KRaft mode and a real consumer that verifies topic records;
- webhook: an in-process or child-process HTTP server is acceptable because it implements the actual HTTP/TLS protocol boundary, but TLS, redirects, delayed responses, disconnects, and status policies must be controllable.

A mock object, direct SDK publish, database seed, request-construction assertion, or hand-written fake is unit/contract evidence only. It cannot fill the end-to-end or protocol-outcome fields.

### 2.9 Compatibility tiers are immutable and reproducible

For each external service, record:

- minimum supported version;
- current recommended version;
- exact container image tag and digest used by CI;
- connector client crate version from `Cargo.lock`;
- relevant TLS implementation/version;
- supported authentication modes;
- supported release platforms and build profile.

No supported row may contain `latest` or `unknown`. Pull-request CI may run the recommended tier; scheduled and release CI must run both minimum and recommended tiers. Version changes require a registry diff, compatibility run, and release-note entry.

### 2.10 Supported build profiles remain narrow

Keep production packaging explicit:

- `core`: built-in PostgreSQL inbox, NATS, webhook, and diagnostics clearly labeled as diagnostics;
- `core-kafka`: `core` plus Kafka on platforms where the native dependency is built and tested;
- `experimental-full`: evaluation only and never production-support evidence.

If Kafka cannot be built or exercised on a release platform, that artifact must not imply Kafka support. Publish at least one tested `core-kafka` production artifact and image for every platform named in the Kafka compatibility row.

### 2.11 Release metadata changes last

Complete behavior, capability generation, compatibility tests, runbooks, examples, packaging, and release evidence before changing:

- workspace package versions;
- `pg_tide.control` files;
- Helm chart/application versions;
- changelogs and release notes;
- lockfile package versions caused only by the release bump.

No SQL migration is expected for connector-only work. Add one only if a reviewed public SQL contract genuinely requires it; do not create a version migration merely to mark the release.

## 4. Workstream A: Directional Registry, Capabilities, and Evidence Integrity

### A.1 Version the connector registry schema

Update `connectors.toml` and `scripts/generate_connector_surface.py` as one schema migration:

- increment the registry schema version;
- split rows when source and sink maturity/evidence differ;
- retain stable runtime type and compatibility-alias fields;
- add structured capability fields required by Section 2.4;
- add supported platform/profile and service-version records;
- replace file-only evidence arrays with records containing scenario ID, level, direction, test target, test name, and CI job;
- keep owner, security contact, docs, and upgrade/rollback evidence;
- reject deprecated free-form or ambiguous supported fields.

Do not maintain both old and new schemas indefinitely. The generator should give one actionable migration error, and the repository should contain only the new canonical shape after conversion.

### A.2 Split bidirectional maturity

Create independent records for:

- NATS sink and NATS source;
- Kafka sink and Kafka source;
- webhook sink and webhook source.

Promote only sink records after all evidence passes. Preserve the current source maturity conservatively. A shared Cargo feature is allowed; a shared feature does not imply shared support.

Treat `pg_outbox` as an alias attached to the PostgreSQL inbox sink record rather than a separate production connector. Keep diagnostics in a non-connector category.

### A.3 Generate Rust descriptors from the registry

Extend the existing generator to emit a checked-in Rust module containing only validated static data:

- connector/surface ID;
- runtime type and aliases;
- direction;
- Cargo feature/compiled availability;
- config schema selector;
- capability enums and numeric bounds;
- declared stable error codes;
- supported profile/platform tags.

Runtime preflight and factory lookup use the generated descriptors. Connector protocol code does not parse TOML at runtime. CI regenerates and fails on drift.

Do not generate behavior or large match-arm implementations. Generated code is data; hand-written connector modules retain protocol logic.

### A.4 Generate public capability and compatibility pages

Generate from the same records:

- README destination connector table;
- `docs/src/support/connector-compatibility.md`;
- `docs/src/support/connector-release-checklist.md`;
- a connector capability reference with one section per supported sink;
- build profile membership and platform limitations.

Every generated page must distinguish:

- product source capability;
- supported destination connector;
- diagnostic;
- preview source/sink;
- experimental source/sink;
- compatibility alias.

### A.5 Validate evidence semantically

The generator/release check must reject:

- missing files, test targets, named test functions, or workflow jobs;
- an evidence record whose named test does not run in the named job;
- unit/contract tests cited as end-to-end;
- source evidence cited for a sink or vice versa;
- direct SDK/request tests cited as real-coordinator evidence;
- one scenario reused for a failure it does not inject/assert;
- mutable or unknown compatibility versions;
- supported rows missing any production-supported category;
- production profiles not built and tested by release CI;
- any fifth destination connector rendered as production-supported.

Prefer explicit test IDs in a small manifest to guessing semantics from filenames. Do not create a second maturity registry; evidence IDs join back to the connector record.

### A.6 Workstream acceptance

- Registry schema and generated outputs are deterministic.
- Runtime and docs consume the same direction-specific capability records.
- Supported evidence points to named, executing scenarios.
- Generated pages show exactly four supported destination connectors.
- NATS/Kafka/webhook source maturity is independent.
- `scripts/generate_connector_surface.py --check` fails on every prohibited drift case.

## 5. Workstream B: Shared Runtime Capability and Failure Contract

### B.1 Route strict validation through connector descriptors

Replace the broad connector field allowlist with connector-specific parsers/schemas for the four supported sinks first. Validate:

- required and unknown fields;
- secret-reference-only fields;
- mutually exclusive local/remote inbox settings;
- batch message and byte limits;
- subject/topic/URL/inbox identifier syntax;
- timeout and retry bounds;
- authentication/TLS mode support;
- feature/profile availability;
- unsupported compatibility aliases or legacy fields.

Validation must run in `config validate`, `doctor`, and startup preflight before ownership or polling. The factory receives validated connector config rather than repeating raw JSON lookups.

Experimental connector parsing may remain on the existing path if needed, but it may not weaken strict validation for supported rows or appear in generated supported schema variants.

### B.2 Add typed connector failures

Introduce one bounded connector failure type and map it to existing relay/coordinator policy. Required common categories include:

- unavailable/connection;
- timeout;
- throttled/backpressure;
- authentication;
- authorization;
- TLS verification;
- invalid destination/configuration;
- message too large;
- protocol rejection;
- shutdown/flush failure;
- unknown internal error.

Each concrete code has one declared retry class. Unknown SDK errors default to the safer documented behavior, are redacted, and are counted separately; they do not expose an upstream string as a stable API.

Add unit tests for each protocol-to-code mapping and coordinator tests proving transient errors retry while permanent errors pause/fail according to v0.42.0.

### B.3 Preserve the acknowledgment state machine

For all four sinks:

1. `publish` returns success only after the declared downstream acknowledgment.
2. The coordinator writes last-success and advances the source checkpoint only after full batch success.
3. Partial downstream success returns failure and leaves the checkpoint unchanged.
4. Retry uses the same stable event IDs/idempotency metadata.
5. Permanent failure follows configured DLQ/pause policy without checkpoint advancement.
6. Crash injection after downstream acceptance and before checkpoint commit proves the documented duplicate outcome.

Do not add connector-local durable offsets.

### B.4 Enforce message and batch limits before I/O

Measure the actual encoded payload sent by each sink. Reject over-limit input with the connector's permanent message-too-large code before network I/O when determinable.

Pipeline `batch_size` must not exceed the sink's maximum. For byte-limited protocols, either split at message boundaries before publish using an existing coordinator batching facility or reject the batch predictably. Never split one logical event silently.

Tests cover exactly-at-limit and one-over-limit cases for both message count and encoded bytes.

### B.5 Make backpressure and shutdown observable

For each supported sink:

- bound in-flight work and internal queueing;
- surface queue saturation/rate limiting as a declared transient class;
- honor coordinator cancellation without abandoning an acknowledged/uncheckpointed ambiguity silently;
- stop accepting new publishes during shutdown;
- flush/drain within the configured timeout;
- return a typed close failure if the drain cannot complete;
- update bounded metrics/status at the same transition points.

Do not add an independent connector scheduler or unbounded buffering layer.

### B.6 Replace unconditional health claims

`is_healthy()` or its v0.45.0 descriptor/doctor replacement must not return unconditional success for NATS, Kafka, or webhook.

- Constructor/preflight validates static config and safe connectivity/auth where supported.
- Runtime health derives from recent real publish/error state and bounded protocol probes that cannot create user data.
- Webhook does not issue arbitrary health requests to a user endpoint unless an explicit safe health URL contract exists; it reports config/preflight plus recent publish state instead.
- Unknown is distinct from healthy.

### B.7 Workstream acceptance

- Supported sink config is strict and capability-bounded before startup.
- No generic wrapped sink error is automatically transient.
- All runtime connector codes are declared in the registry.
- Checkpoint timing remains identical across connectors.
- Limit, backpressure, partial success, and shutdown tests pass.
- Health never claims success without evidence.

## 6. Workstream C: Shared Black-Box and Fault Harness

### C.1 Build one connector scenario harness

Reuse the packaged-extension and coordinator harness from the authoritative NATS E2E path. Parameterize only common orchestration:

- fresh PostgreSQL 18 source instance;
- packaged extension install;
- public outbox and pipeline configuration;
- real relay process/coordinator;
- destination lifecycle;
- public message publish;
- downstream observation;
- checkpoint/status/metric observation;
- relay stop/restart;
- safe log capture and secret canaries.

Connector-specific protocol setup and assertions stay in connector test modules. Do not hide all scenarios behind a generic test loop whose failure lacks connector context.

### C.2 Add precise coordinator fault points

Use the existing test-only failpoint feature to inject only the windows required by the production-supported checklist:

- before the sink publish starts;
- after downstream acknowledgment but before source checkpoint commit;
- during retry backoff;
- during graceful shutdown/flush where applicable.

Failpoints must be absent from production profiles and checked by the same build guard used for v0.42.0 crash tests.

### C.3 Assert public outcomes

Every end-to-end connector scenario must assert:

- exact downstream event IDs and payloads;
- the sink-specific acknowledgment condition;
- no early source checkpoint;
- final checkpoint after durable success;
- duplicate count/identity after crash recovery;
- retry/permanent status and bounded error code;
- success/failure/retry/lag metrics;
- readiness behavior where a permanent connector fault degrades service;
- absence of canary credentials/payloads from logs, status, metrics, and command JSON.

Do not use direct catalog inserts or private test tables to configure the pipeline. Direct SQL reads may verify durable state only when no public read API exists and the table is itself the documented authority.

### C.4 Classify test levels honestly

Keep separate names and CI jobs for:

- unit mapping/validation tests;
- protocol contract tests;
- multi-component integration tests;
- public-API end-to-end tests;
- crash/failure chaos tests;
- compatibility matrix runs.

Rename or rewrite existing tests whose comments and behavior do not match. Database-only Kafka tests and raw-client webhook tests cannot retain connector integration/e2e evidence labels.

### C.5 Workstream acceptance

- All four connectors use the same public-path orchestration where appropriate.
- Every required failure window is deterministic and named.
- Tests verify downstream outcomes, not request construction.
- Evidence levels match actual boundaries.
- Production artifacts contain no test failpoints.

## 7. Workstream D: PostgreSQL Inbox Promotion

### D.1 Unify local and remote inbox construction

Route canonical `inbox` config to:

- the existing relay database client when `postgres_url` is absent;
- a destination-specific verified PostgreSQL connection when `postgres_url` is present.

Both paths use the same validated inbox identifier, batch insert shape, dedup semantics, capability descriptor, and SQLSTATE classifier. Route `pg_outbox` through the remote branch as a compatibility alias.

Do not implement remote outbox federation in this release.

### D.2 Make remote recovery explicit

The remote sink must recover from a destination connection loss without reconstructing the entire process manually:

- detect broken connection/session state;
- reconnect using the configured TLS/auth policy;
- retry only errors classified transient;
- preserve the same event IDs and batch semantics;
- refuse to checkpoint until the destination transaction commits;
- stop retrying on auth, permission, missing-schema, or incompatible-table failures.

Destination failover testing must use a real restarted/replaced PostgreSQL destination or a faithful HA topology, not only a refused initial port.

### D.3 Define the SQL acknowledgment and error contract

Acknowledgment occurs when the destination `INSERT ... ON CONFLICT` transaction commits. At minimum classify:

- connection exception/server restart as transient;
- serialization/deadlock as transient with bounded retry;
- authentication failure as permanent;
- insufficient privilege as permanent;
- undefined table/column or incompatible type as permanent schema mismatch;
- oversized/invalid payload as permanent;
- duplicate `event_id` as successful deduplication, not an error.

Keep raw SQL and server error detail out of public diagnostics.

### D.4 Complete the PostgreSQL failure matrix

Add named scenarios for:

1. Public outbox to a remote pg_tide inbox happy path.
2. Same-database inbox happy path.
3. Repeated event IDs insert one destination row.
4. Crash after destination commit but before source checkpoint creates no second inbox row.
5. A bad row causes the batch statement to roll back and leaves the checkpoint unchanged.
6. Destination restart/failover reconnects and drains pending messages.
7. Login/authentication denial is permanent and redacted.
8. `INSERT` permission denial is permanent and redacted.
9. Missing/incompatible inbox schema is permanent with a safe next action.
10. `sslmode=verify-full` succeeds with the trusted test CA and fails with wrong/untrusted identity.
11. Graceful shutdown completes or reports a typed outstanding-operation failure.

Use `tide.inbox_create()` on the destination and public pipeline APIs on the source.

### D.5 Correct docs and add the runbook

Update the sink guide to describe the canonical local/remote fields, acknowledgment, transactionality, event-ID deduplication, TLS/auth modes, limits, failover, and duplicate implications. Replace the remote-outbox page with a compatibility note or remove it from current navigation if it describes unsupported behavior.

Add a PostgreSQL inbox runbook covering connectivity, TLS, permission denial, schema mismatch, failover, lag, duplicates, and safe replay. Its example must run against two release PostgreSQL instances in CI.

### D.6 Workstream acceptance

- Canonical local and remote inbox config passes strict validation.
- Destination commit is the only success boundary.
- All eleven named scenarios pass.
- Docs and runtime names agree.
- `pg_outbox` cannot make a separate support claim.

## 8. Workstream E: NATS JetStream Promotion

### E.1 Test JetStream rather than core NATS

Replace mutable/direct transport setup with a pinned `nats-server` configured for JetStream. Every integration/E2E case must:

- create a stream whose subject matches the pipeline;
- publish through `NatsSink` and the real coordinator;
- wait for the JetStream publish acknowledgment;
- fetch/consume the stored message from JetStream;
- assert `Nats-Msg-Id`, subject, payload, and order relevant to the declared contract.

Direct core NATS pub/sub may remain a narrow SDK smoke test but is not supported connector evidence.

### E.2 Validate subjects before startup

Use protocol-correct subject validation for fixed subjects and rendered templates:

- reject empty subjects, whitespace, invalid tokens, and publish wildcards;
- validate templates structurally before startup;
- render representative boundary values during config validation where necessary;
- return a permanent safe config code before ownership/polling.

Do not rely on a publish-time server string to discover invalid configuration.

### E.3 Map NATS behavior to the common contract

Declare and test:

- publish success only after the JetStream ack future resolves;
- stream/subject not configured as permanent destination configuration;
- temporary server/network unavailability as transient;
- auth/permission denial as permanent;
- message above server/product limit as permanent;
- broker pressure/timeouts as transient with bounded retry;
- ordering scope as actually observed for the configured subject and sequential publish path;
- duplicate suppression bounded by the stream duplicate window;
- close/drain behavior and timeout.

Use safe protocol metadata for classification; do not parse display messages.

### E.4 Complete the NATS failure matrix

Add named scenarios for:

## 10. Workstream G: HTTPS Webhook Promotion

### G.1 Exercise the real sink and coordinator

Rewrite webhook evidence so requests originate from `WebhookSink` through the real coordinator. The controllable receiver records:

- exact raw body bytes;
- method, path, headers, and connection properties;
- request count and timing;
- TLS peer behavior;
- configured response status, delay, disconnect, and redirect.

Raw `reqwest::Client` tests remain receiver fixtures only and cannot prove sink behavior.

### G.2 Define HTTP status and timeout policy

Lock one policy in code, capabilities, tests, and docs:

- configured 2xx responses are success;
- 408, 425, 429, and 5xx are transient/retryable, honoring a bounded safe `Retry-After` where supported;
- other 4xx responses are permanent request/auth/destination failures unless a reviewed exception is declared;
- 3xx responses are not followed and are permanent redirect rejection;
- connect/read/overall timeout is transient unless caused by permanent TLS/config validation;
- response bodies are never included in public errors.

Do not make the status policy user-programmable in v0.46.0 beyond narrowly justified existing options.

### G.3 Add outbound HMAC signing

Implement the documented sink-side signing fields using resolved secret references. Lock:

- one supported algorithm for v0.46.0 (HMAC-SHA256);
- signature header name and encoding;
- timestamp header and signed timestamp/body format if replay resistance is claimed;
- signature over the exact bytes sent on the wire;
- no secret or full signature in logs/status/metrics;
- constant-time receiver verification in the test fixture.

Inbound webhook signature verification is a separate preview source capability and is not evidence for outbound signing.

### G.4 Make idempotency deterministic

Define the `Idempotency-Key` contract:

- a one-message request uses the stable event dedup key;
- a multi-message request uses a versioned deterministic digest of the ordered event IDs;
- an identical retry sends identical body bytes, signature inputs, and idempotency key;
- a different batch cannot reuse a key merely because it has the same last event;
- receivers remain responsible for durable deduplication and retention.

Document the batch envelope and key algorithm before v0.47.0 freezes it.

### G.5 Preserve SSRF and redirect safety

Test both validation-time and connect-time protections:

- HTTPS required in production;
- loopback, private, link-local, metadata, and prohibited host targets rejected under the supported policy;
- redirects disabled and never used to bypass target validation;
- ambient proxy variables do not redirect supported requests;
- DNS resolution/rebinding behavior follows the v0.44.0 threat model;
- explicit development-only HTTP/private-network escape hatches are excluded from production support evidence and clearly labeled.

### G.6 Complete the webhook failure matrix

Add named scenarios for:

1. Accepted 2xx request and checkpoint advancement.
2. Retryable 408/425/429/5xx responses with no early checkpoint.
3. Permanent 4xx response and bounded safe diagnostic.
4. Connect/read timeout and recovery.
5. Trusted HTTPS success.
6. Expired/untrusted/hostname-mismatch TLS failure.
7. Valid HMAC signature over exact body bytes.
8. Wrong signing secret rejection at the receiver with no secret leakage.
9. SSRF target rejection before polling.
10. Stable single-message idempotency key across retry.
11. Stable, collision-resistant batch idempotency key across retry.
12. Redirect refusal without contacting the target location.
13. Receiver disconnect after body receipt, documenting duplicate ambiguity.
14. Message/batch size boundary.
15. Graceful shutdown during an in-flight request.

### G.7 Add the webhook runbook and executable example

Cover status classes, timeout, receiver capacity, TLS chain/hostname, HMAC rotation, idempotency retention, SSRF refusal, redirects, duplicates after ambiguous disconnect, lag, DLQ, and safe replay. CI runs the example against a TLS receiver and verifies signature and idempotency headers.
