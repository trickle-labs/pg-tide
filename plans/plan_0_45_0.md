# pg_tide v0.45.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** Operators First
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Starting point:** v0.44.0 and current `main`
> **Scope rule:** Make the supported product straightforward to start, inspect, validate, upgrade, roll back where safe, and recover. Do not add connectors, create a second control plane, or hide unsupported operations behind optimistic status output.

---

## 1. Release Outcome

v0.45.0 is complete when a normal operator can manage pg_tide through documented public commands and supported deployment tooling without editing catalog rows directly:

1. The primary command flow is explicit and stable:

   ```text
   pg-tide doctor
   pg-tide status
   pg-tide config validate
   pg-tide config export
   pg-tide run
   pg-tide replay ...
   pg-tide maintenance sweep ...
   ```

2. The previous commandless daemon start, `validate-config`, and top-level `sweep` remain compatibility aliases for v0.45.0, emit a deprecation warning, and execute the same code paths as the canonical commands.
3. Commands used by automation support one versioned JSON envelope. JSON output contains only command results on stdout; logs, warnings, and deprecations go to stderr.
4. Exit codes are documented, stable, and covered by subprocess tests. The same failure category produces the same exit code across commands.
5. Every operator-facing failure identifies the failed component, a safe likely cause, and one concrete next action. Raw connector errors, URLs, credentials, payloads, and SQL are not exposed.
6. `doctor` verifies relay/extension compatibility, PostgreSQL connectivity and TLS, required schemas and migrations, effective privileges, advisory-lock behavior, catalog readability, configured connectors, and startup preflight health.
7. `status` reports each configured pipeline's enabled state, ownership, lag, last durable success, last safe error, retry state, and unresolved DLQ depth. Unknown or stale values are explicit rather than represented as zero or healthy.
8. Catalog rows remain the only authoritative pipeline configuration. Process TOML contains process settings only and cannot define or override pipelines.
9. Process TOML and catalog pipeline configuration reject unknown keys. Enabled pipelines are fully validated before any worker acquires ownership or starts polling.
10. `pg-tide config export` emits deterministic, canonical, secret-safe catalog configuration that conforms to a checked-in versioned JSON Schema.
11. One connector registry drives feature availability, strict config parsing, schema generation, validation, doctor output, and worker construction. Connector maturity remains sourced from `connectors.toml`.
12. Health, metrics, status, dashboards, and alerts agree on pipeline state and answer the roadmap's primary operational questions without mislabeled proxy metrics.
13. Liveness and readiness are separate. A failed pipeline makes the relay unready but does not cause Kubernetes to restart a live process indefinitely.
14. Fresh v0.45.0 install, v0.39.0-to-v0.45.0 upgrade, and v0.44.0-to-v0.45.0 upgrade are tested through packaged extension artifacts rather than equivalent SQL-chain shortcuts.
15. The supported rolling order is explicit: upgrade the extension to v0.45.0, then replace relay instances one at a time. A v0.44.0 relay remains compatible with the v0.45.0 extension during that window.
16. Relay binary rollback from v0.45.0 to v0.44.0 is automated and tested against a v0.45.0 extension. Extension rollback is supported only for the additive v0.45.0 migration and only through an explicit reverse migration.
17. A CloudNativePG example exercises extension upgrade, mixed relay versions, primary failover, and post-upgrade verification.
18. Every required incident has one indexed runbook with symptoms, checks, commands, expected evidence, safe recovery, rollback/escalation criteria, and an executable or recorded rehearsal.
19. Release CI links every v0.45.0 operational claim to a command contract test, upgrade scenario, dashboard/alert check, or runbook rehearsal.

The release does not add a web control plane, a second pipeline store, automatic catalog repair, zero-downtime guarantees for irreversible historical migrations, or exactly-once transport claims.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.44.0 is a hard prerequisite

Do not start operator-surface implementation while the v0.44.0 gate is red. Rerun at least:

- the canonical public SQL-to-NATS path;
- v0.42.0 crash-window and HA ownership tests;
- v0.43.0 retention, cleanup, partitioning, and operational budget checks;
- v0.44.0 privilege, fail-closed, TLS, SSRF, secret-redaction, dependency, and artifact gates;
- fresh v0.44.0 install and v0.43.0-to-v0.44.0 upgrade parity;
- `core` build and generated connector registry checks.

Operator tooling must not turn a reliability or security failure into a better-looking status page. Repair any failing prerequisite in its owning release before building v0.45.0 on top of it.

### 2.2 The canonical CLI is explicit

Use this command tree:

```text
pg-tide
├── doctor
├── status
├── config
│   ├── validate
│   └── export
├── run
├── replay
│   ├── preview
│   ├── execute
│   └── ...
└── maintenance
    └── sweep
```

Compatibility behavior:

| Existing invocation | v0.45.0 behavior | Removal target |
|---|---|---|
| `pg-tide` with no subcommand | Run the daemon, warn that `pg-tide run` is canonical | v0.47.0 API freeze |
| `pg-tide validate-config ...` | Alias `pg-tide config validate ...` | v0.47.0 API freeze |
| `pg-tide sweep ...` | Alias `pg-tide maintenance sweep ...` | v0.47.0 API freeze |

Aliases must call the canonical command handler, produce the canonical JSON shape and exit code, and differ only by a stderr deprecation warning. Do not retain separate parsing or execution branches.

`run` is the only canonical long-running command. Operator commands must never fall through into daemon startup.

### 2.3 One output contract

Add a global output selector:

```text
--output text|json
```

Text remains the interactive default. JSON is opt-in and stable for `doctor`, `status`, `config validate`, `config export`, replay result/preview output, and maintenance results.

Use one envelope:

```json
{
  "schema_version": 1,
  "command": "doctor",
  "ok": false,
  "observed_at": "2026-01-01T00:00:00Z",
  "data": null,
  "error": {
    "code": "postgres.permission_denied",
    "component": "postgres.catalog",
    "message": "The relay cannot read pipeline configuration.",
    "likely_cause": "The login is missing the tide_relay role or required grants.",
    "next_action": "Run pg-tide doctor as the relay login and apply the documented role provisioning."
  }
}
```

Rules:

- `schema_version` is an integer and changes only for a breaking JSON shape.
- `command`, `ok`, `observed_at`, `data`, and `error` are always present.
- Success uses `error: null`; failure uses `data: null` unless the command explicitly supports a partial result.
- Arrays are deterministically ordered.
- Durations use integer milliseconds; timestamps use UTC RFC 3339; byte and message counts use integers.
- Unknown, stale, and not-applicable are distinct values, not zero.
- JSON stdout contains exactly one document, except documented JSON Lines replay streams.
- Logs and warnings never share stdout with JSON.
- Secret references may be returned; resolved secret values may not.
- Rust type snapshots and checked-in JSON examples are part of the compatibility contract.

Do not invent a different envelope per command or expose unstable third-party error strings as machine-readable fields.

### 2.4 Exit-code taxonomy

Keep the taxonomy small:

| Code | Meaning | Examples |
|---:|---|---|
| `0` | Complete success; all required checks passed | Healthy doctor, valid config, complete sweep |
| `1` | Operational/runtime failure | PostgreSQL unavailable, query failed, sink operation failed |
| `2` | CLI usage error | Unknown flag, missing required argument, invalid enum |
| `3` | Validation or compatibility failure | Unknown config key, unavailable connector feature, incompatible extension, failed doctor prerequisite |
| `4` | Partial multi-target result | Some requested pipelines/outboxes succeeded and others failed |

Warnings alone return `0`. A command that cannot determine a required value returns a failure code; it does not downgrade the result to a warning merely to preserve availability.

Centralize the mapping from typed error category to exit code. Remove direct command-local `process::exit` calls except the final process boundary.

### 2.5 Catalog and process configuration have separate jobs

The authoritative split is:

| Configuration | Authority | Examples |
|---|---|---|
| Process TOML and process CLI flags | One relay process | PostgreSQL URL reference, metrics bind address, log format, relay group, shutdown timeout, poll/reconcile intervals |
| `tide.relay_outbox_config` / `tide.relay_inbox_config` | Pipeline behavior | Source, sink, transforms, retry policy, DLQ, batching, encoding |

Requirements:

- Process TOML cannot contain pipeline definitions.
- CLI flags override TOML only when the operator explicitly supplied the flag. Clap defaults must not overwrite configured TOML values.
- `RelayConfig` and every nested process setting use strict unknown-field rejection.
- The vestigial config-mode setting is removed from canonical examples. A recognized legacy field may be accepted for v0.45.0 only when it produces a deprecation warning and has no ability to change pipeline authority.
- Configuration precedence is documented as defaults, then TOML, then explicitly supplied CLI values.
- `config export` reads catalog configuration; it does not serialize process secrets or invent a combined file.

### 2.6 Pipeline configuration is typed, strict, and versioned

Add `schema_version: 1` to the canonical exported pipeline representation. Existing catalog rows without the field are interpreted as v1 only when their complete shape validates.

Use strict typed Rust configuration as the runtime validator and generate the public JSON Schema from the same types. Do not add a second hand-written validation language.

The generated schema must:

- use JSON Schema Draft 2020-12;
- set `additionalProperties: false` at every owned object level;
- discriminate source, sink, encoding, retry, DLQ, transform, and connector-specific variants;
- express required fields, enums, numeric bounds, array bounds, and secret-reference syntax;
- identify fields that are accepted only when a Cargo feature is compiled;
- include descriptions and examples without resolved credentials;
- be checked in as `schemas/pipeline-config-v1.schema.json`;
- fail CI when regeneration changes the checked-in file.

Connector-specific configuration structs become the input to factories. Remove manual `serde_json::Value` getters after each connector is migrated so runtime behavior and schema cannot drift.

### 2.7 One connector registry, one startup preflight

Add one runtime connector descriptor registry containing:

- canonical connector name and aliases;
- source/sink direction;
- compiled feature requirement;
- strict config parser/schema reference;
- validation function;
- factory entry point.

Do not duplicate connector maturity in this registry. Supported/preview/experimental status and ownership continue to derive from `connectors.toml`.

Before worker reconciliation:

1. Load all catalog rows.
2. Validate the structural schema and unknown keys for every row, including disabled rows.
3. Resolve connector names and report whether the required feature is compiled.
4. Fully validate enabled rows, including semantic bounds, secret references, TLS policy, and factory preconditions.
5. Report disabled rows that reference unavailable connectors as warnings; they cannot start until fixed or the feature is installed.
6. Return one sorted aggregate report.
7. Start no workers and acquire no ownership locks if any enabled row or any row's structural schema is invalid.

`config validate` runs the same preflight code. It must not create workers, mutate offsets, acquire pipeline ownership, or perform arbitrary network publishes. Connector checks that require network access are doctor checks and are clearly labeled.

### 2.8 `config export` is canonical and secret-safe

`pg-tide config export`:

- exports one named pipeline or all visible pipelines;
- emits canonical v1 JSON in deterministic pipeline-name/direction order;
- preserves `${env:...}` and `${file:...}` references;
- never resolves or returns secret values;
- omits runtime status, checkpoints, DLQ payloads, and ownership;
- includes enabled/disabled state and enough identity to round-trip through public configuration APIs;
- validates each exported row before emitting it;
- fails rather than exporting a partly understood row;
- supports text only as a concise summary; JSON is the portable representation.

Import or mutation is not added in v0.45.0. Existing public SQL configuration APIs remain the write path.

### 2.9 `doctor` is a deterministic preflight, not a bag of best-effort probes

Doctor checks are grouped and ordered:

1. **Process configuration:** strict parse, required process values, secure secret references.
2. **PostgreSQL connection:** DNS/connectivity, negotiated TLS, server version.
3. **Extension compatibility:** extension installed version, relay binary version, allowed mixed-version window.
4. **Schema and migrations:** required schemas, catalog objects, migration chain/version markers, no partially applied v0.45.0 objects.
5. **Privileges:** effective access for catalog reads, checkpoints, DLQ, status, maintenance, and configured directions.
6. **Advisory locks:** canonical key derivation and safe acquire/release using a doctor-specific key that cannot steal pipeline ownership.
7. **Catalog configuration:** the exact startup preflight over every row.
8. **Connectors:** compiled availability for all configured connectors and safe connectivity/authentication probes where a connector supports them.
9. **Operational state:** stale owners, migration warnings, unresolved permanent failures, DLQ growth, and cleanup staleness.

Each check returns:

```text
id, component, status(pass|warn|fail|skip), summary, safe_detail,
likely_cause, next_action, duration_ms
```

Required-check errors are failures, not `false`, empty rows, or missing-object guesses. Skips require an explicit reason. Human and JSON output render the same result model.

### 2.10 Status has one safe database contract

Add an additive runtime-status table and sanitized operator view in the v0.45.0 SQL migration. The table is observational; advisory locks and durable offsets remain authoritative.

Track per pipeline:

- relay group, tenant, direction, and pipeline identity;
- enabled state from catalog;
- opaque owner instance token and ownership-acquired time;
- last owner heartbeat;
- last durable checkpoint success time;
- last safe error code, component, class, and time;
- retry attempt, retry state, and next retry time;
- last state update time.

Rules:

- A worker writes owner state only after acquiring the canonical advisory lock.
- Heartbeats are conditional on the same owner token.
- Clean release clears ownership only when the token still matches.
- A stale heartbeat is `unknown/stale`, not proof that no advisory lock exists.
- Last success advances only after the durable terminal disposition and checkpoint commit defined in v0.42.0.
- Last error stores a stable safe code and bounded operator-safe summary, never a raw error chain.
- Retry state is cleared on durable success or clean disable.
- Status writes are best-effort only when losing them cannot alter delivery state, but write failures are logged and counted. Status must never gate checkpoint correctness.
- A sanitized view joins catalog identity, runtime state, authoritative lag, and unresolved DLQ count.
- Reader/operator grants follow the v0.44.0 role model; raw status mutation remains relay-only.

CLI status returns these states explicitly:

```text
ownership: owned | unowned | stale | unknown
health: healthy | retrying | permanently_failed | disabled | unknown
lag: known integer | unknown with reason
last_success: timestamp | never | unknown
last_error: safe code/class/time | none | unknown
retry: attempt/next_retry | inactive | unknown
dlq_depth: known integer | unknown with reason
```

### 2.11 Metrics preserve compatibility and gain missing operational state

Keep existing metric names and labels where their meaning is correct. Wire currently registered-but-unused families before adding replacements.

Add only the missing measurements needed to answer the roadmap:

- per-pipeline ownership state without owner IDs as labels;
- last-success timestamp;
- last-error timestamp labeled only by bounded error class;
- current retry attempt and next-retry timestamp;
- unresolved DLQ depth;
- source poll/query duration;
- advisory-lock wait/ownership transition outcome;
- cleanup last-success time, rows deleted, remaining/blocked state;
- authoritative consumer lag updates;
- status-write failures.

Requirements:

- no payload, URL, host, credential, raw error, owner UUID, or arbitrary exception text in labels;
- pipeline/outbox labels follow the existing cardinality policy and are documented;
- gauges are removed when a pipeline is deleted so stale series do not look current;
- counters remain monotonic;
- status and metric timestamps come from the same transition points;
- permanent and transient error classes agree with coordinator retry behavior;
- DLQ depth means unresolved durable rows, not write rate;
- PostgreSQL bottleneck panels use pool acquisition, poll/query latency, lock wait, and query/write rate rather than a generic error count;
- sink slowness uses the existing sink publish-duration histogram and lag trend together.

### 2.12 Liveness and readiness are different

Expose:

| Endpoint | Meaning |
|---|---|
| `/livez` | HTTP process and runtime are alive |
| `/readyz` | Startup preflight passed, coordinator can reach PostgreSQL, and the relay can safely accept ownership |
| `/health` | Compatibility alias to `/readyz` for v0.45.0 |
| `/healthz` | Compatibility alias to `/readyz` for v0.45.0 |
| `/metrics` | Prometheus exposition |

A single permanently failed pipeline can make readiness degraded according to documented policy, but it must not make liveness fail. Helm liveness uses `/livez`; readiness uses `/readyz`.

The health JSON body is sanitized. It may expose bounded counts and safe states, but not pipeline names unless the caller uses the authenticated CLI/database status path.

### 2.13 The default dashboard is small and task-oriented

Keep `pg-tide/dashboards/relay-health.json` as the default installed dashboard, but replace misleading panels and reduce it to:

1. Relay up/readiness and aggregate pipeline health.
2. Per-pipeline ownership, lag, and last-success age.
3. Throughput versus lag growth.
4. Transient/permanent failures, retry state, and DLQ depth.
5. Sink p95/p99 latency beside PostgreSQL pool/query/lock pressure.
6. Ownership movement and ownerless duration.
7. Cleanup freshness, blocked cleanup, and retained growth.

Move tenant, fan-in, receipts, backfill, reverse/inbox fleet, detailed heatmaps, and other specialized panels into separately named dashboards. Experimental dashboards are not installed by default and are labeled with their maturity.

Every panel title, description, unit, and PromQL expression must describe the metric it actually queries. Remove panels that synthesize circuit, retry, DLQ, reverse-lag, or last-error state from unrelated metrics.

### 2.14 Alerts are actionable and share dashboard semantics

The default alert set covers:

- relay scrape/readiness failure;
- permanently failed pipeline;
- retry age or attempt threshold exceeded;
- sustained lag growth;
- non-zero or growing unresolved DLQ depth;
- sink latency increase with growing lag;
- PostgreSQL pool/query/lock bottleneck;
- ownership churn or excessive ownerless interval;
- cleanup stalled or blocked while storage grows.

Each alert contains:

- operator-facing summary;
- likely cause categories;
- dashboard link;
- exact runbook link;
- severity and threshold rationale;
- no secret or high-cardinality annotations.

Use configurable thresholds or recording rules. Do not encode one global message-count threshold as a universal capacity limit.

### 2.15 Upgrade compatibility and order

The supported v0.45.0 order is:

1. Back up the database and record current relay/extension versions.
2. Run the v0.45.0 pre-upgrade config and privilege checks.
3. Upgrade the extension from the current version to v0.45.0.
4. Verify schema, grants, pipeline config, and v0.44.0 relay health.
5. Replace relay instances one at a time with v0.45.0.
6. Verify ownership transfer, lag recovery, DLQ depth, and last-success progression after each replacement.
7. Complete post-upgrade doctor and status checks.

Compatibility guarantee:

| Extension | Relay | Status |
|---|---|---|
| v0.44.0 | v0.44.0 | Supported pre-upgrade |
| v0.45.0 | v0.44.0 | Supported temporary rolling/rollback state |
| v0.45.0 | v0.45.0 | Supported target |
| v0.44.0 | v0.45.0 | Unsupported; upgrade extension first |

The v0.45.0 relay must not require the v0.44.0 relay to understand or write the new status table. The ownership key, offset semantics, and pipeline config consumed by v0.44.0 remain compatible throughout the rolling window.

### 2.16 Migration and rollback boundaries

Keep the v0.44.0-to-v0.45.0 migration additive:

- add runtime-status storage, safe views, indexes, grants, and version markers;
- avoid destructive catalog rewrites;
- preserve v0.44.0-readable pipeline rows;
- do not rename or change ownership-lock identity;
- do not require new config keys for existing valid rows.

Provide `sql/pg_tide--0.45.0--0.44.0.sql`. Because the v0.45.0 migration is deliberately additive, the supported immediate rollback may:

- refuse while a v0.45.0 relay is active;
- remove v0.45.0-only views, functions, and runtime-status storage after an explicit warning that observational history will be discarded;
- preserve delivery tables, offsets, DLQ rows, pipeline config, and messages;
- restore the exact v0.44.0 object/grant shape;
- pass packaged downgrade and re-upgrade tests.

If implementation introduces any destructive delivery-state change, that change is out of scope for v0.45.0 rather than a reason to weaken rollback. Do not ship a nominal downgrade that silently discards delivery state.

Historical migrations remain classified individually. In particular, v0.39.0 offset re-keying and v0.43.0 cleanup/storage conversion boundaries are not made reversible by v0.45.0.

### 2.17 Runbooks are executable operational contracts

Every required runbook uses one template:

1. Scope and severity.
2. Symptoms and alert names.
3. Safety notes and actions not to take.
4. `doctor`, `status`, metric, log, and SQL evidence to collect.
5. Decision tree distinguishing likely causes.
6. Recovery steps using public CLI/SQL/deployment APIs.
7. Verification with expected output/state.
8. Rollback or escalation boundary.
9. Duplicate-delivery and data-loss implications.
10. Linked automated evidence and last release rehearsal.

Maintain one runbook/evidence manifest rather than embedding unvalidated test names in many pages. CI verifies every path and every required incident ID. Release review runs the mapped automated scenario and records any explicitly manual rehearsal.

### 2.18 Release metadata changes last

Complete behavior, migrations, compatibility tests, runbook rehearsals, dashboards, and release gates before changing:

- workspace package versions;
- `pg_tide.control`;
- Helm chart/application versions;
- changelog and release notes;
- lockfile package versions.

Do not tag, publish, push, or deploy v0.45.0 unless separately requested.

## 4. Workstream A: CLI Shape, Output, Exit Codes, and Errors

### A.1 Refactor command parsing around the canonical tree

Update `pg-tide-relay/src/cli.rs` and `main.rs`:

- add `Run`, `Config`, and `Maintenance` command groups;
- place validate/export and sweep under those groups;
- retain aliases through Clap aliases or a thin compatibility enum mapping;
- parse process-wide output/log options once;
- represent CLI overrides as `Option<T>` so unspecified flags do not replace TOML;
- ensure every non-`run` command returns after execution;
- keep replay subcommands and semantics unchanged except for common output/error handling.

Add parser tests for canonical commands, every compatibility alias, missing arguments, conflicting selectors, and deprecation behavior.

### A.2 Add one result renderer

Add one small shared module, for example:

```text
pg-tide-relay/src/cmd/output.rs
```

It owns:

- output format selection;
- versioned envelope types;
- deterministic JSON serialization;
- text rendering helpers for check lists and tables;
- stdout/stderr separation;
- timestamp and unknown/stale serialization.

Command modules return typed result data. They do not print intermediate success messages directly.

### A.3 Add typed operator diagnostics

Extend relay error handling with a bounded operator diagnostic:

```text
code
component
safe message
likely cause
next action
exit category
source for internal logs only
```

Map existing PostgreSQL, TLS, config, feature, connector, replay, and maintenance errors at the nearest layer that knows the component and remediation. Keep the original source for structured internal logs, but never serialize it automatically.

Do not build a general error-localization framework. A static code-to-remediation mapping covers the supported operator surface.

### A.4 Centralize process termination

`main` is the only layer that converts a command result into an exit code. Remove direct exits in replay and other command handlers.

Subprocess tests capture:

- stdout;
- stderr;
- exit status;
- JSON parseability;
- absence of canary secrets;
- one-envelope or documented JSONL behavior.

### A.5 Update CLI documentation

Update `docs/src/relay-guide/cli-reference.md` with:

- canonical command tree;
- aliases and removal target;
- output contract;
- exit-code table;
- examples for healthy, invalid, partial, stale, and incompatible states;
- stdout/stderr behavior;
- safe automation examples using JSON fields rather than parsing human tables.

### A.6 Workstream acceptance

- All canonical and compatibility invocations reach one handler.
- No operator command accidentally starts the daemon.
- Every automation command emits valid schema-v1 JSON.
- Exit-code contract tests cover success and every category.
- Canary secrets never appear in stdout, stderr, or JSON.
- CLI docs and `--help` agree.

## 5. Workstream B: Strict Configuration, Schema, Export, and Startup Preflight

### B.1 Make process configuration strict

Refactor `pg-tide-relay/src/config.rs`:

- reject unknown fields at every process-owned object;
- split file parsing, CLI overlay, secret resolution, and semantic validation into explicit steps;
- ensure CLI defaults are applied only after TOML and do not masquerade as user overrides;
- reject pipeline-shaped keys with an error that points to catalog APIs;
- preserve the v0.44.0 secret-reference and redaction contract.

Test top-level typos, nested typos, type errors, invalid bounds, explicit CLI precedence, omitted flags, and legacy config-mode warnings.

### B.2 Introduce strict pipeline types incrementally

Define a canonical pipeline envelope and strict connector config structs. Migrate the supported production connectors first, then every compiled preview/experimental connector needed to generate a complete schema.

For each migrated connector:

1. Define strict deserialization and semantic bounds.
2. Generate its JSON Schema fragment.
3. Route validation and factory construction through the typed value.
4. Remove the corresponding manual JSON getters and duplicate match branch.
5. Add valid/invalid fixtures, including unknown keys.

A connector that cannot supply a strict schema and validator remains unavailable to v0.45.0 startup when configured; it must not fall back to permissive parsing.

### B.3 Add the connector descriptor registry

Place descriptor ownership near source/sink registration, not in CLI code. Registry tests assert:

- every compiled connector has one descriptor;
- names and aliases are unique;

## 15. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Strict parsing rejects an existing typo that was silently ignored | Pre-upgrade `config validate`, aggregate diagnostics, canonical export, explicit migration note |
| Disabled experimental config blocks startup | Structural errors remain fatal; unavailable connector features on disabled rows are visible warnings |
| Typed connector migration becomes a broad rewrite | Migrate parsing/factory boundaries only; do not redesign connector protocols |
| JSON contract leaks secrets through nested errors | Typed safe diagnostics, canary subprocess tests, stdout/stderr capture |
| Added status writes affect delivery | Keep observational writes outside checkpoint authority; count failures; test injected status-write faults |
| Status row claims ownership after process death | Heartbeat/stale states and advisory lock remain authoritative; never equate stale row with held lock |
| DLQ depth query becomes expensive | Add resolution-state index and bounded aggregate view/refresh |
| Pipeline labels create unbounded Prometheus cardinality | Reuse bounded configured identities, omit owner IDs/raw errors, remove deleted series |
| Readiness policy causes rollout deadlock | Define startup/preflight versus per-pipeline degradation precisely; liveness remains independent |
| Dashboard no-data looks healthy | Explicit no-data states and alert fixtures |
| v0.44.0 relay cannot tolerate new schema | Keep migration additive and old-readable; run historical binary against upgraded extension |
| Reverse migration discards delivery state | Keep v0.45.0 SQL additive; allow only runtime-status history loss and refuse active v0.45.0 relays |
| Historical v0.39.0 fixture is not authentic | Build or fetch pinned signed historical artifacts and record digests |
| Mixed versions use different ownership semantics | Support only v0.44/v0.45 after explicit invariant comparison; test two real processes |
| CNPG bootstrap hook is mistaken for upgrade machinery | Use explicit one-shot migration operation and verify completion |
| Runbooks rot into prose-only checklists | Evidence manifest, path validation, executable scenarios, release rehearsal |
| Compatibility aliases live forever | Document v0.47.0 removal and test deprecation warnings |
| Scope expands into a control plane | No config import, UI, remote API, auto-remediation, or general orchestration |
