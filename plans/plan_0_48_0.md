# pg_tide v0.48.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** Baseline Closure and Deterministic CI
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Detailed program context:** [Pre-v1.0 Hardening, Simplification, and Trust Plan](./PLAN_PRE_V1_0.md)
> **Starting point:** v0.47.0 and current `main`
> **Implementation branch:** `implementation-v0.48.0`
> **Scope rule:** Establish an honest, reproducible baseline. Add no product functionality, remove no product surface, and do not begin v0.49.0 simplification work.

## 1. Release Outcome

v0.48.0 is complete when the project can answer, with committed and reproducible evidence, all three of these questions:

1. **What did v0.47.0 actually prove?**
   The release-evidence records identify the exact v0.47.0 commit and artifacts where evidence exists, and explicitly preserve `pending` status where pilots, reviews, approvals, or digests were not completed. Evidence from a later commit is never presented as v0.47.0 evidence.

2. **What environment proves the PostgreSQL extension?**
   A versioned PostgreSQL 18 and pgrx clean-room environment runs the complete extension suite without depending on a developer's local PostgreSQL installation, a sibling checkout, or an unrecorded system package. The first hard failure remains visible and produces diagnostics rather than a cascade of mutex failures.

3. **Which tests are release-critical?**
   A checked-in required-test manifest names every required PR, scheduled, and release test, its environment and owner, and the permitted retry/quarantine policy. CI verifies that required tests exist and ran; it does not silently turn missing, renamed, skipped, or quarantined tests into green evidence.

The release also captures a machine-readable pre-simplification baseline so that v0.49.0 can measure the cost and benefit of reducing the product surface.

The release does **not** claim that v0.47.0 pilots or independent reviews are complete merely because their records are structured, and it does not claim that the current null operational benchmark values are measured capacity limits.

## 2. Preconditions and Scope Guard

### 2.1 Starting baseline

The implementation branch starts from the v0.47.0 public-beta baseline on `main`.

The current repository state already has:

- `release-evidence/v0.47.0-index.json` with `status: pending` and no candidate or artifact digests;
- four pending v0.47.0 pilot profiles in `release-evidence/v0.47.0-pilots.json`;
- five pending v0.47.0 independent-review disciplines in `release-evidence/v0.47.0-reviews.json`;
- `just check-v1-contracts` and `scripts/check_v1_contracts.py` for the frozen contract inventory;
- `scripts/check_v1_artifacts.py` for machine-readable contract artifacts;
- a pgrx extension test job in `.github/workflows/ci.yml` that installs PostgreSQL 18 and `cargo-pgrx` on an Ubuntu runner;
- `just test-pgrx` for the existing local extension test path;
- an operational benchmark contract whose committed `benchmarks/operational/baseline.json` remains `pending_reference_run` with null metric values.

These are inputs to v0.48.0, not evidence that the new release gate already passes.

### 2.2 Required v0.47.0 evidence decision

Before changing any release-evidence status, inspect the exact `v0.47.0` tag and its released artifacts:

```text
git rev-parse v0.47.0^{commit}
git show --stat --oneline v0.47.0
```

Use the following rule:

- If a pilot or review was completed against the exact tagged commit and exact artifact digest, record the identity, date, commit, digest, scenario result, and linked issue.
- Otherwise, retain `pending` and add an explicit explanation that v0.47.0 established the contract baseline but did not complete the production-pilot or independent-review gate.

Do not infer completion from a passing local test, a later branch, a release tag alone, a request-construction test, or an evidence file that has no reviewer/operator identity.

### 2.3 Explicit non-goals

The following work belongs to later releases and must not be pulled into v0.48.0:

- removing or relocating experimental connectors, protocols, or dependencies;
- deleting the `experimental-full` profile;
- changing the relay delivery state machine or checkpoint semantics;
- adding new connector or wire-format support;
- performance optimization or changing operational budgets;
- lifecycle, migration, rollback, backup, or restore redesign;
- security architecture changes or supply-chain remediation beyond documenting baseline evidence;
- changing public SQL, configuration, metrics, health, CLI, or event-envelope behavior;
- marking the v0.47.0 release evidence `ready` without the required proof.

Tests may be added or repaired only when they are required to make the baseline executable, to expose the first clean-room failure, or to enforce the required-test/reliability policy.

## 5. BASE-1: Reconcile v0.47.0 Evidence

### Objective

Make the v0.47.0 evidence record accurate without backfilling later work or weakening any v1 release gate.

### Files in scope

- `release-evidence/v0.47.0-index.json`
- `release-evidence/v0.47.0-pilots.json`
- `release-evidence/v0.47.0-reviews.json`
- `docs/src/operations/release-evidence.md`
- `CHANGELOG.md`
- the existing v0.47.0 evidence checker in `.github/workflows/ci.yml` and `.github/workflows/release.yml`, if centralizing it is needed for consistent validation

### Implementation steps

1. Resolve the exact v0.47.0 commit from the tag and inspect the release workflow outcome.
2. Compare each pilot and review record against actual evidence, not against the presence of a required-profile entry.
3. For completed evidence, record:
   - exact candidate commit;
   - artifact and image digests;
   - operator or reviewer identity;
   - approval date in UTC;
   - scenario or discipline result;
   - linked issue and finding disposition where applicable.
4. For incomplete evidence, retain `pending` and add a machine-readable reason field or a normative note without changing the existing required profile IDs.
5. Keep the release index `status` as `pending` unless every v0.47.0 release gate is genuinely complete. Do not set `open_blockers` to zero when the blocker query has not run.
6. Update the release-evidence documentation to distinguish:
   - a structurally valid pending record;
   - a complete evidence record for a candidate;
   - a `ready` record approved for release.
7. Update the changelog only to clarify the v0.47.0 evidence state. Do not rewrite historical release notes to imply that later evidence belonged to v0.47.0.
8. If the workflow currently contains duplicated inline JSON validation, extract only the shared validation needed for this release into a standard-library script. Preserve the current schema and status vocabulary unless a field is required to explain an observed state.

### Required evidence fields

Every completed pilot or review entry must be joinable to the v0.47.0 release index by:

```text
release -> candidate.commit -> entry.candidate_commit
release -> candidate.artifact_digests -> entry.artifact_digests
```

The record must remain useful when sanitized for public publication. It must not contain payloads, credentials, certificates, customer names without consent, private hostnames, account IDs, or raw unredacted logs.

### BASE-1 acceptance criteria

- [ ] The v0.47.0 index accurately reflects the tagged release and its evidence.
- [ ] No pilot or review is marked complete without identity, date, exact commit, and artifact digest.
- [ ] Pending evidence states why completion is absent without inventing a new release gate.
- [ ] The CI and release checks accept the truthful pending state and still reject malformed records.
- [ ] The release-evidence documentation explains pending versus ready.
- [ ] Historical v0.47.0 claims are not silently rewritten using later artifacts.

## 6. BASE-2: Authoritative Extension-Test Clean Room

### Objective

Provide one reproducible PostgreSQL 18 and pgrx environment for the complete `pg-tide-ext` test suite. The environment is authoritative for release evidence; local developer setups are convenience paths only.

### Proposed implementation shape

Add a small, versioned clean-room test harness rather than extending the existing runner-specific shell steps indefinitely. The implementation should use the repository's existing pinned inputs:

- Rust `1.97.1` from `rust-toolchain.toml`;
- `cargo-pgrx` `0.18.0` from the current CI setup and extension dependency constraints;
- PostgreSQL major version 18;
- pinned system build dependencies required by pgrx bindgen and PostgreSQL extension compilation;
- a pinned base image and PostgreSQL package source, with the exact image/package versions recorded in the harness metadata.

The final choice between a checked-in Dockerfile and a versioned CI container image must preserve the same local command and CI command. A CI runner's preinstalled PostgreSQL must not be the only implementation of the environment.

### Proposed files and commands

| File or command | Purpose |
|---|---|
| `tests/extension-cleanroom/` or an equivalent narrowly named harness directory | Dockerfile, entrypoint, and environment metadata |
| `just test-extension-clean` | Build/run the clean-room suite locally and return the first failing status |
| `just test-unit-clean` | Run the release-critical non-extension unit suite from the same clean checkout policy |
| `.github/workflows/ci.yml` job `extension-cleanroom` | Required PR validation for the authoritative extension environment |
| `.github/workflows/extension-cleanroom.yml`, if separation keeps CI readable | Optional dedicated workflow; use one required check name either way |
| `target/extension-cleanroom/` | Local transient logs and result metadata; never commit generated logs |

Do not add a second PostgreSQL test implementation with different SQL setup semantics. The clean-room harness should invoke `cargo pgrx test pg18 --package pg-tide-ext` or the smallest wrapper around it required to capture diagnostics.

### Environment requirements

The harness must:

1. start from a clean checkout and a clean temporary PostgreSQL data directory;
2. install the extension and all SQL migrations through pgrx, not through manually created hidden tables;
3. run the complete extension suite, including tests that exercise the public SQL API;
4. pin PostgreSQL, Rust, pgrx, compiler, clang, LLVM, and system library inputs;
5. avoid any sibling `rocklake2` or other workspace outside the checkout;
6. run as a non-root test user after image/package setup where possible;
7. preserve the exact command, commit, image identifier, tool versions, and environment metadata;
8. fail if a required extension test is skipped because a dependency is absent or the environment is unsupported;
9. terminate the server and clean the temporary data directory after success or failure;
10. expose a deterministic non-zero exit code for the first failing test.

### Failure diagnostics

The runner must preserve the first hard failure instead of allowing a shared test mutex to obscure it. On failure, upload or retain:

- test command and exit status;
- the test name and cargo/pgrx test listing used;
- PostgreSQL server log and startup configuration with secrets removed;
- pgrx output and Rust backtrace when enabled;
- compiler and PostgreSQL version output;
- core-dump presence/limits and a core-dump path or absence reason where the platform supports it;
- temporary database metadata needed to reproduce the failure, excluding credentials;
- a machine-readable `result.json` with `status`, `first_failure`, `skipped_tests`, `environment`, and artifact paths.

The harness must not retry a failing extension test until it passes. An infrastructure retry may be configured at the CI job level only when the job records that the retry was an infrastructure retry and the test itself still ran to completion.

### Local developer contract

Document one supported local invocation:

```text
just test-extension-clean
```

The command should fail clearly when Docker or the required container runtime is unavailable. `just test-pgrx` may remain as a faster developer convenience, but its result must not satisfy the authoritative clean-room gate.

### CI contract

The `extension-cleanroom` check must:

- run on pull requests and on the default branch;
- use the same pinned harness inputs as the documented local command;
- be a required status check before the v0.48.0 gate can pass;
- upload logs and the result manifest on every failure;
- upload the result manifest on success;
- report skipped tests as failures, not warnings;
- avoid treating a successful image build with no executed tests as success.

The existing `test-ext-pgrx` job may remain during migration, but it cannot be the only proof and should be removed or demoted once the clean-room job is stable.

### BASE-2 acceptance criteria

- [ ] A fresh checkout can run the complete extension suite with one documented clean-room command.
- [ ] CI and local execution use the same pinned PostgreSQL 18, Rust, pgrx, and system-dependency inputs.
- [ ] The suite does not depend on a developer-local PostgreSQL server or sibling repository.
- [ ] A deliberate first-test failure leaves the original failure visible and produces diagnostics.
- [ ] Missing or skipped required extension tests fail the job.
- [ ] Successful and failed runs emit machine-readable environment/result metadata.
- [ ] The clean-room job is required in pull-request validation.

## 7. BASE-3: Required-Test Inventory and Enforcement

### Objective

Create one inventory that states which tests are required, when they run, what they need, who owns them, and what happens when a test is renamed, removed, skipped, or flaky.

### Manifest

Add `tests/required-tests.toml` as the authoritative inventory. Keep it declarative and small enough for reviewers to inspect. Each record should contain at least:

```toml
id = "extension-cleanroom"
level = "release"
trigger = "pull_request"
ci_job = "extension-cleanroom"
command = "just test-extension-clean"
targets = ["pg-tide-ext"]
dependencies = ["docker", "postgresql-18", "cargo-pgrx-0.18.0"]
owner = "@owner"
blocking = true
max_retries = 0
allow_local_skip = false
flake_policy = "never-quarantine"
evidence = ["target/extension-cleanroom/result.json"]
```

The exact owner values must be agreed with repository maintainers; do not invent a personal owner in the implementation. Use the repository's existing CODEOWNERS identity or an explicit team when available.

### Inventory coverage

Seed the manifest from the current workflows and `justfile`, including at least:

| Group | Existing evidence to inventory |
|---|---|
| Static contract checks | connector generation check, v1 contract check, v1 artifact check, operational-budget configuration check |
| Workspace validation | clean checkout build, relay unit tests, formatting, clippy |
| Core integration | migration, SQL API, outbox source, wire format, property tests, validation fixtures |
| Relay behavior | coordinator, circuit breaker, DLQ, replay, shutdown, backpressure, HA/DAG, inbox sink |
| Supported protocol tests | PostgreSQL inbox, NATS/JetStream, Kafka KRaft, webhook, and public API E2E jobs that exist at the baseline |
| Extension validation | pgrx extension suite and the new clean-room job |
| Documentation/operator checks | executable Quick Start SQL, generated documentation or support checks that are release-required |
| Release validation | migration-chain, packaging, security, SBOM/provenance, and release-evidence checks already present in release workflows |

The inventory records the current v0.47.0 state, including tests that are still experimental, so v0.49.0 can explicitly disposition them. It must not promote an experimental test to a production-support claim merely by listing it.

### Execution records

Add a small standard-library wrapper, for example `scripts/run_required_test.py`, with these rules:

1. Validate the requested manifest ID before executing.
2. Run the declared command without changing its exit status.
3. Write `target/required-tests/<id>.json` with the commit, manifest version, command, start/end time, exit status, skipped-test count, and environment summary.
4. Never convert a failed command into a successful result.
5. Never retry the test inside the wrapper.
6. Preserve stdout/stderr in the CI log and reference uploaded files from the result record.

Add `scripts/check_required_tests.py` with separate modes for:

- validating the manifest schema and unique IDs;
- checking that referenced commands, job names, test targets, and evidence paths exist;
- aggregating result records for the current CI run;
- rejecting a missing result, a skipped result, a manifest/commit mismatch, an unexpected retry, or a result not associated with the required job.

Add a `just check-required-tests` entry point. Use Python's standard library, matching the existing repository validation scripts; do not add a test orchestration dependency.

### Change and removal policy

A required test may be renamed, replaced, or removed only when the same pull request:

- updates `tests/required-tests.toml`;
- names the replacement or records an explicit disposition;
- links the issue or review decision;
- identifies the affected release gate;
- updates the owning CI job and evidence path;
- states why coverage is equivalent or why the test is intentionally no longer required.

An absent manifest record is a failure, not an implicit deletion. A test that is disabled by feature flags or unavailable service dependencies must be represented as a failed or explicitly dispositioned result.

### BASE-3 acceptance criteria

- [ ] Every PR, scheduled, and release-required test is represented exactly once.
- [ ] Every manifest entry has an owner, trigger, job, command/target, dependency list, blocking state, and retry policy.
- [ ] The checker catches a removed or renamed test target before merge.
- [ ] CI produces and validates execution records for required tests.
- [ ] Missing, skipped, unexpected, or silently quarantined required tests fail the relevant job.
- [ ] Updating the inventory is required when a test changes.
- [ ] The inventory does not change the maturity classification of any connector or feature.

## 8. BASE-4: Flake Registry and Policy

### Objective

Make test unreliability visible, owned, and temporary. A rerun is not evidence that a failure did not happen.

### Registry

Add `tests/flake-registry.toml` with one record per active flake. Each record must contain:

```toml
test_id = "example-test"
owner = "@owner"
first_observed = "2026-08-19"
failure_signature = "stable sanitized signature"
issue = "#123"
severity = "P2"
quarantine_status = "active"
quarantine_expires = "2026-09-19"
release_impact = "blocks-v0.48-release"
last_observed = "2026-08-19"
attempt_count = 1
```

The implementation should choose a repository-appropriate issue reference format and validate it consistently. The dates above are illustrative only.

### Policy

Document the policy near the contributor/test workflow, for example in `CONTRIBUTING.md` or a focused page under `docs/src/contributing/`. The policy must state:

- P0/P1 and release-critical tests cannot be quarantined.
- A quarantine needs an owner, issue, failure signature, expiry, severity, and release impact.
- Expired quarantines fail CI until renewed by explicit review or removed after repair.
- Automatic reruns cannot turn a failed required test green without recording the original failure.
- An infrastructure retry is distinct from a test retry and must be visible in the result artifact.
- The registry must be empty before `v1.0.0-rc.1`; v0.48.0 may contain only time-bounded exceptions that do not weaken its required gate.
- A flake is not an excuse to mark a test `allow_local_skip` when CI requires it.

Add `scripts/check_flake_registry.py` and `just check-flakes` to validate dates, owners, issues, severity, expiry, duplicate test IDs, and forbidden quarantine of blocking tests. The checker must fail on an expired entry even when the test currently passes.

### CI behavior

Every required test wrapper consults the registry before execution and records any active flake disposition in its result. The wrapper must not skip a test solely because it is listed as flaky. For an allowed non-blocking quarantine, CI runs the test when possible, marks the result as quarantined, and uploads the failure evidence.

### BASE-4 acceptance criteria

- [ ] The registry and policy exist and are machine-checked.
- [ ] Every active entry has an owner, issue, signature, expiry, and release impact.
- [ ] P0/P1 and release-blocking tests cannot be quarantined.
- [ ] Expired entries fail validation.
- [ ] Reruns and infrastructure retries remain visible in CI evidence.
- [ ] The v0.48.0 gate has no unowned or indefinite quarantine.

## 9. BASE-5: Pre-Simplification Baseline

### Objective

Capture the v0.47.0 repository and artifact shape before v0.49.0 removes or relocates non-core code. The baseline is a measurement record, not a capacity claim and not a reason to preserve unused features.

### Storage and files

Add a small checked-in record under `release-evidence/pre-v1-baseline/`:

| File | Contents |
|---|---|
| `baseline.json` | Versioned summary, provenance, statuses, counts, sizes, durations, and references |
| `README.md` | Reproduction commands, environment requirements, interpretation rules, and known pending values |
| `dependency-tree.txt` or a deterministic equivalent | Full locked workspace dependency graph used for comparison |
| `commands.json` | Exact commands, tool versions, commit, dirty state, and exit statuses used to capture the summary |

Do not commit generated binaries, container layers, raw logs, credentials, or large benchmark outputs. Link those as CI artifacts or retain only their digest and metadata.

### Required measurements

Capture the following from a clean checkout of the v0.47.0 baseline:

1. **Source and dependency surface**
   - `cargo metadata --locked` summary;
   - full `cargo tree --workspace --locked` output or a deterministic digest plus retained artifact path;
   - direct and transitive dependency counts by package and feature profile;
   - Cargo feature names and enabled release profiles;
   - connector and protocol counts from `connectors.toml` and generated outputs;
   - SQL, CLI, metrics, health, and wire-format surface counts where existing checkers can report them.

2. **Build and artifact shape**
   - clean build duration and compiler/toolchain metadata;
   - relay binary size for each supported baseline profile and the current `experimental-full` comparison profile;
   - packaged crate contents and size;
   - container image identifier, compressed size, uncompressed size, layer count, and file/package inventory when the baseline image can be built;
   - platform and architecture for every measurement.

3. **Test and CI shape**
   - test counts by unit, integration, extension, E2E, scheduled, and release level;
   - CI job names, workflow names, required status names, and durations from a named workflow run;
   - cache state and whether a job used a clean or warm build;
   - current retry and skip behavior before the new policy is enforced.

4. **Documentation and repository shape**
   - `SUMMARY.md`/mdBook page count and source page count;
   - connector, sink, source, protocol, feature, example, script, and plan counts;
   - tracked file count by major directory;
   - generated-file and archive locations that v0.49.0 may later reduce.

5. **Operational evidence state**
   - current operational benchmark contract and status;
   - existing measured results and their commit/environment provenance;
   - explicit `pending` status for `benchmarks/operational/baseline.json` if no reference run exists;
   - no invented throughput, latency, memory, WAL, or recovery value for a null metric.

### Measurement rules

- Use the exact commit and record dirty state.
- Record OS, architecture, CPU/memory class, Rust, Cargo, PostgreSQL, pgrx, Docker, and relevant service versions.
- Separate GitHub-hosted CI timings from local timings; do not compare their medians as if they were the same machine.
- Run build and size measurements from a clean target directory when a clean-build value is claimed.
- Use three repetitions and medians for any measured performance number, following `benchmarks/operational/README.md`.
- Record raw correctness counts for any operational benchmark and validate results with `scripts/check_operational_budgets.py`.
- Label unmeasured or unavailable fields as `pending`, `not_applicable`, or `not_available` with a reason.
- Include a method and command for every non-null number.

### Baseline schema

`baseline.json` should include:

```json
{
  "schema_version": 1,
  "release": "v0.47.0",
  "captured_commit": "...",
  "dirty": false,
  "status": "complete-with-pending-fields",
  "environment": {},
  "source_surface": {},
  "dependencies": {},
  "artifacts": {},
  "tests_and_ci": {},
  "documentation": {},
  "operational_evidence": {},
  "provenance": {}
}
```

The example is a shape, not a value template. Do not fill unknown values with zero, an empty list, or a guessed measurement. The checker should require a status/reason for each field that cannot be measured.

### BASE-5 acceptance criteria

- [ ] The baseline is captured before v0.49.0 removal or relocation work.
- [ ] It identifies the exact commit, dirty state, environment, commands, and measurement method.
- [ ] It includes dependency, artifact, test/CI, documentation, surface, and operational evidence state.
- [ ] Pending operational metrics remain pending and are not presented as capacity claims.
- [ ] The record is deterministic enough to compare against a later baseline, with machine-readable summaries and retained raw-artifact references.
- [ ] No credentials, payloads, raw secrets, or large generated binaries are committed.

## 10. INT-1: CI and Release-Gate Integration

### Objective

Make the new artifacts enforceable without duplicating incompatible policy in each workflow.

### Workflow changes

Update `.github/workflows/ci.yml` to add or require:

1. `extension-cleanroom` using the authoritative harness;
2. `check-required-tests` or an aggregate step that validates `tests/required-tests.toml` and all required execution records;
3. `check-flakes` for `tests/flake-registry.toml`;
4. the existing v1 contract/artifact and connector checks as manifest entries;
5. artifact upload for clean-room logs, required-test result records, flake observations, and baseline capture output where the job produces it.

Keep existing independent jobs until the new inventory proves equivalent coverage. Do not hide a job inside a monolithic script just to reduce the visible job count; the CI graph should still show which environment and gate failed.

Update `.github/workflows/release.yml` only as needed to:

- validate the required-test manifest and flake policy before release gates;
- require the clean-room result for the candidate;
- verify that a baseline exists and identifies the parent release;
- preserve the existing v0.47.0 evidence gate semantics;
- avoid changing a `pending` v0.47.0 record to `ready` as a side effect of a v0.48.0 release.

If the release workflow still names the gate `v0.47.0 release evidence`, update the job label only when the underlying v0.47.0 gate logic remains unchanged and the name would otherwise mislead operators. Historical evidence filenames and release identifiers remain `v0.47.0`.

### Trigger matrix

| Check | Pull request | `main` push | Scheduled | v0.48 release candidate |
|---|---:|---:|---:|---:|
| Contract/artifact/registry checks | required | required | optional | required |
| Required-test manifest validation | required | required | required | required |
| Flake registry validation | required | required | required | required |
| Relay unit/integration tests | required | required | required | required |
| Extension clean room | required | required | required | required |
| Public API/service E2E | existing policy | existing policy | existing policy | existing policy |
| Baseline capture | no | optional artifact | scheduled or manual | required once for candidate parent |
| v0.47 evidence status validation | required structural check | required structural check | optional | required structural check |

The manifest is the source for the final status-check list. A test may run more often than its minimum trigger, but it may not run less often without an inventory change.

### CI result aggregation

The aggregate check should reject:

- a required ID with no result;
- a result from a different commit or workflow run;
- a command that exited zero while reporting skipped required tests;
- an unapproved retry or quarantine;
- a required result produced by the wrong job/environment;
- an extension result that exercised only a subset of the suite;
- an artifact that cannot be traced to its command and toolchain metadata.

### INT-1 acceptance criteria

- [ ] The clean-room test is a required CI status check.
- [ ] Manifest and flake validation run on pull requests and the default branch.
- [ ] Required execution records are uploaded and aggregated.
- [ ] CI failures preserve enough metadata to reproduce the first failure.
- [ ] Existing v0.47.0 evidence checks remain structurally valid and semantically unchanged.
- [ ] No v0.48.0 check silently promotes pending v0.47.0 evidence.

## 11. Validation Strategy

### Local validation during implementation

2. **BASE-2 clean-room harness**

3. **BASE-3 required-test manifest**

7. **REL-1 exit review**

Each pull request should include the user-visible problem, affected release gate, failure mode, tests that fail before the change, documentation impact, security/privacy impact of stored logs, rollback behavior, and exact validation commands.

## 13. Rollback and Failure Handling

- If the clean-room image or harness is defective, revert the harness pull request while retaining the v0.47.0 evidence reconciliation.
- If the required-test checker has false positives, fix its manifest interpretation without weakening the required test or deleting the record.
- If a test is genuinely flaky, record it with an owner and expiry; do not raise retry counts until the failure is invisible.
- If baseline capture cannot measure a field, record an explicit pending reason and continue. Do not block the entire baseline on a nonessential measurement, but do not call the baseline complete without declaring the gap.
- If the authoritative extension environment cannot run a required test, v0.48.0 is not complete. The issue must be resolved or the release remains open.
- If an evidence status cannot be established from the exact v0.47.0 artifacts, leave it pending and carry the gap forward to the appropriate pre-v1 release.

The implementation should be reversible by removing the new harness/checker wiring and the new baseline artifacts. It must not require a database migration or alter an installed extension.
