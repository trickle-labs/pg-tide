# pg_tide v0.44.0 Implementation Plan

> **Status:** Proposed
> **Release theme:** Secure by Default
> **Source:** [pg-tide roadmap to focused production grade](./pg-tide-roadmap-to-focused-production-grade.md)
> **Starting point:** v0.43.0 and current `main`
> **Scope rule:** Make the default privilege, network, secret, dependency, and encryption behavior safe. Do not add connectors, build a general secrets platform, or promote a feature without security evidence.

---

## 1. Release Outcome

v0.44.0 is complete when a fresh installation and a v0.43.0 upgrade have the same explicit security boundary:

1. A published threat model covers every roadmap threat with prevention, detection, recovery, ownership, and executable evidence.
2. Five non-login group roles define the supported database privilege model: `tide_admin`, `tide_publisher`, `tide_relay`, `tide_operator`, and `tide_reader`.
3. PUBLIC has no implicit write, configuration, maintenance, replay, rewind, tenant-administration, or raw-secret access.
4. `tide_publisher` membership alone is insufficient to publish. The caller must also be authorized for the target outbox, and any authorization error refuses the publish.
5. Security-definer APIs authorize `session_user`, use a fixed safe `search_path`, fully qualify protected objects, and have PUBLIC execution revoked.
6. Catalog, ACL, tenant, grant, configuration, checkpoint, and maintenance errors cannot become empty results, permissive defaults, partial success, or successful no-ops.
7. Every supported outbound network path verifies peer identity by default. Plaintext transport, disabled verification, or disabled SSRF protection requires an explicit connector-level development override that is visible in validation, logs, and metrics.
8. Every HTTP-capable connector either uses the shared URL, DNS, redirect, proxy, and SSRF policy or remains excluded from production profiles with a checked explanation.
9. Secret references have one grammar, are resolved only in memory, and cannot leak through `Debug`, `Display`, logs, metrics, status, validation, templates, configuration history, or connector error chains.
10. Secret files are opened without following symlinks and pass strict type, owner, and permission checks before use.
11. The production dependency graph has no ignored advisory. Any exception is limited to an experimental graph, names an owner and expiry, and cannot weaken the production gate.
12. Every released binary archive and image digest has an SBOM, signature, and build-provenance attestation produced by pinned tools and actions.
13. `LocalKeyFile` is the only supported encryption provider. Cloud KMS names that return `NotImplemented` are absent from production claims and production feature sets.
14. Fresh-install and v0.43.0-to-v0.44.0 tests prove equivalent roles, grants, revokes, sanitized views, secure defaults, and extension behavior.

The release does not claim that application payloads are trustworthy, that pg_tide can enforce infrastructure firewalls, or that an experimental connector is secure merely because it compiles.

## 2. Preconditions and Decisions to Lock Before Coding

### 2.1 v0.43.0 is a hard prerequisite

Do not begin the security migration while the v0.43.0 release gate is red. Rerun at least:

- the public SQL API through the real relay to NATS JetStream;
- long-transaction fencing;
- safe multi-pipeline retention and bounded cleanup;
- partitioned and heap canonical storage tests;
- scheduled operational budget validation;
- fresh v0.43.0 install and v0.42.0-to-v0.43.0 upgrade parity;
- `core` build and connector-registry generation checks.

If v0.43.0 still permits a silent delivery gap, unsafe cleanup, or an unbounded production path, repair that release first. v0.44.0 must not hide a reliability defect behind stricter permissions.

### 2.2 `connectors.toml` remains the support authority

Security scope follows the checked-in maturity registry, not the number of modules that compile:

| Surface at the v0.43.0 baseline | v0.44.0 obligation |
|---|---|
| PostgreSQL native outbox source | Full role, TLS, secret, fail-closed, and upgrade coverage |
| PostgreSQL inbox and `pg_outbox` sinks | Full role, TLS, secret, fail-closed, and upgrade coverage |
| NATS JetStream | Full TLS, credential-redaction, restart, and production dependency coverage |
| stdout/file diagnostics | Secret-redaction coverage; no connector-support claim |
| Webhook preview | Shared HTTP/SSRF policy and tests; no maturity promotion |
| Kafka preview | TLS/credential default review and redaction tests; no maturity promotion |
| Experimental connectors | Shared security primitives where applicable, otherwise excluded from production and explicitly classified |

If connector maturity changes before implementation starts, the required security matrix changes with it. No plan edit is needed to make a newly supported connector subject to the supported gate.

### 2.3 Trust boundaries are explicit

Use these boundaries consistently in the threat model, code, tests, and runbooks:

1. **Database caller to extension:** SQL arguments, role membership, outbox ACLs, tenant identity, replay ranges, and administrative intent are untrusted.
2. **Extension owner to caller:** security-definer execution must not lend owner privileges beyond the documented operation.
3. **Relay to PostgreSQL:** connection strings and catalog rows are configuration inputs; malformed rows or denied queries are failures.
4. **Relay to connector:** endpoints, credentials, proxy settings, certificates, and connector error text are untrusted.
5. **Message to relay:** payloads, headers, templates, schema identifiers, and encoded sizes are untrusted and resource bounded.
6. **Build system to release consumer:** dependencies, actions, toolchains, base images, generated artifacts, and attestations are supply-chain inputs.
7. **Operator output boundary:** logs, metrics, status, history, validation, templates, and diagnostics are assumed observable by users who must not receive secrets.

### 2.4 Canonical database roles

Add these cluster-level, non-login group roles:

| Role | Allowed capability | Explicitly denied |
|---|---|---|
| `tide_admin` | Create/drop outboxes and inboxes; configure/delete pipelines; manage tenants and ACLs; convert storage; rewind/replay; manage role grants | Login credentials are never attached to the group role |
| `tide_publisher` | Execute publishing APIs for outboxes separately authorized by the outbox publisher ACL | Outbox creation/drop, catalog writes, relay control, raw table writes |
| `tide_relay` | Read canonical source/config rows required by the relay; write checkpoints, receipts, DLQ rows, and inbox deliveries through the supported path | Pipeline administration, role/tenant administration, rewind, storage conversion |
| `tide_operator` | Read sanitized status/history; enable/disable pipelines; run bounded sweep and dry-run maintenance | Configure/delete pipelines, view raw secrets, change ACLs, rewind/replay, storage conversion |
| `tide_reader` | Read sanitized status, lag, health, and non-secret metadata | Mutation, raw config/history, payload access unless separately granted |

All five roles are created with:

```text
NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
```

Application, relay, and operator login roles receive membership in the applicable group role. The provisioning SQL never creates login roles or passwords.

### 2.5 Preserve `pg_tide_admin` as a compatibility alias

`pg_tide_admin` already appears in administrative authorization checks and deployments. Avoid two independent admin authorities:

- make `tide_admin` canonical for v0.44.0 and later;
- when `pg_tide_admin` exists, grant `tide_admin` to it so existing members retain transitive authority;
- update administrative checks to test `tide_admin`;
- do not create `pg_tide_admin` on a fresh installation;
- document `pg_tide_admin` as a deprecated compatibility group, not a second role model;
- test an upgraded login that is only a member of `pg_tide_admin`.

Do not drop an existing cluster role during extension upgrade.

### 2.6 Role creation is separate from extension object migration

PostgreSQL roles are cluster objects and are not owned by an extension. Keep responsibilities separate:

1. Add `deploy/postgres/pg_tide_roles.sql` as idempotent superuser/`CREATEROLE` provisioning SQL.
2. Add `sql/pg_tide--0.43.0--0.44.0.sql` for database-local objects, revokes, grants, views, and function changes.
3. The extension migration must succeed when the group roles have not yet been provisioned. Conditional grants use `to_regrole`.
4. The provisioning script can be rerun after installation or upgrade to apply the exact object grants.
5. Installation docs use the order: install/upgrade extension, run role provisioning, grant group membership to existing login roles.

The migration must not create passwords, alter login attributes, change object ownership to a service role, or silently grant a role to PUBLIC.

### 2.7 Authorization policy

Use one policy for every privileged SQL API:

- authorize `session_user`, never the security-definer owner or an incidental `current_user`;
- allow superuser only where PostgreSQL already gives unavoidable superuser authority;
- require membership in the narrowest canonical group role;
- apply outbox ACL and tenant checks in addition to broad role membership;
- distinguish “not found” from “not authorized” without revealing cross-tenant object details;
- propagate ACL, role lookup, SPI, grant, revoke, and tenant-filter errors;
- perform related checks and mutations in one transaction;
- revoke PUBLIC execution from every security-definer or administrative function;
- set `search_path = pg_catalog, tide` and schema-qualify protected relations and functions;
- revoke CREATE on schema `tide` from PUBLIC and service roles.

Do not add a generic policy engine or row-level-security framework. The fixed role matrix plus existing outbox and tenant ACLs is sufficient.

### 2.8 Secure network defaults

Do not introduce a global “production mode” switch whose accidental absence changes security. Each insecure behavior must require a local, explicit opt-in:

| Behavior | Default | Explicit override |
|---|---|---|
| HTTP destination | Reject | `allow_http = true` on that connector |
| Certificate/hostname verification | Required | Named development-only bypass, never implied by HTTP allowance |
| SSRF protection | Required | Named development-only bypass |
| Redirects | Disabled | Bounded redirects with every hop revalidated |
| Environment proxy use | Disabled | Explicit validated proxy configuration |
| PostgreSQL plaintext or `sslmode=prefer` | Reject for relay service connections | Explicit development connection setting plus warning |
| NATS/Kafka plaintext | Reject for supported production configuration | Explicit connector setting plus warning |

Every accepted insecure override:

- appears in config validation output;
- emits one structured startup warning without credentials;
- increments an `insecure_configuration` metric labeled only by connector type and reason;
- is visible in sanitized status;
- is forbidden in release security tests and production examples.

### 2.9 One outbound HTTP policy

`pg-tide-relay/src/http_util.rs` becomes the only direct HTTP policy implementation. It must:

- parse with a URL parser rather than string splitting;
- reject unknown schemes, userinfo where not explicitly supported, fragments, malformed ports, and ambiguous hosts;
- accept HTTPS only by default;
- normalize IPv4, IPv6, and IPv4-mapped IPv6;
- reject loopback, unspecified, private, link-local, multicast, broadcast, carrier-grade NAT, documentation, benchmarking, reserved, and cloud metadata destinations;
- resolve all DNS answers and reject the destination if any answer is prohibited;
- pin the validated addresses used for the connection so a second DNS answer cannot bypass validation;
- preserve the original hostname for Host and TLS SNI verification;
- disable automatic redirects and re-run the complete policy for each bounded redirect hop;
- disable ambient proxy environment variables by default;
- separately validate an explicitly configured proxy endpoint and redact proxy credentials.

The webhook sink's duplicate validator is removed in favor of this policy. Direct reqwest, tonic, cloud SDK, object-store, schema-registry, and telemetry clients must be inventoried. Each user-controlled outbound endpoint must either use an adapter that enforces the same policy or be rejected by production-profile validation.

Inbound webhook listeners are not SSRF clients. They still require request-size, authentication, and resource-bound review, but they do not pass through outbound URL validation.

### 2.10 Secret model

Use a small local type, not a new secrets framework:

```text
SecretRef
  Env(name)
  File(absolute_path)

SecretString
  redacted Debug
  redacted Display
  explicit expose_secret()
```

Rules:

- canonical references are exactly `${env:NAME}` and `${file:/absolute/path}`;
- the existing `${ENV:NAME}` form is accepted for one release with a deprecation warning, then normalized;
- malformed, unknown, nested, or unresolved references are errors;
- resolution occurs after catalog/config loading and before connector construction;
- resolved values never replace references in catalog JSON, history, diagnostics, or serialized config;
- connector constructors receive secret wrappers or a short-lived exposed value at the final API boundary;
- hardcoded secret-bearing fields are rejected for newly written production configuration;
- legacy inline secrets are detected, never printed, and require migration to a reference before the affected production pipeline starts;
- secret field names are connector-schema metadata, not an unbounded substring heuristic;
- recursive key-based and URL-userinfo redaction remains a defense-in-depth fallback for legacy data and third-party error strings.

The same parser and redactor must handle the process PostgreSQL URL and pipeline connector config. Do not retain separate lowercase and uppercase expansion implementations.

### 2.11 Secret-file policy

On Unix, a secret file must:

- be an absolute path;
- be opened without following symlinks;
- be a regular file;
- be owned by the relay effective user;
- have no group or world permission bits, with effective mode no broader than `0600`;
- remain within the configured file-secret root when one is configured;
- satisfy a bounded maximum size before reading;
- be read completely or return an error, never a partial/default value.

Reuse the same loader for connector secrets and `LocalKeyFile`.

On a platform where equivalent ownership and ACL checks are not implemented, file references fail closed with an explicit unsupported-platform error. Do not silently skip Unix checks.

### 2.12 Dependency policy

Production and experimental graphs have different gates:

- the `core` production graph has no advisory ignore;
- `core-kafka` must meet the production gate before Kafka can be promoted;
- `experimental-full` may have a time-limited exception only when the dependency is unreachable from production artifacts;
- every exception records advisory, affected package, feature/connector, owner, justification, opened date, expiry, and removal condition;
- expired or production-reachable exceptions fail CI;
- unsupported connectors may be removed from `experimental-full` rather than preserving an abandoned dependency chain.

Do not call a root lockfile scan a production-profile audit if it cannot distinguish unreachable optional packages. Add a graph-aware gate and separately prove that exception packages are absent from `cargo tree` for production features.

### 2.13 Encryption decision

Choose roadmap option 1:

- `LocalKeyFile` is the only supported encryption provider for v0.44.0;
- AWS KMS, GCP KMS, and Vault Transit are unavailable/experimental names, not production capabilities;
- provider SDK features that exist only for `NotImplemented` stubs are removed from production and reconsidered for `experimental-full`;
- unsupported provider configuration fails during validation/startup before a worker polls messages;
- local key files use the shared secret-file loader;
- local key rotation, previous-key fallback, backup, loss, and recovery limits are documented and tested.

Do not implement a KMS abstraction refresh, cloud credential chain, or provider integration in this release.

### 2.14 Release metadata changes last

Complete the security behavior, migration, fresh/upgrade parity, and release gates before changing:

- workspace package versions;
- `pg_tide.control`;
- Helm/chart image versions;
- changelog/release notes;
- lockfile package versions.

Do not tag, publish, push, or deploy v0.44.0 unless separately requested.

## 4. Workstream A: Threat Model and Security Contract

### A.1 Add the threat model

Create:

```text
docs/src/reference/threat-model.md
```

For every roadmap threat, record:

| Required field | Content |
|---|---|
| Asset | Messages, credentials, offsets, tenant config, role grants, release artifact, or availability |
| Actor/capability | Database login, connector endpoint, compromised credential, malicious payload, dependency publisher, operator |
| Entry point | Public SQL API, catalog JSON, CLI/config, network response, payload/header, CI/release workflow |
| Prevention | Exact role, validation, TLS, redaction, resource bound, or supply-chain control |
| Detection | Metric, structured log event, audit row, CI gate, or alert |
| Recovery | Credential rotation, rewind/replay, role revocation, artifact rollback, DLQ/retry, catalog repair |
| Evidence | Test/workflow/runbook path |
| Owner | Code owner and security contact from project ownership data |

The model must cover:

- malicious database roles;
- compromised connector credentials;
- SSRF through every outbound endpoint;
- secrets in success and failure output;
- dynamic SQL and identifier injection;
- cross-tenant reads and writes;
- dependency and build-system compromise;
- untrusted payload/header/template content;
- CPU, memory, connection, queue, payload, retry, and disk exhaustion;
- unauthorized rewind, replay, cleanup, and offset mutation.

### A.2 Document trust and support boundaries

Update:

- `docs/src/reference/security.md`;
- `docs/src/guides/security-guide.md`;
- `docs/src/SUMMARY.md`;
- connector security/runbook pages referenced by `connectors.toml`.

Remove the false statement that pg_tide has no security-definer functions. Document:

- which functions run as invoker versus definer;
- why definer rights are required;
- which caller identity is authorized;
- which objects relay and application roles can access;
- what pg_tide cannot protect after a destination credential or database superuser is compromised;
- how preview and experimental connector security differs from supported status.

### A.3 Add an executable security-evidence index

Extend the generated connector release checklist or add:

```text
docs/src/reference/security-evidence.md
```

Generate or validate entries for:

- auth test;
- TLS test;
- SSRF test where applicable;
- redaction test;
- dependency profile;
- runbook;
- threat-model rows.

Do not create a second connector registry. The page derives connector facts from `connectors.toml` and fails generation when a supported connector lacks required v0.44.0 evidence.

### A.4 Workstream acceptance

- Every roadmap threat has prevention, detection, recovery, evidence, and owner.
- Security docs agree with actual security-definer and role behavior.
- Supported connector evidence is complete and path-validated.
- No active page claims support for a cloud KMS stub or insecure default.

## 5. Workstream B: Privilege Model and SQL Migration

### B.1 Add idempotent role provisioning

Create:

```text
deploy/postgres/pg_tide_roles.sql
```

The script must:

1. Refuse to continue without `CREATEROLE`/superuser capability.
2. Create missing canonical group roles with the exact non-login attributes.
3. Correct unsafe attributes on existing canonical group roles only after explicit notices.
4. Link an existing `pg_tide_admin` to `tide_admin`.
5. Apply exact object grants when extension objects exist.
6. Be safe to rerun without duplicate memberships or privilege broadening.
7. Never create a login, password, database, schema, or extension.
8. Emit a concise verification query showing group roles and memberships without exposing login credentials.

### B.2 Add the v0.44.0 migration

Create and register:

```text
sql/pg_tide--0.43.0--0.44.0.sql
```

Update migration registration in:

```text
pg-tide-ext/src/lib.rs
```

The migration must:

- revoke CREATE on schema `tide` from PUBLIC;
- revoke direct table/sequence access from PUBLIC unless a public read is explicitly documented;
- revoke execute from PUBLIC on administrative, tenant, role, maintenance, replay, rewind, configuration, and security-definer APIs;
- conditionally grant exact privileges to canonical roles when they exist;
- preserve extension ownership;
- preserve application login roles and existing memberships;
- update administrative checks from independent `pg_tide_admin` checks to canonical `tide_admin`;
- ensure all protected definer functions have a fixed safe path;
- add sanitized read APIs/views needed by operator and reader roles;
- leave raw config/history and secret-bearing catalog access unavailable to reader/operator roles;
- remain transactional so any failed revoke/grant/function replacement rolls back the upgrade.

Do not use `GRANT ALL`, wildcard assumptions about function signatures, or ownership transfer as a shortcut.

### B.3 Inventory effective privileges, not only current source

Build the privilege inventory from a fresh installation and the full migration chain. Include:

- schema privileges;
- tables, views, materialized views, and sequences;
- every public function signature;
- security-definer flags and `proconfig` search paths;
- default privileges for the extension owner;
- role memberships;
- RLS state where tenant tables use it;
- PUBLIC grants introduced by old migrations.

The v0.44.0 migration repairs the final effective state even if the broad grant came from an older migration.

### B.4 Publisher role and outbox ACL

For each publishing entry point, including large/claim-check helpers:

1. Require `tide_publisher` or `tide_admin`.
2. Resolve caller authorization from `session_user`.
3. Require outbox-specific publisher authorization.
4. Treat missing ACL table, denied ACL query, failed role lookup, corrupt row, or tenant mismatch as an error.
5. Include outbox context in the error without listing other tenant objects.
6. Keep the authorization check and insert in the same transaction.

Reuse the existing publisher ACL implementation and fault tests. Do not create a second ACL table.

### B.5 Relay privileges

Grant `tide_relay` only the operations used by the real relay:

- read enabled pipeline config and canonical outbox rows;
- acquire/release documented advisory locks;
- write monotonic offsets;
- write delivery receipts and DLQ rows;
- call supported inbox delivery functions;
- read only the metadata required for polling, fencing, and cleanup coordination.

Prefer existing public/internal SQL APIs where they preserve batching and correctness. When direct table access is required by the current relay hot path, list exact columns/operations in the privilege matrix and test that unrelated catalog writes fail.

### B.6 Operator and reader sanitized surfaces

Add or amend functions/views so:

- `tide_reader` sees health, lag, enabled state, non-secret connector type, outbox name when tenant-authorized, and bounded operational metadata;
- `tide_operator` additionally enables/disables pipelines and runs bounded sweep/dry-run operations;
- neither role sees resolved secret values, raw credential fields, proxy credentials, payloads, or unredacted config history;
- missing tenant context or filter errors refuse access rather than returning all rows;
- replay, rewind, conversion, role grants, and configuration mutation remain admin-only.

### B.7 Security-definer audit

For every effective security-definer function:

- record purpose and owner in the privilege documentation;
- set `search_path = pg_catalog, tide`;
- schema-qualify protected objects;
- authorize `session_user`;
- revoke PUBLIC execute;
- validate identifiers using PostgreSQL identifier quoting rather than concatenation;
- avoid calling user-controlled functions/operators through an unsafe path;
- ensure errors roll back all side effects.

Delete security-definer marking where invoker rights are sufficient. Do not preserve elevated execution only for convenience.

### B.8 Privilege test matrix

Add a black-box test, for example:

```text
pg-tide-relay/tests/privilege_model_test.rs
```

Create login fixtures that are members of each canonical group plus one unprivileged role. Test allowed and denied behavior for:

- outbox/inbox create and drop;
- authorized and unauthorized publishing;
- raw message and catalog table access;
- relay poll/checkpoint/receipt/DLQ/inbox operations;
- config create/read/list/update/delete;
- pipeline enable/disable;
- tenant assign/grant/revoke/provision/deprovision;
- sanitized and raw status/history;
- sweep and dry-run;
- rewind, replay, and partition conversion;
- direct offset decrease;
- role inheritance and `SET ROLE`;
- extension owner and superuser behavior;
- legacy `pg_tide_admin` membership after upgrade.

Assertions must verify both the SQL error and the absence of side effects.

### B.9 Workstream acceptance

- Provisioning is idempotent before/after rerun.
- Fresh and upgraded databases have the same effective ACLs.
- Every role passes the allow/deny matrix.
- PUBLIC and an unprivileged login cannot invoke or mutate protected surfaces.
- Existing `pg_tide_admin` members retain only canonical admin authority.

## 6. Workstream C: Fail-Closed Extension and Relay Behavior

### C.1 Establish the fallback classification

Audit every `unwrap_or_default`, `unwrap_or(false)`, ignored `Result`, empty-row fallback, and best-effort database operation in security-sensitive code. Classify each:

| Class | Required behavior |
|---|---|
| Optional field successfully decoded and absent | Documented semantic default is allowed |
| Database query/mutation failed | Return contextual error |
| Required row/role/ACL absent | Explicit not-found/not-authorized error |
| Corrupt/null required catalog value | Corrupt-catalog error; never synthesize a value |
| Authorization or tenant filter failed | Refuse operation and roll back |
| Notification/reload signal failed | Fail mutation if the signal is part of consistency; otherwise commit only with explicit warning/metric contract |

For v0.44.0, relay configuration notifications are part of the configuration consistency contract. A failed update notification fails the mutation and rolls it back.

### C.2 Repair relay catalog operations

In `pg-tide-ext/src/relay.rs`, update configuration and tenant operations so:

- insert/update/enable/disable/delete results are checked;
- `pg_notify` failures propagate;
- `relay_get_config` distinguishes no row from SPI failure;
- list operations reject missing/corrupt required fields instead of defaulting name/config/enabled values;
- tenant assignment updates config, offsets, and related state atomically;
- no tenant filter failure broadens a query;
- contextual errors identify the pipeline operation without including config JSON.

Keep SPI blocks short and cast `name` columns to `text`.

### C.3 Repair adjacent SQL-facing fallbacks

Audit and repair:

- `pg-tide-ext/src/backfill.rs` where absence and SPI failure become the same boolean;
- `pg-tide-ext/src/inbox.rs` where schema defaults or ignored drop errors can report success;
- `pg-tide-ext/src/outbox.rs` for every publisher/ACL path;
- `pg-tide-ext/src/fanin.rs`, even though fan-in remains experimental, for offset and tenant authorization;
- `pg-tide-ext/src/lifecycle.rs` and maintenance functions for ignored grant/revoke/drop state;
- SQL migration functions that catch `WHEN OTHERS` and continue.

Add contextual `PgTideError` variants in `pg-tide-ext/src/error.rs`; do not encode security failures as `None`, zero rows, or booleans.

### C.4 Stop relay delivery on policy failures

In `pg-tide-relay/src/coordinator.rs` and related source/sink construction:

- schema-evolution policy failure stops the affected batch before sink publish/checkpoint;
- denied config, secret, TLS, SSRF, tenant, checkpoint, or DLQ operations fail the worker;
- retries apply only to classified transient errors;
- permanent security/config errors do not spin in an unbounded retry loop;
- structured errors include pipeline/connector context but no payload, credential, config JSON, or endpoint userinfo;
- metrics distinguish authorization, policy, TLS, SSRF, secret, and dependency/configuration refusal.

### C.5 Fault-injection tests

Extend existing publisher ACL tests and add targeted catalog fault tests for:

- missing ACL table;
- denied ACL table;
- role lookup failure;
- missing tenant row;
- denied tenant query;
- failure on each step of multi-table tenant propagation;
- grant/revoke failure;
- corrupt/null required catalog fields;
- notification failure;

- common localhost spellings;
- cloud metadata IPs and hostnames;

### D.4 Redirect policy

- allow at most five hops;
- resolve relative `Location` safely;
- rerun scheme, host, port, DNS, IP, credential, and proxy validation for every hop;
- reject HTTPS-to-HTTP downgrade;
- strip authorization and connector-secret headers on cross-origin redirect;
- detect loops;
- sanitize every rejected target in the error.

Webhook tests must include public-to-loopback, public-to-link-local, public-to-metadata, cross-origin credential stripping, loops, and excess hops.

### D.5 Proxy policy

- require HTTPS for the proxy unless a development override is set;
- validate the proxy endpoint with the same address rules;
- store proxy credentials as secret references;
- redact proxy URL userinfo and authentication errors;
- document that an HTTP proxy resolves/connects to the final target and therefore becomes part of the trust boundary;
- expose sanitized proxy use and insecure overrides in status;
- test `NO_PROXY` as unsupported/ignored unless explicit behavior is added.

Do not silently honor process proxy variables.

| Key-based fallback over-redacts harmless fields | Structured types are primary; fallback is limited to documented sensitive names/URL fields |
| Secret file checks reject common Kubernetes defaults | Document secure volume mode/ownership; fail closed rather than silently accepting broad readability |
| Workspace advisory is experimental-only but blocks core | Graph-aware gates plus proof of production unreachability |
| Experimental exception becomes permanent | Required owner, expiry, CI failure, and removal condition |
| Removing KMS SDK stubs breaks unused configs | Parse-time compatibility error and migration note; no silent fallback |
| History sanitation removes rollback data | Protected pre-upgrade backup and preserved non-secret audit metadata |
| Static source guards cause regex workarounds | Use generated inventories/AST-aware tools where practical and small explicit allowlists |
| Security hardening changes delivery behavior | Rerun v0.42/v0.43 crash, offset, retention, and end-to-end invariants |

---

## 16. Explicit Non-Goals

- Adding or promoting connectors.
- Implementing AWS KMS, GCP KMS, Vault Transit, or a general KMS plugin API.
- Integrating a general secrets manager beyond env/file references.
- Rotating external connector credentials automatically.
- Enforcing Kubernetes NetworkPolicy, cloud firewall, or database host firewall rules.
- Treating experimental connectors as production-supported.
- Building application-payload malware scanning, DLP, or content classification.
- Replacing PostgreSQL roles with a custom authorization engine.
- Adding row-level security everywhere without a demonstrated tenant requirement.
- Guaranteeing confidentiality after database superuser, relay host, or destination credential compromise.
- Making v0.45.0 operator packaging/installation work part of this release except where needed to provision security safely.
